## 0. The arithmetic, written out once

Everything below hangs off two functions. `FilmGrainProfile.plateScale`
(FilmLab.swift:824–830):

```
printLongEdgeMM = printSizeInches × 25.4
mag             = printLongEdgeMM / gateLongEdgeMM
pitchOnPrintMM  = (pitchMicrons / 1000) × mag
pixelsPerPrintMM= longEdgePixels / printLongEdgeMM
return max( pitchOnPrintMM × pixelsPerPrintMM , 0.5 )
```

Multiply it out: `printLongEdgeMM` appears once up and once down and cancels exactly, so

> **base(L) = max( pitch_µm × L / (1000 × gate_mm) , 0.5 )  px per plate cell.**

Print size genuinely cancels (the comment is right, and
`testGrainFollowsTheGateAndNotThePixelCount` pins it to 1e-12). Then the per-channel
form, FilmLab.swift:862–866:

```
return max( base(L) × max(sizeScale[i], 0.05) , 0.5 )
```

**The floor is applied twice** — once inside `base`, once after the `sizeScale`
multiply — and `GrainPlan.plateScale` (FilmLab.swift:1095–1099) wraps it in a third
`max(…, 0.5)`. That double application is not in R7 and it is where most of the parity
loss actually comes from, because the red record's `sizeScale` is 0.8.

Thresholds. `base` floors when **L < 500 × gate / pitch**; the **red** record floors
when **L < 625 × gate / pitch** (it needs `base > 0.625` to clear 0.5 after ×0.8).
Shipped stocks (`gate` 36 mm except Cine 24.9; pitch from FilmLab.swift:249/278/308/337/364/395):

| Stock | pitch µm | green floors below | **red** floors below |
|---|---|---|---|
| Tri-X 400 | 18 | 1000 px | 1000 px (sizeScale 1,1,1) |
| Cine 250D | 10 (gate 24.9) | 1245 px | 1556 px |
| Gold 200 | 14 | 1286 px | 1607 px |
| Portra 400 | 12 | 1500 px | 1875 px |
| **Ektar 100** | 7 | **2571 px** | **3214 px** |
| **Velvia 50** | 6 | **3000 px** | **3750 px** |

`RenderGraph.workingLongEdge = 2560` (RenderGraph.swift:24). R7's six numbers in the
green column reproduce exactly.

The other function is the kernel, `Kernels.swift:606–617`:

```
vec3 d   = -log(max(image.rgb,1e-5))/log(10);
vec3 p   = clamp(d/dmax, 0, 1);
vec3 amp = sqrt(p*(1-p));
vec3 n   = (noise.rgb - 0.5) * 8.0;      // plateEncodeScale
vec3 d2  = d + amp * n * amount;
return pow(10, -d2);
```

`n` is a **vec3** and the three components come from three plates built on three seeds
(`plateSeed(channel:)`, FilmLab.swift:790–796) whenever `!monochrome` — i.e. for every
colour stock. There is no chroma fraction anywhere on the path.

## 2. R7's two arithmetic claims

### Claim 1 — "the 0.5-px floor breaks preview↔export parity for Ektar and Velvia": **CONFIRMED, and worse than stated.**

Default Size 1.0, `sizeScale` (0.8, 1.0, 2.0). Preview at 2560, export at 8000.
Parity means the cell footprint *as a fraction of the long edge* is equal.

**Velvia 50** (6 µm). base(2560) = 6×2560/36000 = **0.4267 → floored to 0.5**.
R = max(0.5×0.8, 0.5) = **0.5**; G = **0.5**; B = **1.0**.
base(8000) = 1.3333. R = **1.0667**; G = **1.3333**; B = **2.6667**.

| record | preview cells/edge | export cells/edge | preview is |
|---|---|---|---|
| R | 0.5/2560 = 1.953e-4 | 1.0667/8000 = 1.333e-4 | **46.5 % coarser** |
| G | 1.953e-4 | 1.667e-4 | **17.2 % coarser** |
| B | 3.906e-4 | 3.333e-4 | **17.2 % coarser** |

**Ektar 100** (7 µm). base(2560) = 0.4978 → 0.5; R = G = 0.5, B = 1.0.
base(8000) = 1.5556; R = 1.2444, G = 1.5556, B = 3.1111.
R: 1.953e-4 vs 1.5556e-4 = **25.6 % coarser**. G/B: 1.953e-4 vs 1.9444e-4 = **0.44 %**.

**Portra 400** (12 µm) at 2560: base 0.8533, R 0.6827, G 0.8533, B 1.7067 — nothing
floored, ratio to 8000 is exactly 3.125 on all three channels. **Parity is exact.**

So R7's headline is right but its emphasis is off by a channel: at the default Size and
the 2560 working edge, Ektar's *green* record is off by 0.44 % (invisible), while its
*red* record is off by 25.6 % — and Velvia's red by 46.5 %. The break is the double
floor, not the single one, and it also destroys the layer structure: at 2560 Ektar's R and
G cells are the same size (0.5, 0.5) where at 8000 they differ by 1.25×.

R7 also under-states the reach. Any stock floors on a fit view: Portra 400 floors below
1500 px (red below 1875), which is an ordinary window on a laptop. The test that pins
this says so itself (§C2-04).

### Claim 2 — "colour stocks grow coloured blotches at export the preview never shows": **CONFIRMED.**

Portra 400 at 8000 px, Size 1.0: R **2.13** px / G **2.67** px / B **5.33** px cells
(R7's numbers reproduce). Three plates, three seeds, each renormalised to **unit
variance** (`FilmGrainProfile.plate`, FilmLab.swift:965–979), added per-channel by
`lumenGrain` with no cross-channel term.

The chroma arithmetic, which R7 asserts rather than computes. Let each `n_i` be
independent with σ = 1. The density perturbation is `δ_i = A·n_i`, A = amp×amount.

- luminance component (equal weights): σ_L = A/√3 = **0.577 A**
- an opponent component, e.g. R−G: σ = A√2 = **1.414 A**
- ratio **chroma : luma = 2.45**

With one shared field (the monochrome path, and what the creative grain does) the
opponent σ is **exactly 0**. So a colour stock puts 2.45× more energy into chroma than
into luminance, in cells up to 5.33 px across. At 2560 the same recipe draws 0.68 / 0.85 /
1.71 px cells — at or below the display's own sampling, where the eye integrates them back
to luminance. That is the whole of "the preview never shows it".

This is the identical arithmetic the owner already rejected once. `FilmGrainProfile
.init(creative:)` (FilmLab.swift:719–754) carries his verdict — *"it just turns into
rainbow splotches"* — and answers it by collapsing to `sizeScale = (1,1,1)` and
`monochrome = true`. The film path never got the same treatment, and at export it reaches
larger cells than the creative grain ever could.

## 3. The owner's question: should the two grain systems merge?

**Yes, and most of the merge is already done.** They are not two models. Both funnel into
one `GrainPlan` (FilmLab.swift:1048), one `FilmGrainProfile`, one plate generator, one
kernel, one stage position; `RenderPlan.swift:288–299` picks between them in four lines.
What is genuinely duplicated is the **wire format and the panel**, and that duplication is
where the defects live:

| | `FilmLab.grain: FilmGrain` (RecipeLook.swift:459–478) | `look.grain: CreativeGrain?` (Recipe.swift:986–995) |
|---|---|---|
| amount | 0–100, default `stock.grainDefault` | 0–100, default 0 |
| size | **relative** multiplier 0.5–2.0 on the stock's pitch, default 1.0 | **absolute** 0–100 → 7–56 µm at a 36 mm gate, default 50 |
| roughness | absent — hard-wired to `defaultPersistence` 0.5 (FilmLab.swift:774) | 0–100 → persistence 0.25–0.75 |
| chroma | none; 3 seeds always | none; 1 seed always |
| panel | Film Lab (LookPanel) **and** Effects › Grain | Effects › Grain only |

One word, `size`, means two incompatible things. Roughness exists but cannot be reached
with a stock loaded. The chromatic behaviour is opposite on the two paths and neither is a
control. `GrainPlan.filmOwnsTheGrain` (FilmLab.swift:1137–1141) and the whole
`stockGrainRows` / `creativeGrainRows` fork in `EffectsPanel.swift:212–218` exist for no
reason except that there are two blocks.

**The single control set** — R7 C.2.3, which I endorse with two amendments:

```
Grain {
  amount    0–100   default: stock.grainDefault when a stock is loaded, else 0
  size      0–100   pitch = 3 · 2^(4.22·size/100) µm at the gate   (3…56 µm)
  roughness 0–100   persistence 0.25…0.75            (unchanged; 50 ≡ today's 0.5)
  chroma    0–100   χ; default 30 colour neg, 15 reversal, 0 B&W or bw.enabled
  format    35mm | halfFrame | super35 | 120 | 4x5   (sets gate_mm; replaces printSize)
}
```

Amendment 1 — **`size` must be absolute, and the range must start below 7 µm.** R7's own
migration `size_slider = 100·log2(stockPitch·size/7)/3` returns a **negative** slider
position for Velvia 50 (`100·log2(6/7)/3 = −7.4`) and −40.7 at Velvia Size 0.5 — the
merged control cannot express two shipped stocks. The reachable set the merge must cover
is `min(stockPitch) × min(FilmGrain.size)` = 6 × 0.5 = **3 µm**, hence 3…56 µm and
`size_slider = 100·log2(pitch/3)/4.22` (100 → 3·2^4.22 = 55.9 ≈ 56).

Amendment 2 — **`chroma` is not optional polish; it is the fix for §2 claim 2.** The
kernel gains one line, `n = nL + chroma*(nc - nL)`, and the alpha channel of the existing
RGBAf plate already has a free slot for `nL` (`grainPlate` writes alpha only on the red
tile, PipelineRenderer.swift:1469). χ=0 reproduces the creative grain bit-for-bit; χ=1
reproduces today's film grain bit-for-bit, so the migration has an identity setting.

**The numeric test that proves grain is identical at preview size and export size.**
New `Tests/LumenCoreTests/GrainParityTests.swift`, LumenCore only, no GPU:

1. **The closed-form gate — one assertion, red today, no rendering at all:**
   ```swift
   for stock in [portra400, ektar100, velvia50] {
     let p = FilmGrainProfile(stock: stock, size: 1.0, amount: 50, pushPull: 0)
     for ch in 0..<3 {
       XCTAssertEqual(p.plateScale(longEdgePixels: 2560, printSizeInches: 10, channel: ch) / 2560.0,
                      p.plateScale(longEdgePixels: 8000, printSizeInches: 10, channel: ch) / 8000.0,
                      accuracy: 1e-9)     // Velvia ch0: 1.953e-4 vs 1.333e-4 → FAILS by 1.465×
     }
   }
   ```
   Sweep L ∈ {1024, 1600, 2560, 4000, 6000, 8000} × size ∈ {0.5, 1.0, 2.0} and this is the
   whole of resolution independence, stated as arithmetic.
2. **Pattern identity:** render a flat 0.18 field through `ReferenceRenderer` at
   L ∈ {1024, 2560, 6000}, box-downsample each by an integer ratio to 512, assert Pearson
   r of (render − mean) between every pair > 0.95 and σ ratio within ±10 %.
3. **Spectrum:** radially averaged power spectrum in **cycles per frame** within 1 dB out
   to 200 c/f (the 1024's Nyquist after the box).
4. **Phase lock (K-065's other half):** crop the 6000 render's central 50 %, re-render that
   crop, correlate against the same crop of the full render; r > 0.95.
5. **The rainbow gate:** at 8000 px on Portra 400, σ(a\*) and σ(b\*) of the downsampled
   grain must be < χ · σ(L\*). Today the ratio is **2.45** with no χ, so it fails at every
   χ < 1.

Assertion 1 is the one to write first: it is six lines, needs no image, and goes red on
the shipped code today.

## 4. Findings

### C2-01 — the half-pixel floor is applied twice, so the red record loses parity 1.25× earlier than the green
severity: S2
confidence: measured
class: defect
size: S
evidence: `Sources/LumenCore/Engine/FilmLab.swift:862–866` —
```swift
let base: Double = plateScale(longEdgePixels: longEdgePixels, printSizeInches: printSizeInches)
return Swift.max(base * Swift.max(sizeScale[i], 0.05), 0.5)
```
`base` is already `Swift.max(…, 0.5)` (line 829), and `GrainPlan.plateScale`
(FilmLab.swift:1096–1098) wraps a third `max(…, 0.5)`. Red (`sizeScale` 0.8) therefore
needs `base > 0.625`, i.e. `L > 625·gate/pitch`: Ektar 3214 px, Velvia 3750 px, Portra
1875 px — against 2571 / 3000 / 1500 for green.
Measured at Size 1.0, 2560 → 8000: Velvia red cells/edge 1.953e-4 vs 1.333e-4 (**46.5 %
coarser in preview**), Ektar red 1.953e-4 vs 1.5556e-4 (**25.6 %**), while Ektar green is
0.44 %.
how the owner sees it: on Ektar or Velvia the fit view shows grain a quarter to a half
coarser than the exported file, and the red and green records are drawn at the *same* cell
size on screen where the export draws them 1.25× apart — so the preview's grain has a
different colour texture as well as a different frequency.
fix: `FilmLab.swift` — compute the un-floored per-channel footprint first and apply one
floor, or better, adopt R7 C.2.3's band-limited plate so the preview is the low-pass of
the export rather than a re-pitched pattern (drop any octave whose cell is < 1 render px,
renormalise; `FilmGrainProfile.plate` already renormalises to unit variance at lines
965–979, so the amplitude is preserved for free). Test: §3 assertion 1 — it goes red on
today's code for Velvia ch0 (1.465×) and Ektar ch0 (1.256×), green for both after the fix.

### C2-02 — a colour stock lays three full-amplitude decorrelated fields, so chroma noise is 2.45× luminance noise, in cells up to 5.3 px at export
severity: S1
confidence: measured
class: defect
size: M
evidence: `Sources/LumenPipeline/Kernels.swift:612–613` —
```
vec3 n = (noise.rgb - vec3(0.5)) * 8.0;
vec3 d2 = d + amp * n * amount;
```
`n` is per-channel, from three plates on three seeds (`FilmGrainProfile.plateSeed`,
FilmLab.swift:790–796) each renormalised to unit variance. With independent unit-variance
`n_i`: σ(luma) = A/√3 = 0.577 A, σ(R−G) = A√2 = 1.414 A → **chroma/luma = 2.45**; with one
shared field it is exactly 0. Portra 400 cell sizes: **0.68 / 0.85 / 1.71 px at 2560**
(sub-display-pixel, integrates to luminance) vs **2.13 / 2.67 / 5.33 px at 8000**. There is
no chroma fraction on the path.
how the owner sees it: the export of a colour-stock recipe carries coloured speckle —
the same "rainbow splotches" he rejected in the creative grain and which
`FilmGrainProfile.init(creative:)` (FilmLab.swift:721–740) exists to prevent — and the
preview cannot show it, so it is only ever discovered in the delivered file.
fix: add `chroma` to the merged `Grain` block (§3) and one line to `lumenGrain`:
`n = nL + chroma*(n.rgb - nL)` with `nL` read from the plate's alpha (the red tile already
writes alpha and the other two write 0, PipelineRenderer.swift:1469 / RenderGraph.swift:1414–1422),
plus the same line in `ReferenceRenderer`. χ = 1 is bit-identical to today, so the goldens
move only when the default lands at 0.30. Test: §3 assertion 5 — render Portra 400 on a
flat 0.18 field at 8000, downsample to 512, assert σ(a\*), σ(b\*) < χ·σ(L\*); today the
measured ratio is 2.45 and it fails for every χ < 1.
