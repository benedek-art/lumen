## New findings

### D1-01 — Apply Look and Paste Look move a photograph between the tone-mapped and not-tone-mapped registers: a look saved off a RAW lays a second tone map on every JPEG it lands on, and a look saved off a JPEG throws away 2.5 stops of a RAW's highlights
severity: S1
confidence: measured
class: defect
size: M

evidence: `Look.render` is inside the travelling half of the partition
(`RecipeLook.swift:50`), and `LookSubset.applied(to:)` replaces the layer whole:

```swift
// LookSubset.swift:133-138
public func applied(to recipe: Recipe) -> Recipe {
    var copy = recipe
    copy.look = look                      // ← render.preset comes with it
    copy.pipelineVersion = max(recipe.pipelineVersion, pipelineVersion)
    return copy
}
```

`AppState.applyLook` (`AppState.swift:3642–3644`) runs that over the whole selection
through `updateRecipe`, and `pasteLook` (`AppState.swift:3572–3575`) does
`$0.look = look` directly. Neither consults the target file.

But `render.preset` is not an intent about a set of frames — it is a fact about **this
file**, and this codebase says so three times. `AppState.startingRecipe`
(`AppState.swift:2941–2949`) sets `"Linear"` for any file `PhotoFormats.isRendered`
recognises, with the reason spelled out at `:2919–2926`: *"A JPEG … has already been
through one: it is clipped at display white and carries a manufacturer's S-curve.
Handing it the default sigmoid applies a SECOND, which crushes the blacks, hardens the
highlights."* `WorkspaceModification.swift:43–49` repeats it, `ImageSource.swift:61–68`
repeats it a third time. `LookSubset.swift:20–25` nonetheless justifies `render`'s place
on the travelling side by claiming every look field *"reads a develop-normalized,
scene-referred image … so it computes the same thing on every frame it lands on"* — which
is exactly the property `render.preset` does not have, because a rendered file is not
scene-referred.

Measured, through the shipping curve (`DisplayTransform.tone`, `neutral` preset,
`whiteTarget 100`, `blackTarget 0.0152`, anchors −9/+5 EV), sRGB code value in → out for
a JPEG:

```
 in8   Linear (its starting preset)   Neutral (a RAW look's)   delta
   8            8.0                          1.2              -6.8
  32           32.0                         12.6             -19.4
  48           48.0                         26.7             -21.3
  64           64.0                         44.2             -19.8
 128          128.0                        132.2              +4.2
 224          224.0                        209.1             -14.9
 255          255.0                        221.7             -33.3   ← white is no longer white
```

And the other direction — a look saved off a JPEG carries `"Linear"` onto a RAW:

```
 EV over mid-grey   Neutral (cv8)   Linear (cv8)
        +2.0            207.4          220.6
        +2.5            222.4          255.0   ← clipped
        +3.0            234.5          255.0
        +4.0            250.1          255.0
        −4.0              9.4           27.4   ← shadows washed
```

Everything above +2.47 EV is clipped to paper white; 2.5 stops of highlight the display
transform was holding are gone.

how the owner sees it: he builds "Portra warm" on a RAW, selects the shoot — which on any
real job contains delivered JPEGs, phone frames, or the client's re-sends — and clicks the
look. The RAWs get the grade; the JPEGs get the grade *and* a second S-curve, so their
shadows plug (code value 32 → 13), their whites go grey (255 → 222) and they look worse
than the files he opened. Nothing on screen says why: the Looks header now reports the
frame as modified, which it is, and the preset picker is five sections down inside a
collapsed card. The reverse case is worse to diagnose — one look built on a delivered JPEG
and applied across a RAW shoot silently blows every highlight above +2.5 EV.

fix: `Sources/LumenCore/Recipe/LookSubset.swift` + the two call sites in
`Sources/LumenApp/AppState.swift`. Split `render` the way `denoise` is already split.
Minimal form — a look may never move a frame across the linear boundary:

```swift
public func applied(to recipe: Recipe, startingRender: RenderParams? = nil) -> Recipe {
    var copy = recipe
    copy.look = look
    // `preset` names a REGISTER as well as a curve: "Linear" means "this file has
    // already been tone-mapped once". That half is a fact about the target, not an
    // intent about a set of frames, so it does not travel. The four overrides do.
    if let start = startingRender {
        let targetIsRendered = start.preset == "Linear"
        if targetIsRendered != (look.render.preset == "Linear") {
            copy.look.render.preset = start.preset
        }
    }
    copy.pipelineVersion = max(recipe.pipelineVersion, pipelineVersion)
    return copy
}
```

`applyLook` and `pasteLook` switch to the photo-aware `updateRecipe` overload (which
already exists, `AppState.swift:3179`, and is what `DevelopColumn.swift:596` uses) and
pass `AppState.startingRecipe(for: photo.id, iso: photo.iso).look.render`.
`applied(toAll:)` takes `[RenderParams?]` or a `(Recipe) -> RenderParams?` alongside.
The fuller form, worth the extra field: store the source frame's own starting preset in
`LookSubset` (`sourceRenderBaseline: RenderParams?`, tolerant-decoded, nil for looks
already saved) and carry `preset` only when the photographer moved it off that baseline —
which is the same "compare against the photograph's own default, not the type's" rule the
dot and both Resets already implement, generalised to travel. That preserves "Linear as a
deliberate creative choice on a RAW", which the minimal form above refuses.

test — red today, in `Tests/LumenCoreTests/SavedLookTests.swift`, no macOS needed:

```swift
func testALookNeverMovesAFrameAcrossTheLinearBoundary() {
    // Saved off a RAW: the photographer never touched the preset, so it is "Neutral".
    let fromRaw = LookSubset.extracted(from: Recipe(look: SavedLookTests.loadedLook()))

    // A JPEG's starting point. AppState.startingRecipe writes exactly this.
    var jpeg = Recipe()
    jpeg.look.render.preset = "Linear"

    let out = fromRaw.applied(to: jpeg, startingRender: RenderParams(preset: "Linear"))
    XCTAssertEqual(out.look.render.preset, "Linear",
                   "a look laid the default sigmoid on a file that already carries the "
                     + "camera's own curve — a second tone map, persisted")
    // The creative half still travels.
    XCTAssertEqual(out.look.wheels, fromRaw.look.wheels)
    XCTAssertEqual(out.look.render.contrast, fromRaw.look.render.contrast)

    // And the reverse: a look built on a JPEG must not flatten a RAW.
    var jpegLook = SavedLookTests.loadedLook()
    jpegLook.render = RenderParams(preset: "Linear")
    let fromJpeg = LookSubset.extracted(from: Recipe(look: jpegLook))
    let raw = fromJpeg.applied(to: Recipe(), startingRender: RenderParams())
    XCTAssertNotEqual(raw.look.render.preset, "Linear",
                      "a RAW was handed the escape hatch and lost every highlight "
                        + "above +2.5 EV")
}
```

Substitution proof: restore the plain `copy.look = look` and both preset assertions fail
with the source's preset — which is what ⌥⌘V and every row of the Saved Looks list do
today.

### D1-03 — the look browser's two working verbs both destroy, neither asks, and neither can be undone
severity: S2
confidence: traced
class: defect
size: S

evidence: **Save silently overwrites.** `CatalogStore.saveLook`
(`CatalogStore.swift:1866–1888`) is save-over by design and says so at `:1852–1859`.
`AppState.saveCurrentLook` detects the collision — `let replacing = savedLooks.contains {
$0.name == clean }` (`AppState.swift:3615`) — and uses it only to pick the past tense of
the status message afterwards (`:3623`). The button is enabled on
`LookSubset.normalizedName(newLookName) != nil` and nothing else (`LookPanel.swift:265–267`),
so typing a name that already exists replaces two years of a look's contents with the
current frame's, with the confirmation arriving after the fact.
**Delete asks nothing.** `LookPanel.swift:250–261` wires a bare trash glyph, inside a
`Lumen.rowHeight` row, directly beside the full-width Apply button, to
`state.deleteLook(look)` → `CatalogStore.deleteLook` → `DELETE FROM look`
(`CatalogStore.swift:1951–1953`). `AppState.swift:3668–3670` knows: *"Deliberately said out
loud: throwing a look away is not undoable."* Looks are not in `HistoryStack` — `undo()`
replays `recipes`, not catalog rows.
And the one non-destructive way to keep a second variant, which `CatalogStore.swift:1859`
names explicitly (*"Renaming is how a second variant is kept"*), is **D1-02** — unreachable.

how the owner sees it: a pointer slip one row-height wide, and "Portra warm" is gone with
a status line telling him so. Or he saves a tweak under the name he has been using all
year and the version he liked is overwritten with no prompt. Lightroom asks before
deleting a preset; Capture One asks before deleting a style; both keep a Presets folder on
disk you can put back.

(1) Delete goes behind a `.confirmationDialog` naming the look — the same treatment
`deleteLook`'s own comment argues for. (2) Save-over goes behind a confirmation too, using

`saveCurrentLook`'s guard chain and return a `SaveLookOutcome.wouldReplace(name)` the panel
can prompt on, rather than discovering it after the write. (3) The cheap safety net worth
having anyway: `deleteLook` writes the row's `subsetJSON` into a `look_trash` table (or
simply flips a `deleted_at` column) so "Undo Delete Look" is a status-bar affordance for
the session.
test: `Tests/LumenCoreTests/SavedLookCatalogTests.swift` —

### D1-06 — the look browser is a column of text: no thumbnail, no hover preview, no folders, no search — and the spec asks for preview cards by name
severity: S2
confidence: traced
class: parity-gap
size: M

evidence: `LookPanel.swift:200–234` draws a name field, a Save button, and
`ForEach(state.savedLooks) { savedLookRow($0) }`; `savedLookRow` (`:236–262`) is a text
label and a trash glyph. The file states the absence and its reason at `:163–170`
(*"No swatches … which photograph is a question this pass did not answer. No hover preview
either (audit UX-17 wants one and it needs a ≤100 ms proxy path that does not exist
yet)"*), and `CatalogStore.swift:355–359` says the same about the `look.thumb` column,
which is in the schema with no writer. There is also no filter field and no grouping: the
`grp` column exists, the unique index is built on it (`CatalogStore.swift:837–838`) and
`looks()` orders by it (`CatalogStore.swift:1895–1897`), but no writer ever sets it —
`CatalogService.saveLook` (`:843`) takes no group and `AppState.saveCurrentLook`
(`:3618`) passes none. So the browser is one flat unbounded list of names inside an
accordion card.
docs/05-spec-color.md:495 specifies *"Large visual preset cards, hover live-preview"* for
the stock picker; gap table §D top-5 lists rendered thumbnails and hover preview as gaps 1
and 2, against LrC hover, C1 hover, Luminar image-rendered cards and ON1 module badges.

**What a preview would cost here** (the brief's question, answered with the ladder's own
measured numbers): a look thumbnail is not a new pipeline. `LookSubset.applied(to:)` is a
pure value transform, and the draft path already renders arbitrary recipes at fixed long
edges — `DraftLadder.swift:58–63` records measured per-rung costs on the CI runner:
**80.7 ms at 1728 px long edge, 52.6 at 1024, 37.3 at 768, 34.8 at 576**, monotone across
two sweeps. A browser cell wants ~140 px, a full rung below the ladder's floor, against a
source image that is already decoded and resident for the loupe. So the honest estimate is
**≤35 ms per look**, once, cached on `(photo_id, look_id, recipe_fp)` in the artifact
cache that already exists (`CatalogStore.swift:258, 2638`) — twelve looks ≈ 0.4 s of
background work on the frame under the cursor, re-keyed when the cursor moves. Hover
preview is the same render into the loupe rather than into a cell, which is why it needs
the same budget and no new machinery. The "which photograph" question `LookPanel.swift:165`
declines to answer has an obvious answer the panel already holds: **the photograph under
the cursor** — which is also what makes the preview worth looking at.

how the owner sees it: twelve identical rows of 11 pt text. He cannot tell "Portra warm"

### D1-08 — an unknown display-transform preset name resolves to Neutral silently, so a look from a later build renders the wrong curve with the picker showing nothing
severity: S3
confidence: traced
class: defect
size: S

evidence: `RenderParams.preset` is a free-form `String` on the wire
(`RecipeLook.swift:126`, comment listing the five legal values), and resolution has no
failure case:

```swift
// DisplayTransform.swift:101-110
public static let presetNames = ["Neutral", "Soft", "Punchy", "Film Base", "Linear"]
public static func preset(named name: String) -> DisplayTransformParams {
    switch name {
    case "Soft": …; case "Punchy": …; case "Film Base": …; case "Linear": …
    default: return .neutral        // ← any unknown name, including "linear"
    }
}
```

`LookPanel.transformPresetOptions` (`:1129–1133`) builds the picker from `presetNames`, so
a recipe naming a sixth preset selects nothing in the menu while rendering Neutral, and
the Looks dot lights because `look.render != renderDefault`. Note the contrast with
**J3-01**: the *decode* side of a look is genuinely safe here —
`CanonicalJSON.decodeLookSubset` (`CanonicalJSON.swift:141–147`) merges the sparse tree
onto a full default tree before decoding, so a missing nested key falls back and an
unknown nested key is ignored, and `SavedLookTests.swift:348–355` pins that. The hole is
one layer later: the value survives the decode and is then silently mis-resolved.
Matching is also case-sensitive, so a sidecar written by hand as `"linear"` renders the
default sigmoid on a JPEG — D1-01's pixels by a different route.

how the owner sees it: only after a downgrade or a hand-edit. The frame renders on a curve
he did not choose and the picker shows no selection to correct.

fix: `Sources/LumenCore/Engine/DisplayTransform.swift` +
`Sources/LumenApp/LookPanel.swift`. Make `preset(named:)` case-insensitive over
`presetNames`, and return `nil` for an unrecognised name from a new
`preset(namedIfKnown:)` so the two callers can differ: the engine keeps falling back to
Neutral (rendering something is right), the panel shows the unknown name as a disabled row
with a caption — the same honesty `LookPanel.swift:1224` already gives a film stock this
build does not ship (*"a recipe naming a film stock this build does not ship"*).
test (`Tests/LumenCoreTests/EngineTests.swift` or beside
`FilmLabDisplayTransformTests`): `testAnUnknownPresetNameIsDistinguishableFromNeutral` —
`DisplayTransformParams.preset(namedIfKnown: "Vivid")` is nil while
`preset(named: "Vivid") == .neutral`, and `preset(named: "linear").linear == true`. Red
today on the first and the third.

## Nothing found at these — what I checked and found correct

- **K-027 is genuinely fixed at all three Reset doors**, and the fix is the right shape:
  the model writes the type's default and the caller that knows the file re-applies the
  photograph's own (`DevelopColumn.swift:594–605`), per target rather than per selection.
  The `renderDefault` parameter (`WorkspaceModification.swift:53, 156`) mirrors
  `denoiseDefault` exactly. What survives is not the Reset — it is the same asymmetry
  missing from the two *travel* paths (D1-01).
- **The look decode is not J3-01.** `CanonicalJSON.decodeLookSubset`
  (`CanonicalJSON.swift:141–147`) merges the sparse tree onto a full default tree before
  handing it to `JSONDecoder`, so every nested type sees every key it declares; every type
  inside `Look` additionally hand-writes `init(from:)` with `decodeIfPresent` +
  the memberwise default (`RecipeLook.swift:98–119, 166–174, 219–225, 269–282, 302–307`).
  A field added to a nested type by a later build cannot throw the way `ExportRecipe`'s
  does, and `SavedLookTests.swift:348–355` pins it. Two further differences make the blast
  radius smaller even if one did throw: looks are one row each rather than one blob, so a
  bad row costs one look (`LookRow.subset()` at `CatalogStore.swift:382–384`,
  `AppState.swift:3638–3641` reports it by name), and nothing rewrites the table on the
  next edit the way `saveExportRecipes` does. **This surface is the good version of what
  J3-01 found.**
- **`LookSubset`'s partition is total and enforced.** `carriedRecipeKeys` /
  `uncarriedRecipeKeys` (`:98–110`) cover every top-level `Recipe` key, and
  `SavedLookTests.swift:116–126` fails by name when a key is added to neither. The
  develop/masks exclusions are correct and the crop and white-balance prongs
  (`:185–216`) are the right things to have pinned. My one disagreement with the partition
  is `render.preset`, and it is D1-01.
- **`max` on `pipelineVersion` in `applied(to:)`** (`:136`) is right in both directions and
  is tested both ways (`SavedLookTests.swift:255–276`). (M-06 correctly notes that
  `pasteSettings` does not do the same; `pasteLook` at `AppState.swift:3574` does not
  either, and that is M's row, not a second finding here.)
- **`normalizedName`** (`:160–169`) trims, collapses and caps, is used on every entry to
  the store (`CatalogStore.swift:1869, 1909, 1928`) and on the panel's enable check
  (`LookPanel.swift:265–267`), and is tested at three boundaries.
- **`renameLook`'s taken-name check** is redundant with the unique index and says so
  (`CatalogStore.swift:1920–1926`), correctly, including the substitution proof for why the
  redundancy earns its place.
- **`decodeLook`** (`CatalogStore.swift:3344–3351`) tolerates an unknown `kind` rather than
  throwing, which is the right posture and is documented at `:3340–3343`.
- **The empty-list-draws-nothing decision** (`LookPanel.swift:226–230`) is defensible as
  written; I did *not* file it as a "silent failure looks like empty" finding because
  `looks()`'s failure fallback is logged (`CatalogService.swift:727`) and the catalog-absent
  case is caught one level up (`AppState.swift:3587–3590`).
- **`ControlIndex`** correctly does *not* offer `look.lut`, and records why
  (`:125–134`) — the one place in this area where a dead field was removed from a surface
  rather than left on it.
- **The accordion does not build a closed section's rows** (`DevelopColumn.swift:522`),
  so `savedLooksSection`'s `.onAppear` refresh (`LookPanel.swift:193, 196`) fires once per
  opening of the Looks card and not on a timer — which is the behaviour its comment claims.
