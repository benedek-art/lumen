## Findings

### F3-01 — Painting with a multi-photo selection replaces every selected photo's strokes with the primary's
severity: S1
confidence: traced
class: defect
size: S
evidence: `MaskCanvas.swift:1770-1779` — `.strokes` case:
`state.updateRecipe(coalescingKey: nil) { recipe in … recipe.masks[m].components[index].strokesRef = ref }`
with no `targets:`; `AppState.swift:3112` `let targets = explicit ?? editTargets`;
`:2327-2331` `editTargets` = `selectedPhotos` when `selection.count > 1`. The set being
written was built from the PRIMARY's existing strokes only (`LoupeView.swift:1450-1452`
→ `MaskCanvas.swift:1170-1179` `var set = strokes; set.strokes.append(stroke)`). The
mutation matches by mask id, and ids are shared across photos after Paste Settings
(`AppState.swift:3430-3437` `recipe.masks = source.masks`) or Paste Masks when the id
is not already taken (`Recipe.swift:73-75, 84-86`). The `.component` case (`:1758-1763`)
has the same shape for radial/linear handle drags.
how the owner sees it: paste a sky mask + brush across a sequence, select five frames,
touch up the brush on the primary — the other four frames' brush masks silently become
the primary's painting (their blobs stay on disk, unreferenced). One undo step per stroke.
fix: `MaskCanvasEdit.apply` → `state.updateRecipe(targets: [primary])` for both cases
(canvas gestures are about one picture; the same reasoning Escape-in-crop already
applied). Move the per-photo rule into LumenCore as `Recipe.settingStrokesRef(maskID:index:ref:)`
and add `PasteMasksTests.testACanvasStrokeTargetsOnePhotograph`: two recipes sharing a
mask id, apply the edit to one, assert the other's `strokesRef` unchanged — goes red when
the `targets:` narrowing is removed.

### F3-02 — Above ~20k points the sidecar drops the photo's ENTIRE stroke payload, silently
severity: S1
confidence: measured
class: defect
size: M
evidence: `BrushStroke.swift:237` `payloadLimit = 1_400_000`; `:261`
`guard base64.count <= payloadLimit else { return nil }`. `CatalogService.swift:639-644`
passes `strokes: .some(payload)` → `:976` `content.strokesPayload = nil` → `XMPSidecar.swift:408-410`
omits `<lumen:strokes>` → `XMPMerge.stripOwnedElements` (`:235-285`) deletes the element
the previous flush wrote. Measured (Python, same shortest-round-trip float repr, sorted
compact JSON, base64): the cap is **22,300 points with a mouse (47 B/pt) and 20,200 with a
tablet (51 B/pt)**, not 26,300. At 120 Hz that is ~3 minutes of brush time on one photo.
No log line, no `onFailure`, no badge. No test covers the cap (grep `payloadLimit` in
`Tests/` → 0).
how the owner sees it: nothing, until the catalog is gone — then every brush mask on any
photo he painted for more than a few minutes rasterizes empty (or floods the frame,
F3-03), while lightly-painted photos restore fine.
fix: (1) implement docs/08 §8.9's delta + zstd inside the base64 (`BrushStrokeSidecar`
only; the key stays) — ~10× headroom; (2) never regress: on cap overflow keep the
previously written payload (`enqueueSidecar` treats overflow as `nil`, not `.some(nil)`),
and log + `onFailure`; (3) or spill to `NAME.lumen-strokes` beside the sidecar. Test:
`BrushSidecarTests.testTwentyFiveThousandPointsStillReachTheSidecar` — 25k-point set,
`payload(for:)` non-nil and decodes to the same pixels; goes red with the current encoder.

class: defect
size: S
evidence: `MaskRaster.swift:167-168` `let usable = mask.components.contains { $0.validationError() == nil }`;
`RecipeMasks.swift:477-478` a brush validates on `strokesRef != nil` alone; `:193`
`if c.validationError() != nil { continue }` passes it; `:195` `strokeSets[ref]` → nil →
`brushPlane(…, strokes: nil)` → zero plane; `:210-211` `componentAlpha(raw: 0, invert: c.invert)`

### F3-04 — K-018 residual: the schema's `blob` table is built and unwired; strokes live in a directory no backup or restore touches
severity: S1
confidence: traced
class: defect
size: M
evidence: `Schema.swift:77-82` `CREATE TABLE blob (hash, bytes, data, created_at)` — zero
readers or writers (grep `INTO blob|FROM blob` → only the CREATE). `CatalogService.swift:100-101`
`BlobStore(directory: …/blobs)`; `CatalogStore.swift:1272` `VACUUM main INTO …`;
`CatalogService.backup()` `:1224-1246` copies nothing else; `recoverIfNeeded`
`:1184-1216` restores `lumen.db` only. docs/15 §15.3 puts blobs in the table for exactly
this reason ("mirrored into sidecars; garbage-collected … §15.8").
how the owner sees it: restore a backup onto a new Mac (or lose Application Support):
every brush mask under the cap comes back from the sidecar on rescan; every one over it
(F3-02) is gone; nothing in the backup set contained them.
fix: write blobs to the `blob` table (keep the directory as a read fallback for one
release), so `VACUUM INTO` and `recoverIfNeeded` carry them by construction; or copy
`blobs/` with each backup and restore it. Test: `CatalogTests.testABackupCarriesTheBrushBlobs`
— store a set, `backup(to:)`, open the copy, `strokeSet(for: ref)` non-nil; red today.

### F3-05 — Every stroke stores the whole set as a new blob and pins it in an unbounded cache: O(n²) disk and memory, never reclaimed
severity: S2
confidence: traced
class: defect
size: M
evidence: `MaskCanvas.swift:1170-1179` appends to the full set and content-addresses the
whole thing; `:1769` `blobs.store(payload)` (a new file per stroke — the hash changes);
`:1776` `state.remember(set, ref:)` → `AppState.swift:2289-2291` into `strokeCache`
(`:2213`), which nothing ever removes from (grep `strokeCache` → 7 sites, all inserts).
`BlobStore` has no delete API; docs/15 §15.8's mark-and-sweep does not exist. Number: 200
strokes × 100 pts × 47 B ≈ 4.7 KB/stroke → Σ 4.7 KB × 200·201/2 ≈ **94 MB on disk and
94 MB in `strokeCache`** for one painting session on one photo; a retouch day across 50
frames is gigabytes that outlive the strokes they belong to.
how the owner sees it: Application Support grows by the square of his brush use;
memory climbs across a session; undo history is the only thing referencing 199 of the
200 blobs.
fix: (a) blob sweep in maintenance — mark from every current recipe + history ring,
delete the rest (`BlobStore.sweep(keeping:)`); (b) evict `strokeCache` entries not
referenced by the selection's recipes on selection change. Test:
`CatalogTests.testSweepKeepsOnlyReferencedBlobs` — store 3, mark 1, sweep → 2 gone, the
kept one still decodes; red without the sweep.

### F3-06 — One unknown enum case (a mask kind from a newer build) fails the whole recipe; the photo opens without ANY edit
severity: S2
confidence: traced
class: defect
size: M
evidence: `RecipeMasks.swift:539-540, 548, 552, 566` `decodeIfPresent(MaskOp/MaskKind/
MaskChannel/LuminositySeries.self)` — an unknown raw value throws, it is not nil;
`Recipe.swift:211` decodes `[Mask]` strictly; `RecipeDecoding.swift:34-37` records this
as deliberate ("recorded rather than fixed"). Downstream: `CatalogService.swift:198-215`
opens the photo with `recipe = nil`; the sidecar cannot fill in because
`XMPSidecar.swift:203-205` runs the same decoder. The next slider touch on that photo
saves a fresh recipe over the stored one.
how the owner sees it: open a folder edited on a build with a new mask kind — those
frames show as unedited (develop, look, every other mask), and the first edit he makes
overwrites the stored document.
fix (shared with M): decode `masks` lossily — keep decodable masks, carry undecodable
ones as opaque `JSONValue` so re-encode preserves them byte-for-byte, and surface them
as disabled "unknown kind" rows. Test: `RecipeCodecToleranceTests` — recipe with masks
[radial, {kind: "aiFoo"}] decodes with the radial intact and re-encodes containing
`"aiFoo"`; red today (throws).

### F3-07 — `restoreStrokes` re-parses a sidecar the merge just parsed, per photo per scan
severity: S3
confidence: traced
class: defect
size: S
evidence: `CatalogService.swift:463` `readSidecar(for: file)` inside `merge`, then `:479`
`readSidecar(for: file)?.strokesPayload` again — two `XMLParser` passes over a document
that can be 1.4 MB, on the serial catalog queue, once per photo per folder open. Traced
count: N photos → 2N parses; a 5,000-frame folder pays 5,000 extra.
how the owner sees it: slower folder open on painted folders; nothing else.
fix: return `SidecarContent` from `merge` and hand it to `restoreStrokes`. Test: inject
the reader and count calls (1 per photo).

### F3-08 — Sidecar payload integrity check depends on encoder byte-stability, and re-encodes the whole map to do it
severity: S3
confidence: inferred
class: defect
size: S
evidence: `BrushStroke.swift:281` `sets.filter { ref, set in (try? set.blobRef()) == ref }`
— `blobRef()` re-runs `JSONEncoder` and hashes the output; any change in Foundation's
Double formatting between the writing and reading platform/build silently drops EVERY
restored set as "corrupt" (indistinguishable from the forged-key case
`BrushSidecarTests:160-170`). It also re-encodes up to 1 MB of JSON on every scan.
how the owner sees it: a sidecar written on one OS/build restores empty brush masks on
another, with the merge reporting success.
fix: carry each set as base64 of its stored bytes and hash those bytes (byte-exact,
encoder-independent); keep the forged-key test. Test: a payload whose set was encoded
with a different number format (e.g. `1.0` vs `1`) must still restore.

### F3-09 — Sidecar size: the merge path walks a 1.4 MB document as `[Character]` ~11 times per flush
severity: S3
confidence: traced
class: defect
size: M
evidence: `XMPMerge.swift:50` `Array(original)` (16 B per `Character` → ~22 MB for a
capped payload); `stripOwnedElements` `:244-252` restarts its scan at index 0 for each
owned element — 9 owned elements = 9 full passes, plus `stripOwnedAttributes` and
`ensureNamespaces` = 11 passes; `escapeXML` `:414-436` appends the base64 scalar by
scalar. Per flush, per painted photo, on the catalog queue every 2 s while painting.
how the owner sees it: the queue that serves thumbnails stalls behind each flush on
heavily painted frames.
fix: one forward scan collecting owned spans, then a single splice; escape on `Data`.
Tied to F3-02 — compression shrinks the input 5–10× before any of this runs. Test:
existing `testUpdatingIsIdempotent` byte-equality kept; add a timing assertion under a
1 MB payload (< 20 ms).
