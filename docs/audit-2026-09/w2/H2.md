## Did the scopes show the photographer A1-01?

A1-01 measured Contrast +100 crushing 1.875 stops of highlight and 3.037 of shadow.
Re-running A1's code-value table through what this area actually bins (the preview is
`RGBA8` sRGB — `PipelineRenderer.swift:512-514` — and `Histogram.clipEpsilon` puts the
high threshold at code **254.97** and the low threshold at code **0.804**, i.e. only
code 255 and only code 0):

| scene EV | Contrast 0 | histogram says | Contrast +100 | histogram says |
|---|---|---|---|---|
| +3.0 | 234.51 | clean | 254.83 | **HIGH-CLIP** |
| +3.5 | 243.73 | clean | 255.00 | **HIGH-CLIP** |
| +4.5 | 253.85 | clean | 255.00 | **HIGH-CLIP** |
| −4.0 | 9.41 | clean | 1.01 | clean |
| −5.0 | 3.85 | clean | 0.51 | clean (rounds to 1) |
| −6.0 | 1.45 | clean | 0.50 | LOW-CLIP (rounds to 0) |

**The highlight half is caught, the shadow half is not.** The white triangle lights and
`% white` climbs the moment Contrast passes the point where +3 EV reaches code 255, so a
photographer watching the corner would have seen the highlight burn. The shadow crush is
invisible *as a number*: −4 EV goes from code 9.41 to 1.01 — nine tenths of its remaining
separation gone — and stays on the clean side of a threshold that only counts code 0. It
shows only as a wall at the left edge of the trace, which `normalized()` deliberately
saturates (`Scopes.swift:317-338`), so the shape says "there is a lot down here" and
never "three stops of it are the same value". The instrument does not measure loss of
separation, only pinning at the ends. That is also true of Lightroom, so it is a
statement about the class of instrument rather than a defect — but it is the reason the
`% black` readout could not have warned him, and it is worth recording next to A1-01.

## What I checked and found CORRECT

- **Zone tiling and hit-testing.** `Histogram.zoneBoundaries` (`Scopes.swift:446-475`)
  sanitizes the pivot list, forces strict ascent with a 1/1024 minimum gap, and tiles
  [0,1] with boundaries at pivot midpoints — no gap, no overlap, so a drag anywhere lands
  in exactly one slider. Re-derived: defaults `[0.08, 0.25, 0.5, 0.75, 0.92]` give windows
  `0–0.165 / 0.165–0.375 / 0.375–0.625 / 0.625–0.835 / 0.835–1`.
- **The histogram uses its OWN pivots, not `develop.zones.pivots`** — `HistogramView.swift
  :304-320`, with the reasoning recorded. That is the right call: the Zones register lives
  on the scene-EV axis and the histogram on the display-encoded one, and the file says so.
- **Zone drag is absolute, not accumulating.** `dragStartValue` is latched on first event
  (`HistogramView.swift:341-346`) and every subsequent event recomputes from
  `startValue + translation`, so no rounding drift; one `coalescingKey` per slider means
  one undo step per drag (`:380`).
- **Triangles are genuinely channel-diagnostic.** `clippingColor` (`:450-459`) is
  `ClippingOverlay.colour(mask:)` of `clippingMask(end:threshold: 0.00005)` over R/G/B
  only, so a blown red channel paints red and all three paint white. The `0.00005`
  threshold is 8.7 samples of a 174,592-sample proxy — a sane floor.
- **Spike-resistant normalization.** `Histogram.normalized` (`Scopes.swift:325-347`) scales against the
  99th-percentile *occupied* bin with a ceiling index, so a four-bin histogram scales to
  its tallest and a +5 EV white spike cannot erase the graph. `HistogramDisplayTests`
  covers all three branches including the sparse case.
- **Non-finite discipline.** Every `Int(x)` in `Scopes.swift` is preceded by an
  `isFinite` guard and a clamp (`:276-292`, `:786-808`, `:1126-1140`, `:1326-1341`);
  non-finite samples are excluded from `sampleCount` so percentages stay denominated in
  what was actually measured. This is the rule the file's header states and the code keeps.
- **The skin line is now correct.** `ColorEngine.skinLineDegrees = 56.4` measured from
  `+a` (`ColorEngine.swift:255`), aliased by `Vectorscope.skinToneLineDegrees`
  (`Scopes.swift:1393`), and `skinLinePoints` plots it with `cos/sin` from `+a`
  (`:1432-1450`) — consistent. `skinToneLineDegreesFromB` = 33.6° is the traditional
  reading. The graticule wedge and dashed line are drawn from those points
  (`ScopesView.swift:240-258`). One consumer, one constant.
- **Vectorscope orientation.** `counts` is row-major with row 0 at `+b`
  (`Scopes.swift:1334`: `v = Num.saturate((1 - b * invExtent) * 0.5)`), and `ScopeRaster.vectorscope`
  blits rows straight out with no flip while `ScopeRaster.waveform` *does* flip
  (`row = height - 1 - bin`). Both match their stated conventions exactly.
- **The raw-truth panel's honesty machinery.** Provenance is required at `compute`
  (no default), rides in flags bits 0 and 1–3 written together, and
  `provenance(fromFlags:)` (`Scopes.swift:1006-1013`) resolves all three disagreement cases
  toward the *narrower* claim. `RawTruth.readout` prints a qualification for every
  provenance including "this row is not evidence of anything" for `unspecified`. The
  33 tests in `RawTruthTests` are substantive, with negative controls.
- **Stale-result discipline.** Both feeds bump a generation and re-check it on both sides
  of every `await` (`ScopeData.swift:62-85, 100-153`; `RawTruthFeed.swift:44-95`),
  including the empty-selection branch. Paging fast cannot put the previous photo's
  numbers under this photo's name.
- **The clipping overlay is wired end to end** — triangle hover/click →
  `state.clippingOverlay` → `LoupeView.swift:1492` `ClippingOverlayView` → badge at
  `:1828`. Not a dangling control.
- **`ScopesView` measures nothing and rasterizes nothing in `body`** — the CGImages are
  built once per measurement on the detached task (`ScopeData.swift:71-80`). The comment
  at `ScopesView.swift:33-38` describes what the code does.

### H2-01 — The histogram's clipped % is measured on a 512 px box-average, so a blown highlight smaller than ~32 px on a 45 MP file reports 0.00000 %
severity: S2
confidence: measured
class: defect
size: S
evidence: `ScopeData.swift:40` — `static let scopeProxyLongEdge: Int = 512`; the frame is
box-averaged down to it by `CGContext.draw` (`ScopeData.swift:197-208`, and the comment at
`:186-191` confirms averaging is deliberate). `Scopes.swift:128-148` defines the proxy this
file says the instrument uses — `ScopeProxy.targetPixels = 1_000_000` — and
`grep -rn ScopeProxy Sources/ Tests/` finds **no call site anywhere**: `ScopeProxy` is dead
code. docs/04:502 specifies "a ~1 MP proxy"; 512×341 is **174,592 samples, 5.73× short**.
Re-derived for a 45 MP file (8192×5464 → 512, box factor 16, each sample the mean of 256
source pixels — a sample only reaches code 255 if essentially all 256 contributors do):

| blown square (source px) | true % of frame | histogram reports | |
|---|---|---|---|
| 8×8 | 0.00014 % | 0.00000 % | invisible |
| 16×16 | 0.00057 % | 0.00000 % | invisible |
| 32×32 | 0.00229 % | 0.00057 % | 25 % of truth |
| 64×64 | 0.00915 % | 0.00515 % | 56 % of truth |
| 256×256 | 0.14641 % | 0.12868 % | 88 % of truth |

Compounding it, the frame binned is 8-bit **and dithered**: `PipelineRenderer.swift:464`
applies an 8×8 Bayer plate at ±0.5 LSB *before* the `RGBA8` quantize at `:512-514`, so on a
flat region pinned at exactly display white up to half the cell's pixels are nudged off
code 255 and out of the count.
how the owner sees it: the specular on a wet rock, the sun through leaves, a blown catchlight
— everything that is genuinely gone and small — reads `0.00% white` with a dark triangle,
and he exports the file believing it. The `⇧H` cull panel *does* warn about exactly this
(`RawTruth.Plan.samplingNote`, `RawTruth.swift:126-131`: "a large blown region reads true,
an isolated clipped pixel is averaged down"); the develop histogram, which is on screen all
day, prints no such caption.
fix: `Sources/LumenApp/ScopeData.swift`. (1) Raise the proxy to the definition the codebase
already contains — call `ScopeProxy.proxy`/`ScopeProxy.factor` instead of the hard-coded
512, giving ~1 MP and a factor of 8 rather than 16. (2) Carry a per-block **max** alongside
the mean for the clipping counters only, so one blown source pixel survives the downsample —
that is what makes the number a measurement rather than an area estimate. (3) Print
`samplingNote`'s develop equivalent under the graph, as the cull panel does.
test (red today): in `Tests/LumenCoreTests`, build an `ImageBuffer` of 2048×1365 that is
mid-grey with one 16×16 patch at `RGB(gray: 4.0)`, downsample it by the shipped factor, and
assert `Histogram.compute(...).clippedFraction(.red, end: .high) > 0`. It is exactly 0 today
and stays 0 if the max-carry is removed again.

### H2-02 — The readout-space picker never reaches the bins: every clipping number is judged in sRGB whatever the label says, and on the tap the app uses it cannot be anything else
severity: S2
confidence: traced
class: defect
size: M
evidence: `ScopeData.swift:158-171` — `measure` is `nonisolated static` with no access to
`state`, and hard-codes the space four times: `Histogram.compute(..., readout: .srgb255)`
(`:160`), `Waveform.compute(..., readout: .srgb255)` (`:163`), `Parade.compute(...,
readout: .srgb255)` (`:165`). `state.readoutSpace` is never passed. `ReadoutTransform`
(`Scopes.swift:74-120`) is written to do exactly this job and has **no non-default caller**:
its `output:`/`outputTransfer:` parameters are never supplied anywhere in `Sources/`.
`HistogramView.swift:273-277` states the consequence in its own words — "The axis is ALWAYS
sRGB-encoded — `ScopeData` bins with `.srgb255` whatever the picker says". Because clipping
is judged in the readout space (`Scopes.swift:283-285`, `value <= clipEpsilon` /
`>= 1 - clipEpsilon` on the *readout-linear* triple), picking "Output 255" with a Rec.2020
or ProPhoto export target still reports sRGB clipping. And it could not report anything
else on this tap: the frame handed to the scopes is an 8-bit **sRGB** `CGImage`
(`PipelineRenderer.swift:512-514`) drawn into an 8-bit **sRGB** context
(`ScopeData.swift:203-208`), so working-space headroom above 1.0 and everything outside the
sRGB gamut were clamped away two stages before the binner saw a pixel.
how the owner sees it: he picks "Working %" or "Output 255", the graph does not move, and
the percentages do not change — because they are still sRGB numbers. The label is honest
about it (`HistogramView.swift:295-299` prints "binned in sRGB 255" when the two disagree),
which is the right disclosure and is not the feature. docs/04:498 promises the choice
"applies to histogram, cursor readouts, curve coordinates" and calls it one of the two
answers to Lightroom's fifteen-year Melissa-RGB complaint; a third of it is built.
fix: two steps, in order. (1) `ScopeData.swift`: give `measure` a `ReadoutTransform`
parameter built on the main actor from `state.readoutSpace` and the current export
recipe's colour space, and pass it to all four `compute` calls (the transform-taking
overloads already exist at `Scopes.swift:231-233`, `:1090-1094`, `:1194-1196`). (2) Take
the tap before the sRGB encode — `PipelineRenderer` already has the float image one line
above `applyDither` — so `.working` and a wide-gamut `.outputProfile` have real data to
report. Until (2) lands, the picker should refuse the spaces the tap cannot honour rather
than print a number in the wrong one.
test (red today): assert `AppState.measure(buffer, includeScopes: true,
transform: ReadoutTransform(space: .working)).histogram?.transform.space == .working`.
It cannot compile against today's signature, and once the parameter exists it stays red
until `measure` actually uses it — deleting the pass-through turns it red again.

### H2-03 — The instrument is frozen for the whole of every drag, including a drag on the histogram itself
severity: S2
confidence: measured
class: defect
size: M
evidence: two gates, and together they leave no live path in Develop.
`ScopeData.swift:99` — `if viewMode == .loupe { return }` stands the debounced refresh
down entirely in the loupe. `LoupeView.swift:1197` — the only remaining producer fires
`state.measureScopes(fromViewerFrame: cg, ...)` inside `if let cg = model.image,
!model.isDraft`, i.e. **only when a settle lands**. Every draft frame the photographer
watches during the drag is skipped. Measured cost of that settle, from
`docs/audit-2026-09/w0/perf-baseline.md` (DRAGPROBE, 1280 px): Exposure settle p50
**57.3 ms**, Saturation **269.4 ms**, Whites **388.0 ms** p50 / 477.2 ms p95. Against
docs/04:600 — "Histogram/readout refresh | every frame, <1 ms" — and docs/05:627 —
"scopes update live during slider drags, because a scope that lags is a scope you stop
trusting." The sharpest case is self-referential: **Whites** is one of the five draggable
zones (`HistogramView.swift:337-356`), so dragging inside the graph gives no feedback in
the graph being dragged for 388 ms at a time, and during a continuous drag the settles are
superseded and none lands at all.
how the owner sees it: he drags the Whites zone across the histogram to set the white
point and the trace under his finger does not move; it jumps when he lets go. Lightroom's
histogram tracks the slider live, which is the whole reason its zones are draggable.
fix: `Sources/LumenApp/LoupeView.swift` + `ScopeData.swift`. Feed drafts as well as
settles — the draft CGImage is already in hand and `measureScopes` is already
generation-guarded and already runs off the main actor, so a draft measurement costs one
detached pass and is superseded by the settle for free. Gate it on a short interval
(the existing `scopeDebounce`) so a fast drag measures a few frames rather than all of
them, and mark the trace as draft-sourced in the readout line the way the viewer marks a
draft frame.
test (red today): a `LumenAppTests` case that drives `measureScopes` with `isDraft: true`
and asserts `state.scopes != nil`. Note K-102 — `LumenAppTests` exists and no CI lane runs
it, so this test needs the lane before it means anything.

### H2-04 — Waveform blank columns (K-098), reproduced with numbers
severity: S3
confidence: measured
class: defect
size: S
evidence: `Scopes.swift:1133` — `var col: Int = width > 0 ? (x * c) / width : 0`,
with `c` fixed at 256 by `ScopeData.swift:163`. When `width < c` the map is injective but
not surjective, so `c − width` columns are never written. Re-derived at the app's 512 px
proxy:

| frame | proxy | distinct columns | blank |
|---|---|---|---|
| 3:2, 2:3, 16:9, 9:16, 1:2 | ≥256 px wide | 256/256 | 0 |
| 1:2.5 tall crop | 205×512 | 205/256 | 51 (19.9 %) |
| 1:3 tall crop | 171×512 | 171/256 | 85 (33.2 %) |
| 1:4 tall crop | 128×512 | 128/256 | 128 (50.0 %) |

`Waveform.peak` is computed over the whole grid, so the blanks are true zeros and
`ScopeRaster.waveform` leaves them transparent — the plate shows a comb.
how the owner sees it: crop a vertical panorama and the waveform becomes a picket fence of
alternating trace and black; at 1:4 half the plot is empty and the trace no longer reads
left-to-right as the picture does, which is the one property the column-major storage
convention exists to guarantee.
fix: `ScopeData.swift:163-166` — `columns: min(256, buffer.width)` for both the waveform
and the parade, so a narrow proxy gets a narrower, complete scope (the view already scales
the bitmap to the panel). One line each.
test (red today): `Waveform.compute(ImageBuffer(width: 100, height: 200) { _,_ in
RGB(gray: 0.5) }, columns: 256, bins: 64)` then assert every column in `0..<columns` has a
non-zero total. 156 of 256 are zero today.

### H2-05 — `⇧H` caches per file and claims "no slider can change these numbers", but the decode it measures is recipe-dependent
severity: S3
confidence: traced
class: defect
size: S
evidence: `RawTruthFeed.swift:24-27` — "What is cached is keyed on the FILE, not on the
edit, and that is correct precisely because of what is being measured: the decode runs
before every Lumen stage, so no slider in the app can change these numbers." The decode it
calls is `source.decode(recipe: recipe, ...)` (`PipelineRenderer.swift:1560`), and
`AppleRawSource.decode` sets, from that recipe: `filter.sharpnessAmount = defaultSharpness
* Float(dev.detail.capture.strengthFraction)` (`:299-300`),
`filter.luminanceNoiseReductionAmount` / `colorNoiseReductionAmount` (`:333-334`), and
`filter.isLensCorrectionEnabled = dev.geometry.lens.profile` (`:336`) — all four are in
`DecodeKey` (`:224-230`) precisely because they change the pixels. Capture sharpening
overshoots at edges and lens correction includes vignette gain, which brightens corners by
up to a stop or more: both create and destroy clipped pixels. The cache lookup is
`catalog.rawStatistics(photoID:provenance:)` (`RawTruthFeed.swift:77-78`) — photo and
provenance only, no recipe fingerprint — and `recordRawStatistics` writes the first
measurement back permanently (`:93`).
how the owner sees it: he opens `⇧H` on a frame with the lens profile on, sees `R 0.4%`,
turns the profile off (or drops capture sharpening to zero), reopens the panel and gets the
same cached `0.4%` forever, for a decode that no longer produces it. The number is right
once and then frozen against a recipe it no longer describes.
fix: `Sources/LumenPipeline/PipelineRenderer.swift:1556-1569`. Decode the statistics frame
with a *fixed* measurement recipe — capture sharpening 0, Apple NR 0, lens profile off —
so the claim in `RawTruthFeed`'s header becomes true, and the cache key stays correct as
written. That is also the more defensible instrument: the question is "what did the sensor
give me", not "what does it look like after this edit's sharpener".
test (red today): call `clippingStatistics` on one fixture with
`recipe.develop.geometry.lens.profile` true and false and assert the two `RawStatistics`
are equal. They are not today.
