## What I checked and found CORRECT

Recorded because it is as much of the answer as the defects are.

- **The GPU/CPU gradient arithmetic.** `lumenMaskLinear` / `lumenMaskRadial`
  (`Kernels.swift:497–537`) against `MaskRaster.linearPlane` / `radialPlane`
  (`MaskRaster.swift:508–645`), derived by hand: identical long-edge normalisation,
  identical pixel-centre convention including the `h - (r + 0.5)` flip, identical
  smoothstep orientation (`1 - t²(3-2t)`, the form whose reversal once made every radial
  hard-edged), identical `rin` pixel guard computed once on the Swift side. `maskFold`
  matches `MaskAlgebra.componentAlpha`'s clamp→invert→scale order and the zero-seeded
  accumulator. No drift.
- **`MaskGPU.isParametric`'s eligibility gate** (`MaskGPU.swift:50–71`) is genuinely
  narrow: `refine == MaskRefine()` covers all six refinement fields, not just feather, so
  a mask with only Levels touched correctly falls to the CPU.
- **`maskSourceFingerprint`** (`PipelineRenderer.swift:1396–1409`) really does cover
  everything `localStageInput(maskSource: true)` reads. That path runs S6 (matrix from
  `develop.raw` white balance + `develop.tone` exposure + `look.printerLights`), S7 (tone
  from `develop.tone` + `develop.zones`) and S9/S10 (`develop.color`, `mixer`,
  `pointColors`, `look.wheels`, `primaries`, `bw`) — `RenderGraph.swift:103–153`,
  `RenderPlan.swift:179–195`. The display transform and the film chain are downstream of
  S11 and correctly absent. No under-key here.
- **`MaskRaster.combine`'s per-component `isEvaluable` guard** (`:198–237` and `:259–277`): the
  "absent input × intersect zeroes the whole mask" hole and the "empty stack inverted
  floods the frame" hole are both genuinely closed, at both levels.
- **`BrushPlaneCache`'s key and prefix test are sound.** `componentKey|WxH|sourceKey`
  plus an explicit `set.strokes.prefix(n) == held.strokes` check
  (`BrushPlaneCache.swift:90–103`); the automask case correctly inherits the url-bearing
  `sourceKey` (`PipelineRenderer.swift:1213–1219`) and a plain brush correctly gets `"-"`
  so a tone edit does not throw the painting away. I could not break it by reading. It
  has no test at all — F2-10.
- **Resolution scaling of the refinement chain is right at the top of the range.**
  `refineRadius`, the Gaussian σ and the Edge shift are all fractions of the raster's own
  long edge (`MaskRaster.swift:325–332`, `:389`, `:438`), and `guidedEpsilon` is on a
  [0,1]-normalised guide. Preview and export agree except in the first few units of two
  sliders — F2-08.
- **`plan.masks` vs `plan.allMasks`** is used correctly on both sides: the render folds
  only enabled masks, the overlay and `maskRef` resolution see all of them
  (`RenderPlan.swift:131`, `:466–474`; `PipelineRenderer.swift:1310`, `:1230`).
- **Mask blend modes match the reference.** `lumenBlendMaskMode`
  (`Kernels.swift:578–605`) takes the luminance coefficients as arguments rather than
  hardcoding them, and its `floorY` fallbacks match `MaskAlgebra.blended`. The kernel is
  right; its *roster entry* is missing — F2-02.

## Findings

### F2-01 — a mask that does not read the picture has no photograph in its cache key, so one photo's AI matte renders on another
severity: S1
confidence: traced
class: defect
size: S

evidence:
`Sources/LumenPipeline/PipelineRenderer.swift:1178–1189`

```swift
let sourceKey: String?
if source != nil {
    sourceKey = Self.maskSourceFingerprint(recipe: plan.recipe)
        .map { sourceURL.absoluteString + "|" + $0 }
} else {
    sourceKey = "-"
}
```

`:1240–1245` — the key and the lookup:

```swift
let key = [maskJSON, "\(width)x\(height)", strokesKey, mattesKey,
           sourceKey].joined(separator: "|")
alpha = maskRasters.plane(maskID: mask.id, key: key,
                          identity: sourceURL.absoluteString,
                          allowStale: allowStaleRasters, bakeExact: bake)
```

`MaskRasterCache.swift:87–102` — the identity is passed and then not consulted, on a
stated assumption:

```swift
/// `identity` is the photograph being rendered. An exact key hit is served to
/// any photograph (the key contains the file url wherever pixels are read, so
/// an exact hit cannot lie) …
if let index = entries.firstIndex(where: { $0.maskID == maskID }),
   entries[index].entry.key == key {
    entries[index].entry.identity = identity      // adopted, never compared
    ...
    return held.plane
}
```

The assumption is false. `source` is nil whenever `needsPicture` is false
(`:1365–1370`), and `needsPicture` asks only `kind.readsSourceImage || usesAutomask` or a
refine radius ≥ 1 px — while `RecipeMasks.swift:298–303` returns **false** for every AI
kind and for `depthRange`, with the comment *"These read a cached matte rather than the
picture."* A matte is the most photograph-specific thing in the mask engine. The only
other photo-identifying term in the key is `mattesKey`, which is
`aiMattes.keys.sorted().joined(separator: ",")` (`:1239`) — the kind names, never the
pixels. So the key becomes `maskJSON | 1024x682 | | aiSubject | -`, which contains
nothing about the file.

Two reachable ways in, both without exotic input:

1. **Follow ≤ 2.** The panel seeds AI masks to `refine.feather = 10`
   (`MaskPanel.swift:1950`), which does key on the url — but the Follow row is
   `0…100, step 1, resets to 0` (`MaskPanel.swift:1645`, `refineSlider(_:_:_:_:d:)` at
   `:2298`), and `refineRadius(f, 1024) = round(0.0002·f·1024)` is 0 for f ≤ 2. At
   Follow 0 the url is absent from the key on **every** path including export; at
   Follow 1–2 it is absent on the draft path, which is also the only path allowed to
   serve stale.
2. **A `maskRef` to a disabled matte mask.** `needsPicture` walks `plan.masks` (enabled
   only), so the referenced mask's components are never inspected, while
   `MaskRaster.referenced` (`:297–316`) resolves it against `plan.allMasks` and its
   alpha genuinely depends on the matte.

`AppState.pasteSettings` (`:3514`) does `recipe.masks = source.masks` — ids verbatim,
which the cache's own header (`MaskRasterCache.swift:42–47`) names as the door it is
guarding. And `width×height` collides freely: at draft the raster is capped at 1024, so
any two 3:2 photographs produce `1024x682` regardless of sensor size (6000×4000 → Int(1024.0)×Int(682.67);
8256×5504 → Int(1024.0)×Int(682.67)). At export it collides for any two frames off the
same camera.

`MaskRasterCacheTests.testADraftNeverWearsAnotherPhotographsRaster` (`:105–120`) looks
like the guard for this and is not: it changes the **key** as well as the identity
(`"A"` → `"B"`), so it exercises only the stale door. No test drives the exact-hit branch
across identities, and no test asserts that the key `makeGraph` builds names the file.

how the owner sees it: he puts a Subject mask on one frame, turns Follow down to 0
because "Follow" does nothing he can see at 10, copies settings to the next frame of the
sequence, and that frame's subject brightens where the *previous* frame's subject was —
in the loupe and in the delivered JPEG. Nothing badges it; the mask panel shows a normal
Subject mask.

fix: `Sources/LumenPipeline/PipelineRenderer.swift` — put `sourceURL.absoluteString` in
the key unconditionally (the `"-"` branch becomes `sourceURL.absoluteString + "|-"`).
The cross-photo reuse it gives up is worth nothing now: gradients go to `MaskGPU` and
never reach this cache, a brush's `strokesRef` is a content hash, and a polygon at the
same size is cheap to re-bake. Belt: in `MaskRasterCache.plane`, require
`entries[index].entry.identity == identity` on the exact-key branch too, and delete the
"cannot lie" sentence rather than leaving a comment defending a rule the code no longer
needs. Tests, both red today: (a) lift the key construction out of `makeGraph` into
`static func maskRasterKey(mask:width:height:strokeSets:aiMattes:sourceKey:sourceURL:)`
and assert `testARasterKeyAlwaysNamesThePhotograph` over a mask whose only component is
`.aiSubject` with `refine.feather = 0`; (b) `MaskRasterCacheTests
.testAnExactKeyHitIsRefusedAcrossPhotographs` — same key, `identity: "photo-1"` then
`"photo-2"`, assert the second baked.

### F2-02 — one kernel of thirty-eight is in no availability roster, and it is the mask blend-mode kernel
severity: S2
confidence: measured
class: defect
size: S

evidence: mechanically, over `Sources/LumenPipeline/Kernels.swift` — 38 kernels are
declared as `static let … = make(…)` / `makeGeneral(…)`; `unavailableKernels`
(`:944–966`) and `unavailableMaskKernels` (`:978–996`) between them name 37. The one
missing is `blendMaskMode` (declared `:901`, source `:578`). Its only consumer is
`RenderGraph.swift:921–927`:

```swift
composite = KernelLibrary.apply(KernelLibrary.blendMaskMode, extent: out.extent,
                                [out, adjusted, alpha, mode, Float(w.r), Float(w.g), Float(w.b)])
}
guard let blended = composite else { continue }
```

`KernelLibrary.apply` returns nil for a nil kernel (`:1015–1019`), so a compile failure
does not downgrade Luminosity to Normal — it `continue`s, and the mask's **entire local
adjustment** is dropped. `testEveryKernelCompiles` (`KernelGoldenTests.swift:1443–1457`)
checks `isAvailable` and `parametricMasksAvailable`; neither list contains this kernel.
`scripts/check-swift-surface.py`'s pass 13 (`pass_kernel_reserved`, `:2288`) checks
identifiers against the language's keyword list and nothing else — it has no notion of a
roster. This is exactly N-001's shape: a kernel nobody's sentinel looks at, feeding a
call site whose failure mode is a silent no-op. The kernel does compile today (I checked
its identifiers against the CIKL/GLSL reserved set by hand), which is why this is S2 and
not S1 — the guard is missing, not the pixels.

how the owner sees it: nothing today. On the build where this kernel stops compiling —
one edit to the source, exactly as happened to `lumenMaskLinear` — every mask he has set
to Luminosity or Colour blend does nothing at all, with a green CI lane and no badge.

fix: `Kernels.swift` — add `("blendMaskMode", blendMaskMode)` to `unavailableKernels`
(it gates a stage, so it belongs beside `blendMask`, not with the parametric four). Then
close the category rather than the instance: add a pass to
`scripts/check-swift-surface.py` that parses `static let (\w+) = make(?:General)?\(` out
of `Kernels.swift` and fails when a name is in no roster — it finds exactly this one
today and nothing else, so it goes red now and green on the one-line fix. That
substitution proof is the test.

### F2-03 — the overlay and the row thumbnails still rasterize on the CPU, so N-001's fast path does not reach the gesture it was named for
severity: S2
confidence: traced
class: defect
size: M

evidence: `PipelineRenderer.renderMaskAlpha` (`:1297–1340`) is a second, parallel mask
path. It decodes, builds its own `maskSource` (`:1329`) and calls
`MaskRaster.combine` (`:1331`) directly. `MaskGPU` appears nowhere in it; neither does
`maskRasters` nor `brushPlanes`. Both consumers are the ones a photographer is looking at
while dragging a mask: `AppState.refreshMaskOverlay` (`:699` draft at 512, `:715` full at
1024) and `AppState.refreshMaskThumbnails` (`:1043`, one call per mask at 96 px).

Traced call count for one settled drag of a radial with Show Overlay on and three masks
in the stack: the render pays **zero** CPU rasterizations (`makeGraph:1197` takes the
`MaskGPU` branch and `continue`s), while the overlay pays one 512-px CPU fold per drag
frame plus one 1024-px fold on release, and the thumbnail refresh pays three 96-px folds
— each of the latter re-entering `RenderPlan(...)` and, for any picture-reading mask, a
fresh `localStageInput` render plus a GPU→CPU readback (`:1380–1384`). Against docs/23
probe (b)'s 12.8 ms for a geometry-only stack at 1024, the release-pass fold alone is
~12.8 ms and the drag-time fold ~3.2 ms, on the coordinator, per event — for a mask the
renderer now evaluates for free.

how the owner sees it: the red wash still trails the handle even though the *bright
region* no longer does. His original report — "the mask isn't updating quick enough, so
if I drag it around, it's still delayed" — is now half-true instead of true, and the half
that remains is the half he can see, because the overlay is why the overlay is on.

fix: two steps, and the first is most of the win. (1) In `renderMaskAlpha`, try
`MaskGPU.alpha(for:extent:)` first and read it back through `context.render(...,
format: .RGBAf)` into a `Plane` — the same read-back `MaskGPUParityTests.gpuPlane`
(`:125–138`) already performs, so the machinery exists and is proven. (2) The real K-007:
have `makeGraph` publish the alpha it built (`graph.maskImages[id]`) alongside the frame
so `MaskOverlayView` composites against the render's own alpha and no second evaluation
exists to disagree. Test that is red today: `testTheOverlayPathUsesTheFastPathForAGradient`
— a `MaskRasterCache`/counter-instrumented `renderMaskAlpha` over a radial-only mask,
asserting `MaskRaster.combine` is not entered; today it is entered every time.

### F2-04 — every CPU-rasterized mask is expanded 4× and then copied, 1.45 GB of transient allocation per mask on a 45 MP masked export
severity: S2
confidence: measured
class: defect
size: S

evidence: `PipelineRenderer.image(from:targetExtent:)` (`:1426–1440`):

```swift
var pixels = [Float](repeating: 1, count: plane.width * plane.height * 4)
for y in 0..<plane.height { for x in 0..<plane.width {
    let v = Float(Num.saturate(plane[x, y]))
    let i = (y * plane.width + x) * 4
    pixels[i] = v; pixels[i + 1] = v; pixels[i + 2] = v
} }
let data = pixels.withUnsafeBufferPointer { Data(buffer: $0) }
let image = CIImage(bitmapData: data, bytesPerRow: plane.width * 16, …, format: .RGBAf, …)
```

A single-channel `Plane` (which already holds `[Float]`) becomes a four-channel Float
bitmap, and `Data(buffer:)` copies it a second time. Arithmetic, per mask, at the raster
sizes `makeGraph` actually asks for:

| raster | pixels | `pixels` array | `Data` copy | peak | retained by the CIImage |
|---|---|---|---|---|---|
| export, 45 MP (8256×5504) | 45 441 024 | 727.1 MB | 727.1 MB | **1.454 GB** | 727.1 MB |
| export, 24 MP (6000×4000) | 24 000 000 | 384.0 MB | 384.0 MB | 768.0 MB | 384.0 MB |
| settle at zoom, 4096 ceiling | 11 186 176 | 179.0 MB | 179.0 MB | 358.0 MB | 179.0 MB |
| draft, 1024 proxy | 698 368 | 11.2 MB | 11.2 MB | 22.3 MB | 11.2 MB |

The retained column is per mask and lives for the whole graph build, because the CIImage
holds the `Data`: three refined masks on a 45 MP export is **2.18 GB resident** in mask
alpha alone. Gradients no longer pay this (they take `MaskGPU`), so it is the brush, the
ranges, the AI mattes and anything with Follow/Expand/Soften touched — i.e. most masks
that survive an edit.

how the owner sees it: exporting a masked 45 MP frame swaps, the beachball appears, and
on a 16 GB machine with a batch of three checked recipes it can fail outright. The
settle-at-zoom row is the interactive one: 358 MB allocated and freed per mask per settle
frame is memory-bandwidth cost paid while he waits at rest.

fix: `PipelineRenderer.swift` — (a) build the destination once, in place:
`var data = Data(count: n * 16); data.withUnsafeMutableBytes { … }`, which removes the
duplicate copy and halves peak with no behavioural question at all; (b) then drop the
expansion — `format: .Rf` with `bytesPerRow: plane.width * 4` feeding `plane.values`
directly, a further 4×, since every consumer reads only `.r` (`lumenBlendMask:443`,
`lumenBlendMaskMode:580`). (b) needs one check that Core Image hands `__sample`'s `.r`
back unpremultiplied for a single-component float image; if it does not, `.RGBAh` is the
fallback and still halves. Test, red today: `testAMaskAlphaImageIsNotExpandedToFourFloatChannels`
— assert the bytes-per-pixel of the image `image(from:)` produces (4 today, must be ≤ 8),
plus a value-parity assertion at a handful of pixels so the format change cannot alter
the alpha.

### F2-05 — a settle at zoom still costs 1.7–3.0 s of single-threaded CPU per refined mask (K-064)
severity: S2
confidence: traced
class: defect
size: M

evidence: `PipelineRenderer.swift:447–448` passes
`maskRasterCeiling: CGFloat(DraftLadder.interactiveLongEdgeCeiling)` = 4096 to every
preview, and `:1143–1147` resolves a settle to `cap = min(long, 4096)` — 4096×2731 =
11 186 176 pixels, 16.0× the 1024 proxy's 698 368. docs/23 probe (b), quoted in
`MaskRasterCache.swift:5–7`, measured `MaskRaster.combine` at the proxy in a release
build: **12.8 ms** geometry-only, **105–190 ms** through the guided refine chain. Scaled
by 16.0×, and the chain is O(pixels) throughout — `guidePlane` is a full pass plus a full
sort (`MaskRaster.swift:405–431`), `SpatialOps.guidedFilter` is six box blurs, two zips
and eight full-size `Plane` allocations (`SpatialOps.swift:246–284`), `edgeShifted` is two
`[Double]` distance transforms over the same grid (`MaskRaster.swift:479–498`) — that is
**0.20 s** for a geometry-only mask and **1.68–3.04 s per refined mask, per settle**,
single-threaded, at rest, while the photographer waits. Three masks: up to nine seconds.
The gradient case is now free (`:1197`), which is what makes this the whole residue.

how the owner sees it: he zooms to 1:1 on a masked frame, nudges Exposure, and the
picture arrives instantly at draft and then stalls for seconds before the settled frame
appears — every edit, for as long as he stays zoomed.

fix: this is K-008's fix and this finding's fix, and they are the same fix.
`RenderGraph.applyLocal` composites through the alpha, so every pixel outside the mask's
support is computed and then discarded. Give `Mask` a `boundingBox(in:)` derived from the
folded alpha (or, for the parametric components, in closed form), rasterize only that box
padded by the refine radius, and crop `applyPresence` / `applySharpen` to it
(`RenderGraph.swift:981`, `:986`). A radial covering a quarter of the frame drops both the
raster and the spatial stages by ~4×. Independently and cheaply: lower `maskRasterCeiling`
for the *refined* case only — the chain's output is smooth by construction and 2048 is a
4× cut for an edge nobody is judging at settle. Test: `MaskRasterBoundsTests
.testARefinedRadialRasterizesOnlyItsOwnBox` asserting the pixel count `combine` touches,
plus a parity assertion against the unbounded result inside the box; and a
`DragProbeTests` masked row so the number is on the lane (F2-11).

### F2-07 — the refine guide sorts a full copy of the plane to read two percentiles
severity: S3
confidence: measured
class: defect
size: S

evidence: `MaskRaster.swift:405–431`, `guidePlane`:

```swift

sorted.sort()
…
let loIndex = … 0.02 …

```

Three full-plane allocations for a two-number answer: `g` itself, the `sorted` copy, and
the `.map` at `:431`. At the 4096 settle raster that is 11 186 176 `Float`s — 44.7 MB
copied and then sorted, per mask, per settle, plus 44.7 MB for the map. `Array.sort()` is
O(n log n) with a comparator call per comparison; the two order statistics wanted here are
O(n) by a two-pass histogram over the log-luminance range (which is already bounded — the
values are `safeLog2(…, floorEV: -16)`), or by `partition(by:)` twice. Order of magnitude:
`numpy`'s vectorised sort of 11.2 M float32 in this container is 59 ms; Swift's generic
introsort on `[Float]` is several times that and is not vectorised, so this is tens to
low hundreds of milliseconds of the F2-05 budget, and all of the 89 MB.

how the owner sees it: it is inside the settle stall F2-05 describes. On its own it is
not the headline; it is the cheapest single thing to remove from it.

fix: `MaskRaster.guidePlane` — replace the sort with a 4096-bin histogram over the EV
range [-16, +4] accumulated in the same loop that already computes `ev`, then read the
2nd and 98th percentile bin edges; the guide is normalised and then clamped, so bin
quantisation of the endpoints is invisible. Keep the existing degenerate fallback.
Test: `testTheGuidePercentilesMatchAFullSort` over a synthetic buffer with a known
distribution plus a random one, asserting the normalised guide matches the sorting
implementation to 1e-3 — which is red against a naive histogram that gets the index
arithmetic wrong, and is the property that actually matters.

### F2-08 — the first units of Follow and Expand are denominated in raster pixels, so they mean different things in the loupe and in the file
severity: S3
confidence: measured
class: defect
size: S

evidence: two places, same cause.

**Follow (`refine.feather`).** `MaskRaster.swift:377–378`:
`let r = refineRadius(feather: refine.feather, longEdge: longEdge)` then
`if r >= 1, let src = source`. `refineRadius` (`:325–332`) is
`round(f/100 · 0.02 · L)`, so `r ≥ 1` needs `f ≥ 500/L`:

| raster | threshold on Follow | Follow = 1 | Follow = 2 |
|---|---|---|---|
| draft, L = 1024 | f ≥ 2.44 | **off** | **off** |
| settle, L ≈ 2800 | f ≥ 0.89 | on (r = 1) | on (r = 1) |
| export, L = 8256 | f ≥ 0.30 | on (r = 2) | on (r = 3) |

The row is `0…100, step 1` (`MaskPanel.swift:1645`), so Follow 1 and Follow 2 are
settings a photographer can land on, and on both of them the guided refine runs at rest
and in the file and does not run during the drag. The same threshold also gates
`needsPicture` (`PipelineRenderer.swift:1367–1368`), so on those two values the draft
additionally drops the url from its cache key — this is precondition (1) of F2-01.

**Expand (`refine.edge`).** `MaskRaster.swift:438–447`:
`shift = (e/50) · 0.01 · L`, `engagement = saturate(abs(shift))`, and the output is
`mix(a, rebuilt, engagement)` (`:497`). At the boundary φ = 0 the 0.5-crossing moves by
`engagement · shift`, i.e. by **shift² while shift < 1 px** — a pixel-denominated quantity
squared. At Expand = 2 the delivered boundary shift, expressed as a fraction of the frame:

| raster | shift (px) | engagement | effective shift (px) | as a fraction of the long edge |
|---|---|---|---|---|
| draft, L = 1024 | 0.410 | 0.410 | 0.168 | 1.64e-4 |
| export, L = 8256 | 3.302 | 1.000 | 3.302 | 4.00e-4 |

**2.4× further out in the file than the preview drew it** — about 2 px of boundary on the
exported frame. At Expand = 1 the ratio is 4.9×. Both converge to exact agreement by
|Expand| ≥ 5, where engagement saturates at every resolution; the tooltip's promise
("about one percent of the long edge at either end", `MaskPanel.swift:1659`) is honoured
at the ends and quadratically under-delivered near zero.

how the owner sees it: he sets Follow to 1 because 10 was too much, and the mask edge
visibly changes when he lets go of a slider — the "picture jumps on release" shape, in the
one control whose whole job is the edge. And a hairline Expand he tuned by eye in the
loupe lands twice as far out in the exported file.

fix: `MaskRaster.swift` — denominate the engagement ramp in the slider's own units rather
than in pixels (`engagement = saturate(abs(e) / edgeEngagementUnits)` with the constant
named and resolution-free), and give `refineRadius` a floor of 1 whenever `feather > 0`
rather than rounding to zero, so "Follow is on" is a statement about the recipe and not
about the raster. Test, red today:
`testTheRefinementChainIsResolutionInvariant` — rasterize the same mask with
`refine.feather = 1` and `refine.edge = 2` at 1024 and at 8192, resample the larger to the
smaller, and assert the alpha agrees to 0.02; today Follow 1 differs by the whole guided
step and Expand 2 by ~2 px of boundary.
