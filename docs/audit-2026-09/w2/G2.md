# Findings

### G2-01 — the PLAN's thumb-on-hover cannot be built without re-adding the row hover the owner asked to be removed
severity: S1
confidence: traced
class: defect
size: M
evidence: `LumenControls.swift:536-550` — the slider row has **no `onHover` at all**;
`LumenFocus.swift:39-49` records why: *"I would remove a bunch of the hover effects, like
hovering over the white balance or the temperature or tint… I don't really like the fact
that I can get that hover effect."* PLAN §UI direction item 4 requires *"thumb hidden
until row-hover on untouched sliders"*.
how the owner sees it: if U1 implements the thumb reveal the naive way it re-lands the
exact wave-of-grey the owner rejected twice; if it skips it, the headline move of the
redesign ("a panel of fifteen white dots becomes quiet") never ships.
fix: `LumenHover.swift` — add a `lumenHoverDetect(_ binding:)` that reports hover
**without painting a surface**; `LumenControls.swift` slider row consumes it and drives
only `thumbOpacity` (0 when `!isModified && !hovering && !isDragging`, 1 otherwise). The
surface fill stays focus-only. Test: `LumenAppTests` asserts a row with
`value == defaultValue`, `hovering == false`, `isDragging == false` renders thumb opacity
0, and that hovering does **not** change the row's background colour — the second
assertion goes red if anyone reintroduces `lumenHoverable()` on the row.

### G2-05 — K-035: two cursor helpers leak the `NSCursor` stack at 29 call sites

confidence: traced
class: defect
size: S
