## K-100 — ship it or remove it

**Remove the Start button's promise; keep the planner.** The sheet is not vapour: it
scans (`IngestSheet.swift:635-650`), sizes, previews the full destination path
(`:523-536`), validates both templates and offers a mechanical repair (`:452-489`). What
is missing is one file. `IngestRequest` (`:39-51`) is already the complete plan, and
`IngestDriver` (`:60-66`) is already the seam.

What shipping it costs, concretely: a `VerifiedCopyDriver` that, per file, (a) renders
`folderTemplate` per path component and `renameTemplate` through `RenameTemplate.render`
with the batch position as `seq`, (b) streams the source through an xxHash64 while
writing to each destination, (c) re-opens and re-hashes each written file, (d) records
per-destination verification independently, (e) unlocks eject only when every frame
verifies on every destination. That is the protocol the sheet already describes at
`:387-398`. Two things it must not inherit from export: `RenameTemplate.expand:113`
returns `""` for an unknown token (validation catches it at save time, but the *engine*
must refuse rather than render empty), and `RenameTemplate.sanitize:121-134` does not
reject `""`, `"."` or `".."` — the same hole J3-02 documents on the export side, and the
one place where a copy engine can lose a card.

Removing it instead is also defensible and cheaper, but it costs the one honest thing in
the sheet: it is the only surface in the app that tells the truth about a feature it does
not have (`:69-80`), and the file header says so deliberately.

### J3-01 — the tolerant preset decode is one level deep: a nested field or a new enum case still reverts every delivery preset to the stock four
severity: S1
confidence: measured
class: defect
size: S
evidence: `ExportRecipe.swift:346-375` makes every *top-level* key optional, but each
`decodeIfPresent` still hands the nested type to its **synthesised** decoder:
```swift
sharpen = try c.decodeIfPresent(OutputSharpen.self, forKey: .sharpen) ?? fallback.sharpen
metadata = try c.decodeIfPresent(MetadataPolicy.self, forKey: .metadata) ?? fallback.metadata
format = try c.decodeIfPresent(ExportFormat.self, forKey: .format) ?? fallback.format
```
`OutputSharpen` (`:130-225`), `MetadataPolicy` (`:104-122`), `Watermark` (`:229-248`) and
`HDRSettings` (`:557-574`) all take the synthesised `Codable`, and `ExportFormat`,
`ExportColorSpace`, `ResizeMode`, `OutputSharpen.Medium`, `OutputSharpen.Amount` and
`Watermark.Position` are all raw-value enums. Measured on this box with a reduction of
exactly this shape:
```
unknown enum raw value ("format":"avif")      : THREW dataCorrupted — "Cannot initialize Fmt from invalid String value avif"
nested struct missing a new field             : THREW keyNotFound(newField)
baseline sparse                               : OK, 2 entries
```
`decodeIfPresent` returns nil only for a **missing or null** key; a present-but-unreadable
value throws. `JSONDecoder` decodes an array atomically, so one bad entry takes all of
them, and `AppState.swift:1664-1669` then does `try? … ?? ExportRecipe.defaults`. The
first subsequent edit fires `didSet` (`:1652-1657`) and `saveExportRecipes` overwrites the
stored blob with the stock four — the old presets are unrecoverable. `ExportRecipeDecodeTests`
covers neither door: `testAPresetMissingANewFieldStillDecodes:28` omits only top-level
keys, and `testAListSurvivesEvenWhenOneEntryIsSparse:44` uses only valid enum values.
how the owner sees it: he adds "Copyright to IPTC only" to the metadata policy in one
build, or ships an AVIF format and the client rolls back a version — and on the next
launch the eleven delivery presets he built over two years are replaced by four stock ones
with no message, no error and nothing to restore from.
fix: `ExportRecipe.swift` — give `OutputSharpen`, `MetadataPolicy`, `Watermark` and
`HDRSettings` the same hand-written `init(from:)` treatment (`decodeIfPresent` + the
memberwise default), and decode every enum as its `RawValue` with a fallback:
`format = ExportFormat(rawValue: try c.decodeIfPresent(String.self, forKey: .format) ?? "") ?? fallback.format`.
Then make `AppState.loadExportRecipes` decode `[ExportRecipe]` **element by element**
through an unkeyed container that skips an entry it cannot read, so one poisoned row costs
one preset instead of the list — and log the skip. Test, in `ExportRecipeDecodeTests`:
```swift
func testAPresetSurvivesAFieldAddedToANestedStructAndAnUnknownEnumCase() throws {
    // (a) an old payload, read by a build whose OutputSharpen has grown a field.
    let old = #"[{"name":"Print","sharpen":{"medium":"matte","amount":"high"}}]"#
    let a = try JSONDecoder().decode([ExportRecipe].self, from: Data(old.utf8))
    XCTAssertEqual(a.map(\.name), ["Print"])
    XCTAssertEqual(a[0].sharpen.medium, .matte, "the fields that WERE there must survive")

    // (b) a payload from a newer build, read by this one.
    let newer = #"[{"name":"Future","format":"avif"},{"name":"Mine","format":"tiff"}]"#
    let b = try JSONDecoder().decode([ExportRecipe].self, from: Data(newer.utf8))
    XCTAssertEqual(b.map(\.name), ["Future", "Mine"],
                   "one unreadable entry took the photographer's whole preset list")
    XCTAssertEqual(b[0].format, .jpeg, "the unreadable field falls back; the preset does not")
    XCTAssertEqual(b[1].format, .tiff)
}
```
Substitution proof: restore the synthesised nested decoders, or `decodeIfPresent(ExportFormat.self,…)`,
and both halves fail with a thrown `DecodingError` before the first assertion — which is
exactly what `try?` swallows in production.

### J3-02 — a filename template that renders empty writes the whole delivery *beside* the destination folder, not in it
severity: S1
confidence: measured
class: defect
size: S
evidence: `AppStateActions.swift:318-333` — `renderFilename` guards only the *literal*
empty template (`out = template.isEmpty ? "{name}" : template`), not an empty **result**.
A template of `{recipe}` against a recipe whose name was cleared (the sheet permits it:
`ExportSheet.swift:384-386` is a bare `ExportTextEntry` with no validation, and
`ExportRecipeRow:351` renders the blank as "Untitled" rather than refusing it) substitutes
to `""`. `destination` (`:300-313`) then does
```swift
return folder.appendingPathComponent(base).appendingPathExtension(recipe.format.fileExtension)
```
Measured on Foundation here:
```
base=""   -> /Users/x/Deliveries.jpg      ← one level ABOVE the granted folder
base=".." -> /Users/x/Deliveries/...jpg
base="."  -> /Users/x/Deliveries/..jpg
```
`ExportRecipe.disambiguated` (`:529-550`) prevents an overwrite, so the whole batch lands
as `Deliveries.jpg`, `Deliveries-1.jpg` … `Deliveries-199.jpg` **outside** the directory
`NSOpenPanel` granted (`AppStateActions.swift:335-345`) — which is the one boundary
`sanitizedSubfolderComponents` exists to defend (`ExportRecipe.swift:479-489`), defended on
the subfolder axis and not on the filename axis. No entitlements file exists in the tree,
so the write succeeds. docs/11:213 requires the opposite — *"Bad templates (illegal
characters, empty result) refuse the Export button with the reason inline"* — and
`IngestSheet.swift:461-463` already implements exactly that check for its own templates.
how the owner sees it: he picks `~/Deliveries/Smith wedding`, presses Export on 200 frames,
and gets nothing in the folder — 200 files called `Smith wedding.jpg`, `Smith wedding-1.jpg`
… sitting next to it in `~/Deliveries`, in an order that has nothing to do with the
photographs, and no way to tell which frame is which.
fix: three lines and a guard. In `renderFilename`, after substitution and sanitizing,
`let cleaned = out.trimmingCharacters(in: .whitespaces); return cleaned.isEmpty || cleaned == "." || cleaned == ".." ? name : cleaned`
— fall back to the source basename, which is never empty and never traversal. Then port
`IngestSheet`'s guard into `ExportSheet`: a `templateProblems` computed property that
reports "the filename template renders empty for the first selected photo" and disables
Export, so a template that would need the fallback is refused rather than silently
repaired. Test, in `Tests/LumenCoreTests/` against an extracted pure `ExportNaming.render`
(the current function is `static` on an `#if os(macOS)` extension and unreachable from the
core lane — extracting it is part of the patch):
```swift
func testATemplateThatRendersEmptyStaysInsideTheChosenFolder() {
    let folder = URL(fileURLWithPath: "/Users/x/Deliveries", isDirectory: true)
    let source = URL(fileURLWithPath: "/Pictures/DSCF0001.RAF")
    for template in ["{recipe}", "", "   ", ".", ".."] {
        let base = ExportNaming.render(template: template, source: source, recipeName: "")
        let url = folder.appendingPathComponent(base).appendingPathExtension("jpg")
        XCTAssertEqual(url.deletingLastPathComponent().standardizedFileURL,
                       folder.standardizedFileURL,
                       "template \(template.debugDescription) wrote to \(url.path) — "
                         + "outside the folder the open panel granted")
        XCTAssertFalse(base.trimmingCharacters(in: .whitespaces).isEmpty)
    }
}
```
Substitution proof: restore the unguarded `out` and the `{recipe}` case fails on the first
assertion with `/Users/x` as the parent.

### J3-03 — export never gamut-maps into the destination space, so the soft proof the photographer approved is not the file he ships
severity: S2
confidence: traced
class: defect
size: M
evidence: `PipelineRenderer.exportedImage:592-603` builds its `RenderPlan` with no
`softProof:` argument, so `RenderPlan.softProof` is nil (`RenderPlan.swift:81, 171, 310-311`)
and `:622-623`'s proof composition is skipped. The only gamut operation on the export path
is `DisplayTransform.swift:345-349`:
```swift
if let gamut, white > 0 {
    let normalized = out / white
    let mapped = Gamut.softClip(normalized, boundary: gamut)
```
whose boundary is the **working** space's (`forRecipe(_:displayWhiteTarget:space:)` defaults
`space: .rec2020`, `:360-362`). `write:1005, 1021` then hands the image to
`writeJPEGRepresentation(of:to:colorSpace:)` and lets ColorSync convert Rec.2020 → sRGB,
which clips per channel. The destination-gamut compressor exists and is complete —
`SoftProofTransform.mapped` (`SoftProofTransform.swift:105-137`) composes
`workingToProof` → `Gamut.softClip` against `ProofGamut.boundary(settings.space)` →
`proofToWorking` — and `grep -rn softProof Sources/LumenPipeline` returns only preview call
sites (`PipelineRenderer.swift:354, 373, 425, 2004, 2018`, `RenderGraph.swift:217`). This
contradicts docs/11:275-280 ("gamut-maps into the destination space using the
ACES-2.0-style hue-preserving compressor") and docs/11:310-312 ("what is on screen is the
export, not an approximation") — and the export sheet's own note at `ExportSheet.swift:462-467`
states the true behaviour, so the sheet and the spec already disagree.
how the owner sees it: he presses ⇧S with Perceptual selected, watches a saturated red
dress or a deep blue sky desaturate cleanly inside sRGB, exports — and the delivered JPEG
has that red flat and hue-shifted where the proof showed it rolling off. The one instrument
built to answer "what will this file look like" answers about a different file.
fix: `PipelineRenderer.exportedImage` — build the plan with
`softProof: SoftProof(enabled: true, space: exportRecipe.colorSpace, intent: .relativeColorimetric, showGamutWarning: false, simulatePaperWhite: false)`,
so the delivery is compressed toward the recipe's own space before ColorSync sees it, and
add `intent` to `ExportRecipe` (behind the tolerant decoder of J3-01) so a print recipe can
ask for Perceptual. `showGamutWarning: false` is load-bearing — `flagged` (`:144-147`)
paints `warningColor` grey, and that must never reach a file. Test, in
`Tests/LumenCoreTests/` (core-only, no GPU): take the sRGB primary-blue corner pushed 20%
past the boundary in Rec.2020, run it through `SoftProofTransform(SoftProof(enabled: true,
space: .srgb, intent: .perceptual)).mapped(_:)` and through a bare `RGB.clamped(0,1)` in
sRGB primaries, convert both to OKLCh, and assert the compressor's hue is within 2° of the
input's while the clip's is not — then assert `exportedImage`'s plan carries a non-nil
`softProof` whose `settings.space == exportRecipe.colorSpace`. The second assertion is red
today with `nil`; the first documents why it matters and is already green.

### J3-05 — `{date}` in an export name is the file's creation date, not the capture date, so one token means two different days in ingest and export
severity: S2
confidence: traced
class: defect
size: M
evidence: `AppStateActions.swift:321-327`:
```swift
formatter.dateFormat = "yyyy-MM-dd"
let attributes = try? FileManager.default.attributesOfItem(atPath: source.path)
let date = (attributes?[.creationDate] as? Date) ?? Date()
...
out = out.replacingOccurrences(of: "{date}", with: formatter.string(from: date))
```
The ingest renamer's `{date}` is the **capture** date: `RenameTemplate.swift:97-98` reads
`context.captureDate`, seeded from EXIF per `IngestSheet.swift:372-373`. The export path
has no access to one — `renderFilename(template:source:recipeName:)` takes only a URL, and
`PhotoItem` (`AppState.swift:69-83`) carries `flag`, `rating`, `label` and `iso` but no
capture date, so the catalog's EXIF row never reaches the naming call. `.creationDate` is
the date the file arrived on this disk: a card copied a week after the shoot dates every
frame to the copy day; an archive restored from backup dates all of it to the restore; a
file with no readable attributes falls all the way through to `Date()` — **today**.
docs/11:205 lists one grammar and `ExportRecipe.swift:277-283` already records that the
export and ingest token sets diverged; this is the case where they share a token *name* and
disagree about its meaning, which is worse than not sharing it.
how the owner sees it: `{date}_{name}` on a wedding he ingested on Monday and delivered on
Thursday names every file with Thursday. Re-exporting the same job next year renames the
whole delivery to next year.
fix: give the naming function the photograph rather than the path. Add `captureDate: Date?`
to `PhotoItem` (the catalog row already holds it — the same backfill that fills `iso`),
pass it through `AppState.destination` into `renderFilename`, and use
`captureDate ?? creationDate ?? Date()` in that order. While there, add `{time}`, `{camera}`,
`{lens}` and `{iso}` — the four `ExportRecipe.swift:277-283` names as absent — from the same
value, which closes most of the grammar split for free. Test:
```swift
func testTheDateTokenIsWhenTheShutterFiredNotWhenTheFileWasCopied() {

    let name = ExportNaming.render(template: "{date}_{name}",
                                   source: URL(fileURLWithPath: "/x/DSC_0001.NEF"),
                                   recipeName: "web", captureDate: shot)
    XCTAssertEqual(name, "2026-06-14_DSC_0001",
                   "the delivery was named after the day the card was copied")
}
```
Red today: the parameter does not exist and the answer is the file's creation date.

### J3-06 — output sharpening is a per-channel unsharp mask, not the luminance pass docs/11 specifies, so a print recipe halos in colour
severity: S2
confidence: traced
class: parity-gap
size: M
evidence: `PipelineRenderer.applyOutputSharpen:1885-1896`:
```swift
let filter = CIFilter.unsharpMask()
filter.inputImage = image.clampedToExtent()
filter.radius = Float(sharpen.appliedRadius(printPPI: resolutionPPI))
filter.intensity = Float(Num.clamp(sharpen.energy(), 0, 2))
```
`CIUnsharpMask` adds `intensity × (image − blur(image))` **per channel**, in the working
Rec.2020 primaries. docs/11:240-241 specifies the opposite in as many words: *"Sharpening
runs after resize, on final pixels, in the luminance channel of the resized image."* The
function's own header (`:1870-1884`) is meticulous about the two things it does not do
(asymmetric halo weighting, which `OutputSharpen.energy`'s doc at `ExportRecipe.swift:196-214`
