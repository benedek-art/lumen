## Headline: N-002 — why the settle path misses `PlanTableCache`

**Answer: it does not "miss the cache entirely". It misses exactly the tables the
dragged control re-keys, and then it pays for them TWICE — because the blocking door
and the stale door do not know about each other. The `0h` half of the number is a probe
artifact; the `36b` half is real and is a double bake.**

### 1. Both paths mint the same key. The size asymmetry is gone.

`renderPreviewDelivery` builds ONE plan for draft and settle
(`PipelineRenderer.swift:398–437`): `lutSize: LUT3D.interactiveSize` on both
(:423, with the comment recording that draft-at-17 / settle-at-33 was removed),
same `displayWhiteTarget` (nil), same `space`, same `bandMeanHues`. The only
difference is `allowStaleTables: draft` (:434). So the four minted keys —
`cg` (`RenderPlan.swift:229`), `fin` (:352), `fin|proof` (:437),
`tonecube` (:494) — are byte-identical between a draft frame and the settle
frame that follows it. There is no key bug. That hypothesis is dead.

### 2. The `0h` is arithmetic, and it is the probe's arithmetic.

`DragProbeTests` samples the drag at `t = (event + 0.5) / events` (:225) with
`events = 48` on the draft path and `Self.settleEvents = 12` on the settle path
(:73–75, :207). Draft values are `(2e+1)/96`; settle values are `(8e+4)/96` —
odd ninety-sixths against even ninety-sixths. **They can never coincide.** And the
probe calls `PlanTableCache.resetStats()` (:210), which zeroes the counters but
does not `clear()` the entries — so the settle run is measured against a cache
full of tables it is arithmetically incapable of asking for. `0h` is guaranteed
before the first frame runs.

The `36b` decomposes exactly: 12 settle frames × the 3 tables a Whites move
re-keys. Whites writes `develop.tone.whites`, which moves
`toneEngine.whiteAnchorEV`/`blackAnchorEV`; those anchors are IN the `fin` key
(`RenderPlan.swift:355–356`) **and** in the `cg` key (:231–232), and
`develop.tone` is the `tonecube` key (:495). 12 × 3 = 36. Saturation writes
`develop.color`, which is in `cg` only: `24h/12b` = 12 finish hits + 12 tone-cube
hits + 12 colour-grade bakes. The counters are behaving correctly; the row's
reading of them ("the settle path misses `PlanTableCache` entirely") is not
supported by the code.

The cost is likewise decomposable and is a clean per-table number:
Saturation settle 269.4 − draft 24.1 = **245 ms for one blocking 33³
colour-grade bake**; Whites settle 388.0 − draft 69.0 = **319 ms for two**
(finish + colour-grade). At the header's release figure of 23.7 ms for a 33³
finish bake and the DEBUG inflation the baseline warns about, that is the whole gap.
Nothing else in the settle path is slow.

### 3. What IS real: the settle blocks on a bake that is already in flight.

This is the defect the row is pointing at, and it survives the probe artifact.

On a draft frame the finish and colour-grade tables go through
`pairedTableAllowingStale` (`PlanTableCache.swift:257`). On a key miss it serves
the newest same-identity table (:287–305), stores the exact bake in
`pending[slot]` (:296) and kicks `drainPending` on `bakeQueue` (:305).
So at the end of a gesture the exact table for the FINAL slider value is either
being baked or queued.

The settle frame then calls `table` (`PlanTableCache.swift:171`). **`table` never
reads `pending` or `inFlight`.** It looks in `entries`, misses, and runs
`build()` at :200 — the identical closure, on the identical key, while
`bakeQueue` is running it. Worse, it does not remove `pending[slot]`, so after the
settle stores its result at :205, `drainPending` (:308–330) pops the same key and
**bakes it a third time** at :318 and overwrites the entry. One gesture, one key,
up to three 33³ bakes of the same table.

`LoupeView.swift:860` multiplies it: the settle loop refuses to give up while
`PlanTableCache.anyBakePending` is true, sleeps 60 ms × attempt, and re-issues a
whole settle render — which calls `table` again, misses again (the drain still has
not landed), and blocks on yet another exact bake. The guard added to stop a stale
picture resting on screen is, in the miss case, a bake amplifier.

### 4. The fix

`PlanTableCache.swift`, one change, no call-site churn:

- Replace `inFlight: Set<Slot>` + `pending: [Slot: …]` with a per-key promise:
  `inFlightKeys: [Slot: [String: NSCondition-or-DispatchSemaphore]]`.
- In `table` (:171), between the `entries` miss and `build()`: if this exact key
  is pending or in flight, **wait on it and return its result** instead of
  building. If it is only pending (queued, not started), take it — remove it from
  `pending` and build it here, so the drain cannot repeat it.
- In `pairedTableAllowingStale` (:296), key `pending` by `(slot, key)` and clear
  the entry when any path stores that key.
- Count deferred bakes (see I1-03), so the fix is visible on the HUD.

**The test that goes red with the defect substituted back** (LumenCore, no GPU):
`testASettleJoinsTheDragsBackgroundBakeInsteadOfRepeatingIt` — `clear()`,
`resetStats()`, build a draft plan at Whites = w (posts the pending bake), then
immediately build a settle plan at the SAME w, then wait for
`hasPendingBake(.finish) == false`. Assert `traffic(.finish).bakes == 1`. Today it
is 2 or 3. A second test,
`testTheProbesSettleRunVisitsTheSameValuesAsItsDraftRun`, asserts the settle
sample set is a subset of the draft's in `DragProbeTests`.

**And fix the probe**, or N-002 cannot be closed by measurement: either sample the
settle at the same 48 values as the draft (measuring the settle-after-a-drag the
row claims to describe), or `PlanTableCache.clear()` before it and label the row
"cold settle". Today it is neither, and it reports the union as if it were one.

## Findings

### I1-01 — A settle blocks on the exact bake the drag already queued, and neither cancels the other
severity: S2
confidence: measured
class: defect
size: M
evidence: `PlanTableCache.swift:171–210` — `table` reads only `entries`; `pending`
(:296) and `inFlight` (:298) are invisible to it, and it never clears `pending[slot]`
after storing at :205, so `drainPending` (:318) rebakes the same key it just stored.
Number: Saturation settle 269.4 ms vs 24.1 ms draft = **245 ms for one 33³ bake**
(`w0/perf-baseline.md`); Whites 388.0 vs 69.0 = **319 ms for two**. In the worst case
one gesture pays that bake three times (settle + drain + the `anyBakePending` re-settle).
how the owner sees it: releasing a Whites or Saturation slider drops a third of a
second of nothing before the picture sharpens into its final version — the settle is
7–11× the drafts that preceded it, and the machine is doing the same 35 937-sample
bake two or three times over on two threads.
fix: `PlanTableCache.swift` — per-key promise as in §4 above; `table` joins or steals
an in-flight/pending bake for its own key instead of racing it. Test:
`testASettleJoinsTheDragsBackgroundBakeInsteadOfRepeatingIt` asserts
`traffic(.finish).bakes == 1` across a draft-then-settle pair on one key; it reads 2–3
with the defect in.

### I1-02 — The settle row of DRAGPROBE cannot hit the cache by construction, so N-002's number does not mean what it says

confidence: measured
class: defect
size: S

### I1-03 — Background bakes are invisible to the cache counters, so the HUD cannot see the cache being defeated
severity: S2
confidence: traced
class: defect
size: S
evidence: `PlanTableCache.swift:308–330` — `drainPending` builds at :318 and inserts at
:323 without touching `stats` or `slotTraffic`. Only `table` (:190–197) and the exact-hit
branch of `pairedTableAllowingStale` (:266–268, :291–292) count. So the Whites draft row
`0h/48b/96s` reports 48 bakes while performing up to 96 more on `bakeQueue` — real CPU,
competing with the render thread, uncounted.
how the owner sees it: the HUD's cache-hit line — added by docs/23 M1b precisely so a
key bug would be visible on a live machine — reads healthy while every draft frame is
queueing a full 33³ rebake behind it. This is the "green lane is not evidence" shape:
the counter that exists to catch the failure is structurally blind to half of it.
fix: `PlanTableCache.swift` — add `deferredBakes` to `Stats`, increment in
`drainPending` under the lock it already takes; surface it on the HUD beside `b`.
Test: `testADeferredBakeIsCounted` — one stale serve, wait for
`hasPendingBake == false`, assert `currentStats.deferredBakes == 1`; reads 0 today.

### I1-04 — The `anyBakePending` settle loop re-renders whole frames while the bake it is waiting for is the one it keeps restarting
severity: S2
confidence: traced
class: defect
size: S
evidence: `Sources/LumenApp/LoupeView.swift:860`
`if image != nil, !usedEmbeddedPreview, !PlanTableCache.anyBakePending { return }` —
then `attempt += 1; try? await Task.sleep(nanoseconds: UInt64(attempt) * 60_000_000)`
and around the loop to another full settle render. That render calls
`PlanTableCache.table`, which (I1-01) neither joins nor cancels the in-flight drain, so
`anyBakePending` is still true when it returns.
how the owner sees it: after releasing a tone slider the app can render the settle
frame twice or three times — each one a full-resolution graph plus its own duplicate
33³ bake — before the picture stops moving.
fix: gate the retry on the bake for THIS key rather than any bake
(`hasPendingBake(slot)` per key, exposed as an `isBaking(key:)`), and land I1-01 first
so the second settle joins instead of rebuilding. Test:
`testTheSettleLoopIssuesOneRenderWhenABakeIsPending` — count `renderPreviewDelivery`
calls behind a stubbed renderer across one settle; 1 expected, ≥2 today.

### I1-05 — `table` does not promote an entry on hit, so an 8-slot cache evicts by insertion order, not by use
severity: S3
confidence: inferred
class: defect
size: S
evidence: `PlanTableCache.swift:178–189` — an exact hit updates `identity` and writes
the array back, but leaves the entry at its index; only `insert(…, at: 0)` (:205, :323)

`testAHitKeepsAnEntryAliveAcrossCapacityChurn` — hit key A, insert eight new keys, ask
for A; expect a hit, get a bake today.

### I1-08 — `finishProofed` is uncacheable on the draft path by design, so every proofed drag frame pays the map
severity: S3
confidence: traced
class: defect
size: S
evidence: `RenderPlan.swift:432–447` — `if allowStaleTables { self.finishLUT = mapProof() }`,
