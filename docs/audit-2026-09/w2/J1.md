### K-052 — `photo_fts` is never rebuilt after `cache.db` is recreated

**At HEAD.** Three separate paths recreate `cache.db` inside `init` — `schemaTooNew`
(`CatalogStore.swift:999`), corruption (`:1013`), and simple absence (first run, or the
user emptying `~/Library/Caches`, which is exactly what `defaultCachePath`'s comment
invites at `:1035-1038`). All three land on `prepareCacheDatabase`, whose FTS step is
`CREATE VIRTUAL TABLE IF NOT EXISTS` (`:906`) followed by `return true` (`:1098`). The
store cannot distinguish "the index exists and is populated" from "I just created it
empty", and `ftsEnabled` is a `let` decided before `main` is even attached. Every text
query then routes to `photo.id IN (SELECT rowid FROM cache.photo_fts …)` (`:2961-2963`)
and returns zero rows, permanently, with the LIKE fallback unreachable.

**Fix (patch sketch).**

1. `prepareCacheDatabase` must report *which* case it was in, not just a Bool:

```swift
enum TextIndexState { case unavailable, ready, empty }   // `empty` == just created
// in prepareCacheDatabase, replace the best-effort block:
do {
    let existed = try cache.scalarInt(
        "SELECT COUNT(*) FROM sqlite_master WHERE type='table' AND name='photo_fts';") == 1
    try cache.execute(CatalogStore.ftsDDL)
    return existed ? .ready : .empty
} catch { return .unavailable }
```

2. `init` stores `ftsEnabled = (state != .unavailable)` and, after `ATTACH` + `migrate()`,
   calls `try rebuildTextIndexIfNeeded(state)`.

3. New method on `CatalogStore`, one statement, one transaction, driven by SQL so it does
   not pay a Swift round trip per photo:

```swift
/// Repopulate `cache.photo_fts` from `main`. The index lives in the disposable
/// database; the rows it indexes do not. Recreating cache.db therefore has to be
/// followed by this, or the text chip silently matches nothing forever.
func rebuildTextIndex() throws {
    guard ftsEnabled else { return }
    try db.transaction {
        try self.db.execute("DELETE FROM cache.photo_fts;")
        try self.db.execute("""
        INSERT INTO cache.photo_fts (rowid, filename, ext, camera, lens, job, keywords)
        SELECT p.id, p.filename, p.ext,
               COALESCE(p.camera,''), COALESCE(p.lens,''), COALESCE(p.job,''),
               COALESCE((SELECT group_concat(k.name, ' ')
                           FROM photo_keyword pk JOIN keyword k ON k.id = pk.keyword_id
                          WHERE pk.photo_id = p.id), '')
          FROM main.photo p;
        """)
        try self.setMetaValue("fts_generation", try self.metaValue("catalog_uuid") ?? "")
    }
}
```

Guard the cost: `rebuildTextIndexIfNeeded` runs it only when the state is `.empty`, or
when `cache.photo_fts` is empty while `main.photo` is not — that second condition also
repairs a catalog already in the broken state, which matters because the shipped builds
have been creating them.

**The test that goes red.** `Tests/LumenCoreTests/CatalogTests.swift`. It must not use
`XCTSkipUnless` for the *existence* of the index (that is the green-lane trap already in
this file at `:492`); skip only when FTS5 is absent, and assert the rebuild separately.

```swift

    let store = try makeStore()
```

Substitution proof: delete the `rebuildTextIndexIfNeeded` call from `init` and the second

### K-053 — a colour label Lumen cannot name is deleted on the first culling keystroke

**At HEAD.** The round trip is lossy in the middle, not at the ends.
`XMPSidecar` reads any string (`:520-521 case "xmp:Label": content.label = value`) and
writes any string (`:389-391`). The loss is the app's five-case enum:
`CatalogService.appLabel(_:)` (`:930-937`) maps anything that is not red/yellow/green/
blue/purple to `.none`, and `saveCullingState` (`:571-587`) then asserts that `.none` back
into the sidecar as `.some(nil)` — "the label was cleared" — because the double-optional
was designed to distinguish *cleared* from *silent*, and this call site never produces
*silent*. `XMPMerge.owns("xmp:Label")` (`:37-40`) strips the element, `fieldLines` does
not re-emit it, and Lightroom's "To Print", any translated colour name and any custom
label are gone from the file. `XMPMerge`'s own header (`:12-14`) promises the opposite.

Same defect on the read side, one step earlier: `stored(_:row:)` (`:495-502`) converts
`state.label` through `appLabel`, so the catalog row's foreign label never reaches
`PhotoItem` and the grid shows no label either.

**Fix (patch sketch).** Carry the unrecognised name through instead of collapsing it.

1. `PhotoItem` gains `var labelName: String?` — the verbatim string from catalog/sidecar.
   `ColorLabel` stays what the swatch row and the `6`–`9` keys drive; `labelName` is what
   the file says.
2. `stored(_:row:)`: `label: appLabel(state.label)` **and** `labelName: state.label`.
3. `saveCullingState`: only speak about the label when this keystroke was about the label.

```swift
// The keystroke that set a flag or a rating has NOTHING to say about the colour
// label. Saying `.some(nil)` here deleted `xmp:Label` from the file — including a
// name this build has no swatch for, which is somebody else's work and the one case
// where "clear it" is certainly wrong.
let labelForSidecar: String??
if label == .none, let existing = photo.labelName, !existing.isEmpty {
    labelForSidecar = nil                       // silent: leave the file's label alone
} else {
    labelForSidecar = .some(label == .none ? nil : label.displayName.lowercased())
}
...
self.enqueueSidecar(for: url, photoID: id, rating: rating,
                    flag: Self.sidecarFlag(flag),
                    label: labelForSidecar, recipe: nil)
```

4. The explicit "clear the label" action (the swatch row / `0`) must still send
   `.some(nil)`; route it through a distinct `setLabel(_:)` call site rather than through
   `saveCullingState`, so "clear" stays reachable and "rated a frame" stays silent.
5. `store.setLabel` keeps taking `LumenCore.ColorLabel?`; add
   `setLabelName(_ raw: String?, photoID:)` so the catalog column can hold the foreign
   name (the column is already `TEXT`, see `photoColumns` `:920`), and have
   `persistRecovered` (`:529-531`) compare raw strings instead of round-tripping through
   `appLabel`, which today rewrites `"to print"` to `nil` in the catalog too.

### K-054 — `xmp:Rating="-1"` (Lightroom's reject) is rewritten as 0

**At HEAD.** `XMPSidecar.swift:510-516`:

```swift
case "xmp:Rating":
    let parsed = Int(value.trimmingCharacters(in: .whitespacesAndNewlines)) ?? 0
    content.rating = Swift.min(Swift.max(parsed, 0), 5)
```

The clamp is right for the *upper* bound (the comment at `:511-515` is correct that 999
stars must not reach the grid) and wrong for the lower one: `-1` is not out-of-range noise,
it is XMP's specified reject marker and the value every Lightroom user's rejects carry.
`fieldLines` (`:385`) then writes `<xmp:Rating>0</xmp:Rating>` over the stripped original,
so a folder culled in Lightroom loses every reject on the first Lumen write to those files.
Lumen's own model has the axis to hold it — `SidecarContent.flag` / `SidecarFlag`, and the
header at `:19-23` explicitly says flag and rating are separate axes — so this is a
translation the file already has a slot for.

**Fix (patch sketch).**

```swift
case "xmp:Rating":
    let parsed = Int(value.trimmingCharacters(in: .whitespacesAndNewlines)) ?? 0
    if parsed < 0 {
        // -1 is XMP's reject marker, which is how Lightroom, Bridge and Camera Raw
        // record a reject. Lumen keeps flag and rating on separate axes, so the
        // marker is TRANSLATED into the flag rather than clamped away — clamping
        // rewrote the file as 0 on the next write and silently un-rejected a cull.
        content.rating = 0
        if content.flag == .none { content.flag = .reject }
        content.ratingWasRejectMarker = true
    } else {
        content.rating = Swift.min(parsed, 5)
    }
```

and, symmetrically, on the write side in `fieldLines`:

```swift
// Give the marker back in the form the tool that wrote it reads. A frame Lumen
// still holds as rejected keeps `-1`; one whose reject was lifted here writes 0,
// which is the correct erasure and the only one.
let ratingOut = (content.flag == .reject && content.ratingWasRejectMarker)
    ? -1 : content.rating
fields += "   <xmp:Rating>\(ratingOut)</xmp:Rating>\n"
```

`ratingWasRejectMarker` is a new `Bool` on `SidecarContent` defaulting to `false`, so
Lumen-authored sidecars keep writing `lumen:flag` and never invent a `-1` (which would
change the meaning of a Lumen reject for readers that treat `-1` as zero stars). Two
knock-ons to include in the patch: `SidecarMerge.fillingIn` (`:252`) and `taking`
(`:275`) both gate on `sidecar.rating > 0`, which is already correct for `0`; and
`CatalogStore.setRating` clamps at `[0,5]` (`:1324` region) — leave it, the reject rides
the flag column.

### K-015 — two RAWs with the same base name share one `NAME.xmp`

**At HEAD.** `CatalogService.swift:1119-1124`:

```swift
static func sidecarURL(for photo: URL) -> URL {
    guard PhotoFormats.isRaw(photo) else {
        return photo.appendingPathExtension("xmp")
    }
    return photo.deletingPathExtension().appendingPathExtension("xmp")
}
```

The RAW branch drops the extension, which is the Adobe convention and correct for a
folder with one RAW per basename. It is wrong the moment a folder holds
`DSC_0001.NEF` **and** `DSC_0001.DNG` — which is the normal state of a folder after an
Adobe DNG Converter run, after a Lightroom "Convert to DNG" that keeps the original, and
after any dual-format card import. Three separate losses follow, and they compound:

1. **Write.** `pendingSidecars` is keyed by the *photo* URL (`:963`), so the two frames
   are two queue entries — but `flushSidecars` (`:1005`) resolves both to one `path`. The
   later flush's `lumen:recipe` overwrites the earlier one's. Each entry seeded itself
   from `readSidecar(for: url)` (`:963`), so the NEF's entry may already have been seeded
   with the DNG's recipe.
2. **Read-back.** On the next open, `merge(row:…)` (`:452-464`) hands both rows the
   *same* `SidecarContent` and the *same* `sidecarMTime`. The file's mtime now differs
   from the NEF's recorded `sidecar_mtime`, so `moved` is true (`XMPSidecar.swift:210-223`),
   `recipeDiffers` is true (the fingerprint is the DNG's), and the decision is
   `.sidecarWins` (`:233`). `persistRecovered` (`:526-528`) then writes the DNG's recipe
   into the NEF's catalog row with `store.saveRecipe(recovered, photoID: row.id,
   isCurrent: true)`. The NEF's edit is now gone from both copies.
3. **Strokes.** `restoreStrokes(from: file, blobs:)` (`:477`) reads the same shared
   payload for both, so a brush painting made on the DNG is silently claimed by the NEF's
   mask references (harmless where content-addressed, misleading where not).

This is the row's stated shape and it is intact.

**Fix (patch sketch).** Disambiguate only where it is needed, and never move a sidecar a
another application already owns.

```swift
/// Where this photo's sidecar lives.
///
/// The Adobe convention for a RAW is `NAME.xmp` — extension dropped — and that is
/// right up to the moment a folder holds two RAWs with one basename, which is the
/// normal state after a DNG conversion that keeps the original. Both frames then
/// address one file, and the second edit destroys the first's recipe; the next scan
/// reads it back as `.sidecarWins` and writes the wrong recipe into the catalog too.
///
/// So: the bare name only while it is unambiguous. When a sibling RAW shares the
/// basename, this photo's sidecar is `NAME.EXT.xmp`, which is the same convention
/// non-RAW files already use here and which exiftool and Capture One both read.
static func sidecarURL(for photo: URL) -> URL {
    guard PhotoFormats.isRaw(photo) else { return photo.appendingPathExtension("xmp") }
    let bare = photo.deletingPathExtension().appendingPathExtension("xmp")
    guard hasRawSibling(sharingBasenameWith: photo) else { return bare }
    let qualified = photo.appendingPathExtension("xmp")
    // An existing bare sidecar belongs to whichever frame already claimed it; a
    // qualified one that exists is unambiguously ours. Never rename or delete the
    // bare file — it is somebody else's document (XMPMerge.swift:12-14).
    if FileManager.default.fileExists(atPath: qualified.path) { return qualified }
    return claimant(forBare: bare) == photo ? bare : qualified
}
```

Two supporting pieces:

- `hasRawSibling(sharingBasenameWith:)` — one `contentsOfDirectory` per directory,
  memoized in a small `[URL: Set<String>]` cache on `CatalogService` invalidated by the
  scan, so this does not stat per keystroke. Comparison on
  `deletingPathExtension().lastPathComponent`, case-insensitively (HFS+/APFS default).
- `claimant(forBare:)` — deterministic tie-break so the *same* frame keeps the bare file
  across launches: the sibling whose extension sorts first, or, better, whichever one the
  bare file's `lumen:catalogUUID` + filename already names. `SidecarContent` already
  carries `catalogUUID` (`XMPSidecar.swift:389` region), so the read is free.
- Migration: on folder open, if a bare `NAME.xmp` exists and two RAWs claim it, log once
  and write the non-claimant's fields to `NAME.EXT.xmp` rather than into the shared file.
  Nothing is deleted.

**The test that goes red.** `Tests/LumenAppTests/` (the function is `static` and pure
apart from one directory listing, so it is testable without a store) — and this is also
the argument for K-102's missing lane:

```swift
                   dir.appendingPathComponent("DSC_0002.xmp"))
}
```
