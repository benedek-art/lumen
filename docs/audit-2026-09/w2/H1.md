### H1-01 — `⌘B` assessment surround and `L` lights-out never reach the field the photograph sits on
severity: S1
confidence: traced
class: defect
size: S

evidence:
`ContentView.swift:213-219` is the only place `state.surroundColor` is painted —
`.background(state.surroundColor)` on the outermost stack. The loupe then covers it,
opaquely, with a constant:

- `LoupeView.swift:1118` — `Lumen.viewerBackground.frame(maxWidth: .infinity, maxHeight: .infinity)`
  as the first layer of the viewer `ZStack`;
- `LoupeView.swift:1236` — `.background(Lumen.viewerBackground)` on the `GeometryReader`;
- `CompareView.swift:101` / `:211` / `:432` — the same constant in both compare surfaces.

`Lumen.viewerBackground` is `static let viewerBackground = surroundCanvas`
(`LumenControls.swift:177`) and `surroundCanvas` is
`Color(nsColor: NSColor(white: 0.165, alpha: 1))` (`LumenControls.swift:77`). It is a
`let`. Nothing in it reads `assessmentMode` or `lightsOut`.

Meanwhile `AppState.toggleAssessmentMode()` (`AppState.swift:1475-1478`) posts the status
message *"Assessment surround on — ISO 12646 mid-grey"*, and `LoupeView.swift:1793-1798`
does draw the ISO 12646 diffuse-white anchor around the plate.

how the owner sees it: he presses `⌘B`, the status bar says the surround is now ISO 12646
mid-grey, the chrome dims to 0.35 — and the field immediately around the photograph, the
only region the standard is about, stays at 0.165. He then gets a 2 px white line drawn
around the picture on that near-black field, which is worse than not entering the mode at
all: the anchor exists to stop the eye adapting to the picture, and on a 0.165 ground it
is a maximum-contrast border instead. `L`'s black surround is the same no-op — `L` takes
the chrome away and leaves the photograph on the same grey it was always on.
`ViewingConditions.surround`'s carefully argued "assessment wins over black"
(`ViewingConditions.swift:92-106`) decides a value nothing in the viewer reads.

I am calling this S1 under the rubric's "silent no-op control": the control announces, in
words, a change to the surround that it does not make where it matters, and the half that
DOES fire makes the viewing condition wrong rather than merely unchanged.

fix: `LoupeView.swift:1118` and `:1236`, and `CompareView.swift:101/211/432`, read
`state.surroundColor` instead of `Lumen.viewerBackground` (`SurveyCell`/`ComparePane` take
it from the environment object they already hold). D46's right-click surround menu then has
exactly one value to write and one place that paints it. THE TEST: `ViewingConditionsTests`
already pins the arithmetic; what is missing is a wiring test, so add to `LumenAppTests` a
`SurroundWiringTests` that asserts `AppState.surroundValue` changes under
`toggleAssessmentMode()` **and** that the viewer's painted value is derived from it — the
cheapest substitution-proof form is a small `ViewerSurround.color(for:)` helper in
`LumenCore` that both `ContentView` and `LoupeView` call, with a test asserting
`ViewerSurround.value(lights:.normal, assessment:true) != Lumen.surroundCanvasValue`;
put `Lumen.viewerBackground` back at either call site and the app test that reads the
loupe's resolved background goes red. (`check-swift-surface.py` can also carry a pass:
`Lumen.viewerBackground` must not appear in `LoupeView.swift`/`CompareView.swift`.)

### H1-02 — the "before" rendition is drawn stretched on every cropped or straightened photograph
severity: S2
confidence: traced
class: defect
size: S

evidence:
`LoupeView.swift:1069` — `private var beforeRecipe: Recipe { Recipe(pipelineVersion: recipe.pipelineVersion) }`.
A default `Recipe` has `develop.geometry.crop == Crop()` and `angle == 0`, so the before
rendition is the **uncropped, unstraightened** frame and comes back at the source aspect.

`LoupeView.swift:1483-1485` computes `ratio` and `drawn` from the EDIT's image `cg` (the
cropped one). `LoupeView.swift:1708-1719` then hands the BEFORE image those same numbers:

```
if viewport.beforeMode == .split, let before = beforeImage {
    BeforeAfterSplit(split: $viewport.splitPosition) {
        plate(before, ratio: ratio, drawn: drawn)
...
} else if state.showBefore, let before = beforeImage {
    plate(before, ratio: ratio, drawn: drawn)
```

and `plate` (`:1764-1780`) is `Image(decorative:).resizable()…​.frame(width: drawn.width, height: drawn.height)`
— `.resizable()` with an explicit frame and no `aspectRatio`, i.e. a non-uniform scale.
`BeforeAfterSplit` (`ViewerOverlays.swift:99-104`) reinforces it: both children get
`.frame(width: geometry.size.width, height: geometry.size.height)`.

how the owner sees it: he crops a frame to 1:1, presses `\`, and the before state is the
whole 3:2 negative squashed into the square — faces narrowed, horizons the wrong length.
The same in `⇧Y` split, where the two halves of one picture disagree about geometry across
the divider. On an uncropped, unstraightened photograph it is invisible, which is why it
has survived. `w1/gap-table.md §H` flags exactly this row for this area
("`before keeps crop/geometry` rule — H1 verify"): the parity question is whether before
should keep the crop; the *distortion* is a defect either way.

fix: `LoupeView.swift:1069` — carry the framing forward into the before recipe
(`beforeRecipe.develop.geometry = recipe.develop.geometry`), which is both the C1 rule the
gap table cites and the thing that makes the two plates the same shape by construction.
Belt and braces at `:1710/:1716`: pass the before plate its OWN `drawnFull` extent rather
than the edit's. THE TEST: `BeforeAfterGeometryTests` in `LumenCoreTests` over a new pure
rule `BeforeAfter.plateSize(beforePixels:afterDrawn:)` asserting that a 6000×4000 before
against a 2000×2000 after drawn extent returns a 2000×1333 box, not 2000×2000; substitute
`drawn` back and it goes red. Plus a one-line `LumenAppTests` assertion that
`beforeRecipe.develop.geometry == recipe.develop.geometry`.

### H1-03 — the loupe's 256-px render bucket can never bind, so a window resize mints a render key (and a decode) per pixel
severity: S2
confidence: traced
class: defect
size: S

evidence:
`LoupeView.swift:2107-2126`:

```
let longEdge = Double(Swift.max(container.width, container.height)) * scale
let bucket = Int((longEdge / 256).rounded(.up)) * 256
let asked = Swift.min(Swift.max(bucket, 640), LoupeView.maxRenderLongEdge)
...
guard let ceiling = DraftResolution.visibleCeiling(drawnDeviceLongEdge) else { return asked }
return Swift.max(Swift.min(asked, ceiling), 64)
```

`visibleCeiling` (`DraftResolution.swift:97-104`) is `Int(drawn.rounded(.up))` — **not
bucketed**. And `drawnDeviceLongEdge` is by construction ≤ the container's long edge in
device pixels (`LoupeView.swift:1107-1113` × `drawnFull`, which fits the frame inside the
container), while `bucket` rounds that same container long edge UP. So
`ceiling ≤ containerLongDevice ≤ bucket` **always**: `min(asked, ceiling) == ceiling`
on every fit frame, and the 256-px bucket at `:2110` is dead arithmetic. The comment two
lines above it — *"quantized to 256-px buckets so a window resize does not spam the render
queue"* — describes a quantization the next statement removes.

`longEdge` is a field of `ViewerRenderKey` (`RenderRequest.swift:59`) and the `.task(id:)`
key at `LoupeView.swift:1182-1185`. A 200 pt window-edge drag on a 2× display walks the
drawn long edge through ~400 distinct integers, i.e. ~400 distinct keys. Each completed
render is also a distinct `AppleRawSource.DecodeKey` (the scale factor follows the ask —
`DraftLadder.swift:348-354`), so each one that lands pays a fresh full RAW decode. This is
verbatim the cost the same function's own comment at `:2118-2122` says the ceiling was
added to remove ("every photograph paid two full RAW demosaics… docs/34 §3") — it removed
the draft/settle mismatch and introduced a continuum.

how the owner sees it: dragging the window edge, the panel splitter, or toggling the
filmstrip re-decodes the RAW repeatedly instead of once; on a 33 MP file from the offload
drive (2.4 s/decode, `DecodeWarming.swift:279-281`) a resize is seconds of stalled picture.
It also means no two window sizes share a decode-cache entry or a developed-preview rung
(see the I3-01 note above).

fix: quantize the ceiling in the same denomination as the ask —
`DraftResolution.visibleCeiling` rounds UP to the next 256 (or takes a `bucket:` parameter),
so that `min(asked, ceiling)` is always a bucket boundary. Rounding UP costs at most 255
invisible pixels and keeps the "never fewer than the panel draws" guarantee; the draft ask
(`draftLongEdge`, same function) inherits it for free, which is what keeps both passes on
one `DecodeKey`. THE TEST: in `DraftResolutionTests`,
`XCTAssertEqual(DraftResolution.visibleCeiling(2100), DraftResolution.visibleCeiling(2103))`
and `XCTAssertEqual(DraftResolution.visibleCeiling(2100)! % 256, 0)`; substitute
`Int(drawn.rounded(.up))` back and both go red.

### H1-04 — every survey cell now drafts at the SETTLE's resolution, under a comment that says 512
severity: S2
confidence: traced
class: defect
size: S

evidence:
`CompareView.swift:495-501`:

```
// Survey panes have no zoom; DraftResolution at fit returns
// the floor, so this stays the cheap 512 draft it was — but
// through the shared rule rather than a bare number.
draftLongEdge: DraftResolution.draftLongEdge(
    settledLongEdge: longEdge, fitLongEdge: 512, zoomRatio: 0),
```

`DraftResolution.draftLongEdge` (`DraftResolution.swift:67-73`) is

```
Swift.max(fitLongEdge, Swift.min(settledLongEdge, visibleCeiling(drawnDeviceLongEdge) ?? settledLongEdge))
```

With `drawnDeviceLongEdge` nil (the survey never passes one) this is
`max(512, min(longEdge, longEdge)) == longEdge` — the settle's own size. The function's own
header says so explicitly at `:50-63`: *"This used to return the bare floor… `fitLongEdge` is
a floor rather than the answer."* The comment in `CompareView` was written against the old
behaviour and was not updated when the rule changed. `requestedLongEdge`
(`CompareView.swift:513-519`) caps at 2048, so a survey cell's draft went from 512 px to up
to 2048 px — 16× the pixels — per cell, per edit event.

how the owner sees it: `N` with a dozen frames selected, then any slider move: twelve
full-size drafts queue on the serial coordinator instead of twelve cheap ones. The survey
grid is precisely where the multiplier is largest, and `CompareView.swift:505-509`'s own
comment ("a survey grid renders many panes, so the settle storm this removes is multiplied")
shows the author already knew the shape of it.

fix: pass the cell's drawn device extent (the `SurveyCell` has `geometry.size` and
`displayScale` in hand at `:429`) so `visibleCeiling` binds — that is both the honest number
and, at a ~200 pt cell, close to the 512 the comment intends. THE TEST: extend
`DraftResolutionTests` with `testAFitAskWithNoDrawnExtentIsNotTheFloor` pinning
`draftLongEdge(settledLongEdge: 2048, fitLongEdge: 512, zoomRatio: 0) == 2048`, so the
stale reading cannot be re-derived from the comment; and a `LumenAppTests` assertion that
the survey passes a non-nil drawn extent.

### H1-07 — `record` re-derives the ladder's answer without the floor the caller used, so the loupe's ladder goes permanently deaf after its first hot frame
severity: S3
confidence: traced
class: defect
size: S

evidence:
The call site sizes the draft WITH a floor (`LoupeView.swift:613-622`):

```
let draftTarget = region != nil ? draftRequested
    : draftLadder.longEdge(requested: draftRequested,
                           notBelow: DraftLadder.sharpnessFloor(drawnDeviceLongEdge: drawnDeviceLongEdge))
```

but reports the result WITHOUT one (`LoupeView.swift:709-720` → `DraftLadder.record`), and
`record` recomputes its own answer floorless at `DraftLadder.swift:514`:

```
let answer = longEdge(requested: requested)
guard renderedLongEdge > 0,
      renderedLongEdge <= answer + Swift.max(2, answer / 100) else { return }
```

Walk it at fit. `requestedLongEdge` returns `ceil(drawnDevice)` (H1-03), `draftLongEdge`
returns the same number, and `sharpnessFloor` is `ceil(drawnDevice / maxUpscale)` with
`maxUpscale == 1` (`DraftLadder.swift:447, 452-456`) — so the floor equals the ask and
`longEdge(requested:notBelow:)` (`:384-391`) returns the ask whatever the rung is. The first
hot frame calls `stepDown(below: answer)` and moves the rung below the ask. From the next
frame on, `answer` is `rungs[rung] < delivered`, the guard at `:517-518` rejects, and
`record` returns before it can hear heat OR cheapness — for the life of that
`PhotoRenderModel`. `record`'s climb condition `answer == Self.rungs[rung]` (`:588`) is
independently unreachable at fit, since the ask is a viewport size and never a rung.

Worth stating plainly alongside it: **`DraftLadder` has no authority anywhere in the shipping
loupe.** At fit `sharpnessFloor >= ask` by the arithmetic above, so the rung cannot change
the answer; zoomed, `LoupeView.swift:613` bypasses the ladder entirely for a region render.
The only paths where the ladder still chooses a size are the very first draft of a photograph
(no image yet, so `drawnDevice` is nil — and `isRepresentative` discards that frame anyway,
`DraftLadder.swift:369-373`), a viewport whose drawn photograph is under 1024 device pixels,
and the compare/survey/before models, which never pass a floor. That is a deliberate trade
argued at `DraftLadder.swift:412-446` ("sharp and stepping is the failure mode he asked
for"); what is not deliberate is that the mechanism can no longer even OBSERVE, so nothing
in the loupe now enforces `budgetMilliseconds = 35` — against `w0/perf-baseline.md`'s
measured 56–60 ms p50 at 1280, 47/47 events over budget.

Every `record` test in `DraftLadderTests` passes `requested: 4096` and
`renderedLongEdge: ladder.longEdge(requested: 4096)` — the floorless answer — so no test
exercises the combination the app actually ships. `testTheLadderMayNotDescendBelowWhatIsOnScreen`
(`:1029`) drives `record` floorless and only then applies the floor to a `longEdge` query.

how the owner sees it: nothing, today, because the floor pins the render size anyway. It
matters the moment anyone changes `maxUpscale`, adds a rung, or gives the ladder a lever
back: the instrument will be silently dead and its 1093-line test file will still be green.

fix: `DraftLadder.record` should take the answer it is reporting on rather than re-deriving
it — `record(draftMilliseconds:renderMilliseconds:renderedLongEdge:answerLongEdge:allowStepUp:)`
— with `LoupeView.swift:709` passing `draftTarget`. The guard and the climb test then both
run against the size that was actually rendered. THE TEST: in `DraftLadderTests`,

```
var ladder = DraftLadder()
let ask = 2360, floor = DraftLadder.sharpnessFloor(drawnDeviceLongEdge: 2360)
let a1 = ladder.longEdge(requested: ask, notBelow: floor)          // 2360
ladder.record(draftMilliseconds: 60, renderedLongEdge: a1, requested: ask)
let a2 = ladder.longEdge(requested: ask, notBelow: floor)          // 2360 again
ladder.record(draftMilliseconds: 60, renderedLongEdge: a2, requested: ask)
XCTAssertGreaterThan(ladder.rung, /* the rung after ONE hot frame */ 3)
```

red today (the rung stops at 3 because the second frame is rejected), green once `record`
is told the floored answer.
