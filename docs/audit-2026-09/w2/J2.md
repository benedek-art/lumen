the tree decides which. If the window's view hierarchy answers `performKeyEquivalent:`

### J2-02 — one cull keystroke over a multi-selection copies the whole roll once per photo and publishes once per photo; undo does it three times
severity: S2
confidence: traced (arithmetic over the shapes below, not a device measurement)
class: defect
size: S

evidence: `AppState.swift:2842–2857`, the loop inside `mutateTargets`:

```swift
for i in allPhotos.indices where targets.contains(allPhotos[i].id) {
    let was = Self.culling(of: allPhotos[i])
    body(&allPhotos[i])                       // ← :2844
    let now = Self.culling(of: allPhotos[i])
    …
```

`allPhotos` is `@Published private(set) var allPhotos: [PhotoItem]` with a `didSet`
(`:513–515`). A `@Published` property is reached through Combine's enclosing-instance
subscript, which offers **get and set only** — there is no `_modify` — so
`body(&allPhotos[i])` is materialised as *read the whole array, mutate the temporary,
write the whole array back*. The temporary shares the stored buffer, so the element
write forces a full copy-on-write of the entire roll, and the write-back sends
`objectWillChange`. Per target photo: **one O(allPhotos.count) array copy and one
publish.**

This file already states the rule and follows it forty lines away, in
`adoptCaptureISO` — `AppState.swift:1934–1935`: *"One assignment rather than one per
row: `allPhotos` is `@Published` and a per-element write republishes the whole grid."*
`mutateTargets` is the one path that does the opposite, and it is the app's
highest-frequency action.

Undo is worse. `restore` (`:2871–2881`) is called once per photo from `apply`
(`:3469–3483`) and does an O(n) `firstIndex(where:)` plus **three** separate element
writes (`:2874–2876`) — three more whole-array copies each.

Arithmetic, at the sizes this app is for: `x` over a 200-frame selection in a
20,000-frame folder = 200 × 20,000 = **4 million `PhotoItem` copies with 4 million URL
retains, plus 200 whole-window invalidations**, before the SQL refresh at :2864 even
starts. ⌘Z on the same step = 200 × (≈10,000 predicate calls + 3 × 20,000 copies) =
**12 million element copies**. At 50,000 frames it is 2.5× that.

how the owner sees it: rejecting a run of frames selected with ⇧-click, or undoing one,
locks the window for a visible beat — and the beat grows with the size of the folder,
not with the size of the selection, which is the opposite of what the gesture feels like
it should cost. It is also the same main-actor budget `J1-05` is spending on the SQL
side, so the two compound on the same keystroke.

fix: `AppState.swift:2837–2868` — build the roll once, assign once, exactly as
`adoptCaptureISO` does:

```swift
var updated = allPhotos
for i in updated.indices where targets.contains(updated[i].id) { … body(&updated[i]) … }
if changed { allPhotos = updated }        // one copy, one publish
```

and in `restore`, take the three field writes into one `var item` before assigning back;
better, give `apply` a batched sibling that restores every URL in the step in one
assignment. Hoist the roll arithmetic into a pure static —
`static func applyCulling(to roll: [PhotoItem], targets: Set<URL>, _ body:) ->
(roll: [PhotoItem], before: […], after: […])` — the same seam `CullCounts.counting`
already uses (`:1782`) so `LumenAppTests` can reach it without `AppState.init`, which
opens the real catalog.

**Test (red today):** `Tests/LumenAppTests/CullBroadcastTests.swift`, in the genre of
`DragBroadcastTests` ("These tests count publishes… they fail the moment somebody puts a
per-event write back on the shared object"): seed 50,000 `PhotoItem`s, apply a 500-target
cull through the new static, and assert (a) the helper returns one roll value and (b) a
wall-clock budget — with the per-element loop substituted back through an
`inout`-through-a-getter stand-in, the 500 × 50,000 copies blow it by two orders of
magnitude. Pair it with a `objectWillChange` sink asserting exactly one publish once a
test seam for `AppState` exists (`AppState.swift:1698` is the only initializer today, and
it opens Application Support — that seam is part of this fix, and of K-102's coverage).

### J2-03 — the filter's "live counts" describe three different corpora and none of them is the grid
severity: S2
confidence: traced
class: defect + parity-gap
size: M

evidence: the popover puts a number under every flag chip, every star and every label
swatch (`FilterBar.swift:174–243`), a number beside every camera, lens and keyword
(:320–367), and they are computed from three different populations:

1. **flag / rating / label** — `FilterBar.swift:606–617` → `state.cullCounts` →
   `AppState.swift:1800–1805`: `CullCounts.counting(allPhotos)`. `allPhotos` is the
   **whole open folder**, unfiltered. It ignores `selectedCollectionID` entirely — an
   album is applied only as `query.albumID` in the SQL (`AppState.swift:390`,
   `:1893–1895`), never to the roll — and it ignores every other lit criterion.
2. **camera / lens** — `CatalogService.swift:778–783`, `facetCounts(facet,
   folderID:)`: **folder-scoped**, still album-blind and criterion-blind.
3. **keywords** — `CatalogService.swift:870–872` → `CatalogStore.allKeywords()`
   (`:2394–2400`): `SELECT k.name, COUNT(pk.photo_id) … GROUP BY k.id` with **no scope
   at all** — every photo in the catalog, from every folder ever opened.

The doc comment at `CatalogStore.swift:2392–2393` says the keyword list and "the keyword
chip's live counts read the same rows", which is true and is the problem: both are
catalog-wide. `LibraryFacet`'s own doc (`AppState.swift:481–484`) promises the opposite —
*"computed by the same indexes the chip's predicate uses, so the number and the result
agree."*

how the owner sees it: with an album selected in the sidebar he reads "★4 · 37" in the
popover, clicks it, and gets six frames. On a freshly opened folder of ninety pictures
a keyword reads 1,203 — the whole catalog — and filtering on it returns two. C1's
per-value live counts are the single feature `w1/r2-captureone.md §J` calls "the most
useful thing in its Filters tool"; Lumen has the shape and not the arithmetic.

fix: `CatalogStore` already has the machinery — `countPhotos(matching:)` and the
indexed builder. Add one `facetCounts(for query: PhotoQuery)` entry point that counts
each candidate value against the **current** query with that one criterion removed
(the standard "count as if I clicked this" semantics), scope `allKeywords` by folder
and album the way `facetCounts` is scoped, and have `AppState` publish one
`FilterCounts` value refreshed on the same generation stamp `refreshLibraryQuery` uses
(`:1885–1887`) so a stale answer is dropped rather than shown. Keep `cullCounts` as the
memory-mode fallback only, and make it count `photos` rather than `allPhotos` there.
**Test (red today):** `Tests/LumenCoreTests/CatalogTests.swift` — seed two folders and
one album, put keyword "portrait" on 3 photos in folder A and 40 in folder B, add
folder A's three to an album, then assert the keyword count reported for
`PhotoQuery(albumID: album)` is 3. Today `allKeywords()` returns 43 and there is no
call that can return 3. `CullCountsTests` cannot catch this by construction: it pins
`CullCounts.counting(roll)` against the roll it is handed
(`Tests/LumenAppTests/CullCountsTests.swift:20–46`) and never asks which roll the bar
passes.

### J2-04 — a stack is invisible in the contact sheet: no count badge, no expand, and the only place that explains it ships collapsed

confidence: traced
class: parity-gap
size: M

evidence: the cell draws three badges and no fourth — `GridView.swift:326–345`

**Test (red today):** `Tests/LumenCoreTests/CatalogTests.swift` — create a 3-frame stack,

### J2-06 — one cursor move rebuilds the whole id list twice and scans it four times on the main actor, and nothing measures it (K-066's mechanism)
severity: S3
confidence: traced (call counts, not a device measurement)
class: defect
size: M

evidence: per arrow press, with `N = photos.count`:

| site | cost |
|---|---|
| `AppState.moveSelection` `list.firstIndex(of:)` (`:2731`) | O(N) URL `==` |
| `AppState.moveSelection` `selected.firstIndex(of:)` (`:2733`) | O(sel) |
| `GridView` `.onChange` → `photos.map(\.id)` (`GridView.swift:106`) | allocates an N-element `[URL]`, N retains |
| `ThumbnailLoader.prefetch` `urls.firstIndex(of: anchor)` (`ThumbnailLoader.swift:282`) | O(N) |
| `FilmstripView` `.onChange` → `photos.map(\.id)` (`FilmstripView.swift:130`) | a **second** N-element `[URL]` |
| `ThumbnailLoader.prefetch` again | a second O(N) |

and on a cull key, two more: `cursorIndex` (`AppState.swift:2905–2908`) before the
mutation and `advanceIfNeeded`'s `list.firstIndex(of:)` (`:2896`) after it. `PhotoItem.==`
is `a.id == b.id` (`AppState.swift:83`), so every one of those comparisons is a Foundation
`URL` equality. At 50,000 frames that is **100,000 URL allocations and ~150,000 URL
comparisons per keystroke**, on the main actor, before a single decode is requested — and
the filmstrip is on screen in grid mode too (`FilmstripView.swift:69–71` picks
`surface: .grid` there), so both halves really do run. Against docs/10 §10.2's 8.3 ms
frame budget this is the same class of bookkeeping the `photoCache` memo was introduced
to kill (`AppState.swift:1727–1735`), left standing one layer up.

Nothing in the repo measures it: `SpeedBenchTests` skips itself unless `LUMEN_BENCH` is
set (:24) and benches `RenderPlan` only; `BrowsePrefetchTests` asserts ladder and ring
*arithmetic* with no timing.

how the owner sees it: holding ← or → through a long take, or holding `x` with
auto-advance on, gets choppier as the folder gets bigger — the exact scaling K-066 was
filed to characterise and never did.

fix: keep the id list beside the roll. `AppState` already memoises `photos` and
`catalogIDCache` on the same invalidation (`:1758–1763`); add `photoIDs: [URL]` and
`photoIndex: [URL: Int]` to that memo, hand `prefetch` the index instead of the array
(`prefetch(around:in:index:size:surface:)`), and replace all four `firstIndex(of:)` with
a dictionary lookup. That takes the per-keystroke cost from O(N) to O(1) and deletes both
`map(\.id)` allocations. **Test (red today):** extend `SpeedBenchTests` with a
non-skipping case — seed 50,000 URLs, call the cursor-move path 200 times and assert a
budget; and a substitution-proof structural test in `BrowsePrefetchTests` that
`PrefetchRing`'s caller is handed an index, not a list, so restoring the linear scan
fails to compile. Fold the result into K-066, which asks for a number and has never had
one.

## 3. What I read and found correct

Recorded so nobody re-audits it.

- **`ArrowNavigation` is right, and its tests are real.** The comparing/browsing split
  (`ArrowNavigation.swift:62–75`) preserves a survey's membership, falls back to the roll
  below two selected frames, lands a stray cursor back inside the set, and clamps rather
  than wraps. `ArrowNavigationTests` covers all sixteen branches including zero delta,
  empty roll, cursor-outside-the-set and both ends — **no `XCTSkip` anywhere in the
  file**, and every index it returns is asserted addressable (:212).
  `ComparePanes.pairWindow` slides with the cursor and is tested against the
  two-frame case staying unchanged.
