### E2-03 — `estimatePSFSigma` returns the 2.0 px ceiling on every real frame, and is √2 too large by construction even on the geometry its own comment assumes
severity: S2
confidence: measured
class: defect
size: M
evidence: `Sources/LumenCore/Image/SpatialOps.swift:526-530` derives the model —
*"A Gaussian PSF of width σ maps a point source to `exp(−d²/2σ²)`, so the ratio between a
local peak and its neighbour **one pixel away** is at most `exp(1/2σ²)`"* — and then
inverts it two lines later as `σ = sqrt(1 / ln(maxRatio))` (`:609`). The inverse of
`exp(1/2σ²)` is `sqrt(1/(2·ln r))`. RT's constant is right for RT because
`capturesharpening.cc` measures **CFA green** neighbours at `d = √2`, where `exp(d²/2σ²) =
exp(1/σ²)`; this function measures the **demosaiced luminance plane** at `d = 1`
(`DetailEngine.swift:502,506`). Measured, running the port on impulses blurred by a known σ:

| true σ | reported σ | ratio |
|---|---|---|
| 0.50 | 0.737 | 1.47 |
| 0.80 | 1.199 | 1.50 |
| 1.00 | 1.488 | 1.49 |

That is the smaller half. On any frame that is a photograph rather than a star field the
99.5th-percentile statistic collapses: measured on 1/f fractal noise, a 1 px checkerboard
and a 3 px checkerboard, each blurred at σ 0.5/0.8/1.2, the function returned **2.000 px —
`maxPSFSigma`, the clamp — in 8 of 9 cases**. The mechanism, instrumented: on the fractal
frame **5014 of 5051** ln-ratio samples land in bin 0 of the 256-bin histogram (bin width
0.0244 over a 0–6.25 range), and even the true maximum ratio inverts to σ = 4.94 px. A
smooth local extremum's peak/neighbour ratio is `1 + curvature/2`, not `exp(1/2σ²)`; the
formula only holds for an isolated point source at full contrast.
how the owner sees it: today, nothing — the function has no shipping caller. He sees it the
moment K-075/K-088 are closed by *wiring* rather than *removing*: docs/06 sells a σ readout
("σ 0.58 on the 35/1.8") as the trust device that distinguishes Lumen from LrC's constant
40, and this estimator would print 2.00 px on every frame — a constant, arrived at
expensively. Measured cost of running 8 RL iterations at that σ on a σ-0.8 edge: bright
overshoot 34.1% against 10.0% at the true σ, a **+19.0 sRGB code value** white rim against
+5.9.
fix: (a) `σ = sqrt(0.5 / lnRatio)` for the 1 px luminance geometry, and set `maxLn` to
`0.5/minPSFSigma²` so the histogram still spans the representable σ range; (b) replace the
percentile-of-all-peaks with RT's guarded maximum over *unclipped, high-contrast* peaks —
require the peak to clear its neighbour by a floor, and take a high quantile of that
subset, not of every local bump; (c) return `nil` rather than a clamp when too few peaks
qualify, so the caller can fall back to a stated default instead of the ceiling.
**The test that goes red today:** a `LumenCoreTests` case that blurs `ProofFrames.fineTexture`
(or a synthetic impulse field) by an exact Gaussian of σ ∈ {0.5, 0.8, 1.2} and asserts
`estimatePSFSigma` returns it within 20%. Today it returns 1.47–1.50× on impulses and the
2.0 clamp on texture. This function currently has zero test coverage of any kind.

## Checked, and found correct — so nobody re-checks it

- **Output sharpening runs in the right place.** `PipelineRenderer.exportedImage:708-709`
  applies it after geometry+resize (`:645-656`) and after `RenderGraph.build`'s S14/S15
  picture formation (`RenderGraph.swift:180-197`), i.e. on final, display-referred pixels —
  which is what docs/11 and Fraser require, and what `baseRadius(printPPI:)`'s "output
  pixels" denomination assumes. The `appliedRadius` clamp is shared with the export
  sheet's readout (`ExportRecipe.swift:179-191`, `ExportSheet.swift:633-648`), so the
  printed number is the applied number. The `lightHaloRatio` claim was already removed
  from `energy()` and its removal documented (`ExportRecipe.swift:196-215`) — accurate.
- **`richardsonLucy` itself is sound.** The iteration is
  `est ← est · (PSF ⊛ (obs / (PSF ⊛ est)))` with a symmetric Gaussian PSF, non-negativity
  floor, a division floor and an 8× ratio clamp (`SpatialOps.swift:492-514`). Re-derived in
  Python and run against a Gaussian-blurred edge, it recovers the edge and its overshoot at
  the *correct* σ is 10.0% — in the same territory as the 10.9% RT figure quoted in
  docs/26 §6. The defect is the σ it is handed (E2-03), not the deconvolution.
- **S12's halo damp and edge gate are at parity between the two paths.**
  `DetailEngine.swift:586-602` and `Kernels.swift:192-212` compute the same
  `v·(1 − halo·smoothstep(0.15,0.60,usm))` on the positive side only and the same
  `mix(1, smoothstep(0.02+0.10m, 0.10+0.25m, gradient), m)` gate, with the encoded-plane
  `range` conversion applied in the kernel and the tensor scaled at source. The remaining
  divergence is the fine band (E2-06) and the tensor's radius floor of 2, which
  `RenderGraph.swift:1175-1180` declares.
- **Halo suppression missing the rim is already pinned, with the failing test pre-written.**
  `FieldBaselineProbeTests.testHaloSuppressionCurrentlyMissesTheRimItExistsToDamp:246-288`
