Area: the cold-open path and its cost, the memory ceiling on a 45 MP frame, the six
caches between a file on disk and a frame on screen, the embedded-preview path, decode

## 0. The six caches, keyed and bounded

Stated once, because the brief asks it of every cache and three of the findings below
are about a row in this table.

| cache | keys on | bound | can it serve stale? | test |
|---|---|---|---|---|
| `AppleRawSource.decodeCache` (:168) | `(draft, scaleFactor, captureStrength, lumaNR, chromaNR, lensProfile, decoderVersion)`, per source | 8 interactive entries (:140) **and** 320 MB (:516), plus ONE inspection entry exempt from both (:443–448) | No. Every field the filter reads before `outputImage` is in the key, and `decode` sets all of them on the miss path (:280–336). | none — `DecodeResidencyTests` tests the two ceiling *rules* in `DraftLadder`, never the cache |
| `RenderCoordinator.sources` (:73) | `URL` | 12, LRU by `sourceOrder` (:78–79, :684–687) | Only across a file rewrite; `invalidate(url:)` (:542) is the door. | none |
| `ThumbnailLoader.cache` (:132) | `(url, pixels)` — **no fingerprint** (:101–104) | 512 MB LRU, evicts to 90 % (:484–493) | Yes, by design at thumb/grid (docs/10 §10.1) — and by accident at `fit`, see I3-05 | none |
| `PreviewStore` disk rows | `(photo_id, level, recipe_fp)` after `cacheMigration2` | `PreviewCache.budgetBytes` 10–100 GB, capped at free space (:293–298) | No: `decide` refuses `.stale` (:139) | `PreviewCacheTests` (rules only) |
| `PreviewStore` pending-encode queue | — | 128 MB (`admitsWrite`, :269–273) | n/a | `PreviewCacheTests` |
| process-wide decode residency | sum of `heldDecodeBytes` over `sourceOrder` | nominally 768 MB (`RenderCoordinator.swift:105`) — **actually ~1.79 GB, see I3-02** | n/a | none (LumenApp, K-102) |

Two things I went looking for and did **not** find, said plainly so nobody re-looks:

- **No integer overflow in size arithmetic.** `DraftLadder.mayHoldAsPixels`
  (`DraftLadder.swift:164–178`) uses `multipliedReportingOverflow` on both the area and
  the byte product, and `DecodeResidencyTests.testLargeProductsDoNotOverflow:141` pins
  `Int.max × Int.max`. This is the one place in the area where a corrupt header's
  dimensions are multiplied, and it is correct.
- **No partially-mutated cache on a decode failure.** `AppleRawSource.decode` returns
  nil at :346 before it touches `decodeCache`; the two writes (:394–397) happen only
  after `stored` exists. `DecodeMaterializer.materialize` returns nil on every guard
  (:110–137) and the caller falls back to the lazy image (:392), which is a correct
  decode. Nothing half-writes.

## 1. Known-open dispositions

- **K-036** — **CHANGED. The 3.8 GB figure is closed; the replacement budget is
  advertised at 768 MB and its enforceable floor is ~1.79 GB.**
  `RenderCoordinator.trimDecodeResidency` exists (:129–158) and runs on the one line
  every consumer passes through (`source(for:)` :676, :688), which is the mechanism the
  row wanted. But the trim spares `sourceOrder.last` in pass one (:139 `dropLast()`) and
  `sourceOrder.suffix(4)` in pass two (:152, :168), and `AppleRawSource.evictDecodes`
  lets one source keep 320 MB of interactive entries (:516) *plus* one budget-exempt
  inspection plane of up to `DraftLadder.materializedDecodeByteCeiling` = 512 MB
  (`DraftLadder.swift:159`). Multiply: 832 + 3 × 320 = **1792 MB the trim cannot reach**.
  On the owner's 7008 × 4672 ARW the inspection plane is 262 MB, so the realistic floor
  is 582 + 3 × 320 = **1542 MB**. See I3-02.
- **K-068** — **STILL-OPEN, and the shipped instrument cannot close it.** Decode wall
  time is measured (`PipelineRenderer.swift:381–387`), carried on
  `RenderResult.decodeMilliseconds` (`RenderCoordinator.swift:45`) and delivered to the
  HUD on both passes (`LoupeView.swift:742`, `:844`) — so the *cold* number is on
  screen. There is no warm counterpart anywhere: `LatencyHUD.noteDecode` discards every
  value at or below 1 ms (`LatencyHUD.swift:212–217`), which is exactly the cache-hit
  case, so the line keeps printing the last cold open however many warm ones followed.
  See I3-06.

**Cross-cutting rows.** K-014, K-058, K-073: not touched, no disposition.
**K-102 — STILL-OPEN and it bites here specifically.** Every bound that stands between
this app and a machine that swaps — `trimDecodeResidency`, the source-cache limit, the
512 MB thumbnail LRU, the 128 MB encode queue's caller — is in `LumenApp`, which no CI
lane runs. The rules that *were* moved into LumenCore (`DraftLadder`, `PreviewCache`,
`ThumbnailLadder`, `DecodeWarming`) are all tested and all correct. The arithmetic that
combines them is not tested and is where I3-02 lives.

## 2. Findings

### I3-01 — a settled frame is filed at the `fit` rung whatever size it is, so the disk cache can serve a preview softer than the rung it is stored under
severity: S2
confidence: traced
class: defect
size: S
evidence: `Sources/LumenApp/ThumbnailLoader.swift:187–195` —
```swift
func recordDeveloped(url: URL, image: CGImage) {
    guard let previews else { return }
    guard let pixels = ThumbnailLadder.pixels(for: .fit) else { return }
    ...  previews.record(plan, image: image, source: .lumen)
```
`pixels` is the constant 2560 (`ThumbnailLadder.swift:63`); `image` is whatever the
viewer settled at. That size is `requestedLongEdge` (`LoupeView.swift:2107–2126`):
`min(max(container·displayScale rounded up to 256, 640), 4096)`, then narrowed again by
`DraftResolution.visibleCeiling(drawnDeviceLongEdge)` — "AND NOT ONE PIXEL MORE THAN THE
PANEL DRAWS" (:2112). A portrait frame in a landscape pane, or a windowed loupe on a
1× display, settles at 640–1600 px. `PreviewStore.persist:220–223` then calls
`PreviewCache.rowForDecode(pixels: plan.pixels)` — the **ask**, 2560 — and files a `fit`
row with `source: .lumen`, i.e. under the photograph's current fingerprint
(`PreviewCache.swift:175–178`).
On the next launch `PreviewCache.decide` (:131–149) scores that row `.current`, rank 0,
against the camera's embedded `fit` row at rank 1 — so the `.lumen` row **wins the tie**
(:143) — and `PreviewStore.decodePayload` (:175–186) never upscales, so the loupe's
instant path (`ThumbnailLadder.loupeInstantPixels` 1600 → bucket 2560) receives, say,
900 px where it asked for 2560.
`PreviewCache.swift:110–114` states the rule this breaks — *"Serving a 256 payload to a
1024 request produces a contact sheet that is four times softer than the code believes
it is, and nothing downstream can tell"* — and `:184–191` explains why an **embedded**
payload smaller than its rung is not that lie: *"the payload is by construction exactly
what decoding the ORIGINAL at that request size would have produced"*. That construction
is true of an ImageIO extraction and false of a viewer frame, and `recordDeveloped` is
the writer that broke it.
how the owner sees it: a photograph he has edited comes back *blurrier* on the first
frame than one he has not — the camera's own preview used to appear there and has been
displaced by a smaller picture of his own edit. The smaller the window he edited in, the
softer it is, and it stays that way until he edits the photo again in a bigger one.
fix: `PreviewCache.swift` — `rowForDecode` gains the payload's real long edge and files
at `ThumbnailLadder.level(for:)` of the largest rung the pixels can fill, returning nil
below `thumb`; `PreviewStore.persist` passes `max(image.width, image.height)`;
`ThumbnailLoader.recordDeveloped` stops naming a rung and lets the rule pick one. Test
(LumenCore, no GPU, no Mac):
`testALumenRowIsNeverFiledAtARungItsPixelsCannotFill` — `rowForDecode(pixels: 2560,
payloadLongEdge: 900, source: .lumen)` must return the `grid` row or nil, never a `fit`
row. Today the parameter does not exist and the function returns `.fit`.

### I3-02 — the process-wide decode budget is 768 MB in a comment and ~1.79 GB in the code; in two ordinary cases the trim can free nothing at all
severity: S2
confidence: measured
class: defect
size: M
evidence: `Sources/LumenApp/RenderCoordinator.swift:105`
`private static let decodeResidencyBudget = 768 * 1024 * 1024`, and the trim below it:
```swift
let cold: [URL] = Array(sourceOrder.dropLast())            // :139  pass 1 spares the newest
...
let alternating: [URL] = Array(sourceOrder.suffix(Self.residencyLiveSources))  // :152, :168 = 4
for url in cold where !alternating.contains(url) { ... releaseDecodes() }      // :153
```
What is *not* releasable therefore weighs: the newest source's interactive working set
(`AppleRawSource.swift:516`, 320 MB) **plus** its budget-exempt inspection plane, which
`evictDecodes` never counts against the byte budget (:443–458) and which
`DraftLadder.materializedDecodeByteCeiling` (`DraftLadder.swift:159`) caps at 512 MB,
**plus** three more spared sources at 320 MB each. **832 + 960 = 1792 MB — 2.33× the
number the file names.** With the owner's 33 MP ARW (7008 × 4672 × 8 = 262 MB) it is
582 + 960 = 1542 MB.
And in two everyday cases the trim runs and frees zero:
· **two-up compare** — `sourceOrder` = 2, so `cold` = 1 and `alternating` = both;
pass 1 drops the older pane's inspection plane, pass 2's `where` clause is empty. Floor
= 582 + 320 = **902 MB, over budget, nothing left to take**.
· **one loupe on a 60 MP body** — 9504 × 6336 × 8 = 481 MB inspection plane + 320 MB
interactive = **801 MB in a single source**, which is `sourceOrder.last` and therefore
excluded from `cold` (:139) before either pass begins. `trimDecodeResidency` iterates an
empty list and returns.
Also: nothing has bounded the total *after* an allocation — the trim is called from
`source(for:)` (:676, :688), i.e. before the decode that grows the cache, never after.
how the owner sees it: nothing that reads as a render bug. The machine starts paging
under a wired IOSurface working set several times the size of the 512 MB thumbnail
cache, so *everything* gets slower at once and stalls appear that no single render could
explain — the attribution problem the comment at :96–99 says the budget exists to avoid,
committed by the budget itself.
fix: `RenderCoordinator.swift` — make the two passes exhaustive rather than
advisory: after the `alternating` pass, if `total` is still over, release inspection
decodes from the newest source too (it is recomputable and the trim's own doc-comment at
:118–123 argues exactly that), and re-check after the decode rather than only before it.
Then move the whole rule into LumenCore so it can be tested: a pure
`DecodeResidency.plan(holdings: [(bytes: Int, inspection: Int)], budget: Int) -> [Int]`
returning which sources to trim. Test:
`testTheResidencyPlanGetsUnderBudgetWithFourLiveSources` — four sources each holding
320 MB interactive + 262 MB inspection against a 768 MB budget; assert the residual is
≤ 768 MB. Today's rule leaves 1542 MB.

### I3-03 — `Int(_:)` on a file-derived Double is guarded at one of the five sites that read the same number, and the guard's own comment says why the other four are wrong
severity: S2
confidence: traced
class: defect
size: S
evidence: `Sources/LumenPipeline/AppleRawSource.swift:236–243` states the rule and
implements it once:
```swift
// Guarded rather than converted, because `Int(_:)` on a non-finite `Double`
// TRAPS — the same trap `PipelineRenderer.byte` guards for the same reason a few
// files away. `nativeLongEdge` comes from `CIRAWFilter.nativeSize`, and a source
// that cannot say how big it is answers zero here...
let asked = clampedScale * nativeLongEdge
let askedLongEdge = asked.isFinite && asked > 0 && asked < 1e9 ? Int(asked.rounded()) : 0
```
The same `filter.nativeSize` reaches four unguarded conversions:
`AppleRawSource.swift:99–100` `return (Int(size.width), Int(size.height))` — and note it
**truncates** where every other site rounds; `RenderCoordinator.swift:350`
`nativeLongEdge: Int(source.nativeLongEdge.rounded())`; `RenderCoordinator.swift:377`
`maxLongEdge: Int(source.nativeLongEdge)` on the export/full-size path; and the sibling
conformer `ImageSource.swift:104–105` `Int(image.extent.width.rounded())`, whose extent
comes from `CIImage(contentsOf:)` on any JPEG/HEIC/TIFF the user drops in. The
precedent the comment cites is real — `PipelineRenderer.swift:2048–2051`
`guard v.isFinite else { return 0 }` — so the codebase has already decided that a
number read out of a file is not to be trusted into an `Int`; it has just applied the
decision in one place out of five.
Zero, which the comment says is a reachable answer, is also unguarded downstream at
`RenderCoordinator.swift:377`: `renderFullSize` asks the exporter for `maxLongEdge: 0`.
how the owner sees it: the app quits without warning while opening a file — no crash
report the photographer can act on, no bad frame, just gone — on the one class of input
that is not under the app's control. If instead the dimension is merely zero, an export
is requested at a zero long edge.
fix: one `ImageSource` extension — `var nativeLongEdgeInt: Int` and
`var safePixelSize: (Int, Int)`, both applying the `:242` guard — and route all four
sites through it; add `guard native > 0` to `renderFullSize`. Test (LumenCore, no Mac):
move the guard itself into `DraftLadder.pixelCount(from:)` and assert
`pixelCount(from: .nan) == 0`, `pixelCount(from: .infinity) == 0`,
`pixelCount(from: 7008.6) == 7009`. Written against today's `Int(_:)` the first two
assertions do not fail, they crash the test process — which is the point.

### I3-04 — nothing calls `invalidatePreviews`, so a `.stale` payload is never unlinked and `prune()` runs only at quit
severity: S3
confidence: measured
class: defect
size: S
evidence: `grep -rn invalidatePreviews Sources/` returns the definition
(`CatalogStore.swift:2561`, and the unavailable stub at `:3685`) and **three comments
that assume it runs** — `PreviewCache.swift:52`, `:67`, `:71`, and
`ThumbnailLoader.swift:170` *"it is the one rung an edit makes STALE rather than merely
browsable, and `invalidatePreviews` already deletes it"*. There is no call site.
`PreviewCache.Freshness.stale` (`PreviewCache.swift:62–63`) says *"Never served, and its
payload should be unlinked"*; the first half is enforced (`decide` :139), the second is
not by anything. Because `cacheMigration2` made the primary key
`(photo_id, level, recipe_fp)` (`CatalogStore.swift`, `preview_v2`) and
`payloadPath` hashes `recipeFP` into the filename (`PreviewCache.swift:236–239`), every
new fingerprint is a **new row and a new file**, and the old one is orphaned rather than
overwritten. With I3-01's writer live, one settle per gesture means one 2560-rung HEIC
payload per gesture per photograph. The only reclaim is `PreviewStore.prune()`
(:283–294), whose one caller is the quit path (`AppState.swift:3451`), against a floor
budget of 10 GB (`PreviewCache.swift:277`).
how the owner sees it: `~/Library/Caches/Lumen` grows through a long editing session and
does not shrink until he quits — and what it is holding is mostly renders of recipes he
has already moved past. Nothing is ever *shown* wrong.
fix: call `catalog.invalidatePreviews(photoID:keeping:)` from the same place the recipe
fingerprint changes (`CatalogService.saveRecipe`'s queue block, :644–655), unlink the
returned rows' payloads through `PreviewStore.resolve`, and call `prune()` on a folder
change as well as on quit. Test: `PreviewCacheTests` already pins the `level >= 2`
predicate against `isBrowseRung` (:111); add
`testEveryStaleRowIsInThePredicateInvalidateDeletes` — build rows at all four levels
under two fingerprints, assert `freshness == .stale` implies membership. That passes
today; the red one is the app-side assertion that a fingerprint change produces a delete,
which needs LumenAppTests to run at all (K-102).

### I3-05 — the memory LRU is not keyed by recipe, so a developed frame filed to disk cannot be read back in the session that wrote it
severity: S3
confidence: traced
class: defect
size: S
evidence: `Sources/LumenApp/ThumbnailLoader.swift:101–104` —
```swift
private struct Key: Hashable, Sendable {
    let url: URL
    let pixels: Int
}
```
no fingerprint. `thumbnail(for:size:)` (:201–208) answers from `cache` and never
consults `previews`, and `image(for:size:)` short-circuits on it (:214) before the
detached worker that reads the disk (:386–392) can run. So the sequence
open A (memory entry (A, 2560) = the camera's embedded JPEG) → edit A → settle →
`recordDeveloped` files a `.lumen` fit row → page away → page back, is a memory hit on
the *pre-edit* entry. The row written a moment ago is read for the first time on the
next launch.
That is deliberate and right for `thumb`/`grid` — `PreviewCache.swift:41–46` argues it
at length, and swapping the picture under a cull pass is the complaint docs/10 §10.1
exists to defuse — but the `fit` rung is the one an edit is *supposed* to invalidate
(`PreviewCache.swift:47–48`, `Freshness.stale`), and the memory cache in front of it
cannot express that.
how the owner sees it: the instant preview when he returns to a photograph he edited
five minutes ago is still the camera's version, badged as such, until he restarts the
app. It is not wrong, it is just the thing this cache was wired up to stop doing.
fix: `ThumbnailLoader.Key` gains a `fingerprint: String` used **only** at
`.fit` (empty string at the browse rungs, which keeps their intentional staleness), and
`recordDeveloped` inserts the settled `CGImage` into `cache` under the new key on the
way past. Test: with `Key` in LumenCore as a small `BrowseCacheKey` type,
`testTheFitRungIsKeyedByRecipeAndTheBrowseRungsAreNot` — same url, two fingerprints:
equal at `thumb`/`grid`, unequal at `fit`. Red today because the type has no such field.

### I3-06 — the decode HUD discards every cache hit, so warming can never be shown to have worked
severity: S3
confidence: traced
class: defect
size: S
evidence: `Sources/LumenApp/LatencyHUD.swift:210–217` —
```swift
/// Record a decode that actually went to the file. Values at or below
/// `decodeHitCeiling` are cache hits and are ignored...
static let decodeHitCeiling: Double = 1.0
func noteDecode(milliseconds: Double) {
    guard enabled, milliseconds > LatencyHUD.decodeHitCeiling else { return }
    decodeMs = milliseconds
}
```
Both call sites pass the real number (`LoupeView.swift:742`, `:844`). The entire value
of `DecodeWarming` is that the decode which *would* have cost 2.4 s off the offload
drive (`DecodeWarming.swift:5–7`) becomes a hit — and a hit is precisely what this
filter throws away, so the line keeps printing the last cold figure. `warmDecode`
(`RenderCoordinator.swift:514–523`) also discards its own result deliberately and
returns nothing, so no caller can tell a warm that landed from one that was skipped by
`mayWarm`. `DecodeWarmingTests` covers `indices` and `mayWarm` — the two pure functions
— and nothing observes the effect.
how the owner sees it: he cannot tell whether read-ahead is doing anything, and neither
can the next person to change it. This is the K-068 row restated as a mechanism: the one
instrument that could answer it is built to ignore the answer.
fix: `LatencyHUD` — keep `decodeMs` as the last *cold* decode and add a second counter
`decodeHits` / `decodeMisses` since launch, incremented on both sides of the same
threshold, printed beside it; have `warmDecode` return `Bool` (whether the key was
already resident) and note it. Test:
`testAWarmedKeyIsAHitAndAColdOneIsAMiss` at the `LatencyHUD` level — feed 0.2 ms then
40 ms, assert `(hits, misses) == (1, 1)` and `decodeMs == 40`; today `hits` does not
exist and the 0.2 ms sample vanishes.

## 3. Nothing at S1

No S1 in this area. The two candidates I chased both came back clean: the size
arithmetic that a corrupt header reaches is overflow-checked and tested
(`DraftLadder.swift:164–178`, `DecodeResidencyTests:141`), and no decode failure path
leaves a partially-mutated cache (`AppleRawSource.swift:346`, `:394–397`). I3-03 is the
crash-shaped finding and I have filed it S2 rather than S1 deliberately: the trap is
real and the guard for it is written down eleven lines away from four sites that lack
it, but I cannot demonstrate from this machine that `CIRAWFilter.nativeSize` ever
returns a non-finite value, and the brief is right that a wrong S1 costs more than a
missed one. It should be fixed as an S1 would be — the fix is six lines and needs no
Mac to test.
