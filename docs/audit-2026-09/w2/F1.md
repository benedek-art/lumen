## 3. FINDINGS

### F1-01 — Delete while masking flags the photograph rejected instead of deleting the mask
severity: S1
confidence: traced
class: defect
size: S
evidence: `Sources/LumenApp/Keymap.swift:521-523`
```swift
case NSDeleteFunctionKey, 0x7F:
    state.setFlag(.rejected)
    return true
```
No guard on `PanelLayout.shared.layout.isMasking` anywhere before it — the very next
case (`0x1B`, Escape, `:524-540`) *does* test `isMasking`, which proves this function is
reached with the mask editor up. LR's Delete/Backspace deletes the selected mask
(r1 §F.1 "Delete" row).
how the owner sees it: he draws a radial he does not want, presses Delete the way he has
for fifteen years, the ellipse stays exactly where it was and the *photograph* silently
picks up a Rejected flag. With a cull-then-delete-rejected workflow that is a photograph
queued for deletion by a keystroke aimed at a mask.
fix: `Keymap.swift` — before `setFlag(.rejected)`, if `PanelLayout.shared.layout.isMasking`
and `state.activeMaskID != nil`, delete the selected component (or the mask when it is the
last component) through the same path `MaskPanel`'s Delete menu item uses, and return true.
THE TEST: a `LumenAppTests` keymap case asserting that with masking up and a mask selected,
`0x7F` leaves `photo.flag == .none` and removes the component — it goes red the moment the
`isMasking` branch is removed. (Note K-102: no CI lane runs `LumenAppTests`; this test
needs the filter added or it is another green lane that proves nothing.)

### F1-02 — A linear gradient cannot be rotated without changing its feather
severity: S2
confidence: traced
class: parity-gap
size: M
evidence: `Sources/LumenCore/Interaction/MaskHandles.swift:293-311` — `enum LinearGrab`
is `move | startHandle | endHandle | startBand | endBand | create`. There is no `.rotate`.
`MaskCanvas.swift:739-750` (`.startHandle/.endHandle`) moves one endpoint to the pointer,
which by construction changes both the direction *and* the distance between the two band
lines, i.e. the feather (`MaskRaster.linearPlane` ramps between them, `:453-476`). The
radial got a 360° rotate band (`MaskHandles.swift:280`); the linear got nothing.
r1 §F.2: "hover the centre line → rotate cursor, drag rotates about the pin, ⇧ snaps 15°."
how the owner sees it: he sets a horizon gradient with the falloff he wants, then wants it
five degrees off level. Every gesture available turns it *and* re-spreads it, so he ends up
re-dragging the whole gradient from scratch — the "I have to redraw it" complaint that
`MaskHandles` exists to kill, still alive on the other shape.
fix: add `LinearGrab.rotate` returned for a press within `grabRadius` of the **axis**
between the two band lines but outside `interiorMoveFraction`; in `MaskCanvas.dragLine`
rotate both endpoints about their midpoint by the pointer's angular travel, reusing
`MaskHandles.snapped` for ⇧. THE TEST: `MaskHandlesTests` — a press on the axis one third
of the way along returns `.rotate`, and a `MaskCanvas`-level arithmetic test that the
rotated line's length is unchanged to 1e-9; substituting `.startHandle` back makes the
length assertion red.

### F1-03 — The rotate band and every other radial grab region are invisible: no affordance, no cursor
severity: S2
confidence: traced
class: defect
size: S
evidence: `MaskCanvas.drawRadial:1264-1272` ends "NO ROTATION KNOB… the whole band just
outside the rim turns the ellipse now" — and draws nothing there. The only cursor logic in
the file is `setDrawCursor` (`:288-301`), which pushes `NSCursor.crosshair` **only** when
`needsDrawing` is true (`:304-318`), i.e. only before the shape exists. After that the
pointer is a plain arrow over move, resize, feather and rotate alike. LR changes the cursor
for each (r1 §F.1 "cursor becomes a curved-arrow rotate icon"). The 22 pt-wide rotate
annulus is therefore discoverable only by reading the `.help()` tooltip string
(`MaskCanvas.swift:355-359`).
how the owner sees it: the feature he asked for by name — "I would like to be able to turn
it wherever I want… on the outside of it" — exists and is unfindable; worse, a drag started
there looks identical to the drag 12 pt further out that throws the ellipse away.
fix: `MaskCanvas` — in `onContinuousHover`, run the same `radialGrab`/`lineGrab` the press
will run and push the matching `NSCursor` (`openHand`/`resizeLeftRight`/`crosshair`/a
drawn rotate glyph); optionally stroke the rotate annulus at alpha 0.15 while the pointer is
inside it. THE TEST: the hit-test half is already covered
(`MaskHandlesTests.testTheBandOutsideTheRimTurnsTheEllipse:237`); add a pure function
`MaskHandles.cursor(for: RadialGrab) -> CursorRole` in LumenCore with a case-exhaustive
test, so deleting the rotate case fails to compile rather than failing silently.

### F1-04 — ⇧ on a radial resize handle makes a circle where LR preserves the aspect; ⌥ (scale from the opposite side) is unread
severity: S2
confidence: traced
class: parity-gap
size: S
evidence: `MaskCanvas.swift:992-994`
```swift
if isShiftDown {
    nextRadii = roundedRadii(nextRadii, drivenByX: grab == .resizeMajor)
}
```
`roundedRadii` (`:1040-1047`) sets the other radius to `r · w/h`, i.e. a **circle in
pixels**, discarding whatever ratio the ellipse had. r1 §F.1: "⇧-drag a handle preserves
aspect; ⌥-drag scales from the opposite corner rather than the centre." `isOptionDown` is
never read in either resize branch (the whole `.resizeMajor/.resizeMinor` case,
`MaskCanvas.swift:962-994`).
how the owner sees it: he has a 3:1 ellipse along a wall, holds ⇧ to grow it "in
proportion" as every other tool in the industry does, and it snaps to a circle — one drag
and the shape is gone.
fix: split the two meanings — ⇧ **on create** keeps the circle constraint (that matches
LR's ⇧-drag-to-create); ⇧ **on resize** scales the other radius by the same factor
(`nextRadii[1] = origin[1] * (nextRadii[0]/origin[0])`); add ⌥ on resize to hold the
opposite rim point fixed by translating the centre half the radius delta. THE TEST:
`MaskHandlesTests`-style pure helper `MaskHandles.resized(origin:axis:delta:shift:option:)`
in LumenCore, asserting ratio preservation under ⇧ and a fixed opposite rim under ⌥;
substituting `roundedRadii` back makes the ratio assertion red.

### F1-05 — A brush stroke that begins within 11 pt of another mask's pin is discarded, and the selection jumps
severity: S2
confidence: traced
class: defect
size: S
evidence: `MaskCanvas.swift:383-387`
```swift
if case .idle = mode, let id = foreignPin(at: value.startLocation) {
    mode = .pin(id)
    return
}
if case .pin = mode { return }
```
This runs **before** the `switch component.kind` that reaches `dragBrush` (`:388-403`).
`foreignPin` (`:1355-1369`) excludes only *docked* pins — its own comment argues at length
that a docked pin must not steal a stroke ("Losing a stroke to a signpost is a real
cost") — and then applies none of that reasoning to on-image pins, whose 11 pt discs
(`pinGrab = 11`, `:1374`) sit on every radial centre and every gradient midpoint on the
picture.
how the owner sees it: he paints over the middle of an existing radial, the stroke never
appears, and the panel jumps to a different mask — so his next stroke lands on the wrong
mask entirely.
fix: `MaskCanvas` — for a `.brush` (or `.polygon`) component, only treat a press as a pin
press when the gesture ends without travel (`< outlineClickSlop`), i.e. carry `.pin` as a
*candidate* and fall through to `dragBrush` as soon as `drawsShape(from:to:)` is true;
the geometry kinds can keep today's press-wins rule. THE TEST: promote the decision into
`MaskHandles.pinPress(kind:travelled:) -> PinDecision` with a LumenCore test that a brush
press with 20 pt of travel over a pin returns `.paint`; substituting the unconditional
`return` makes it red.

### F1-06 — Another mask's pin makes the canvas swallow pan and scrub-zoom over the whole picture
severity: S2
confidence: traced
class: defect
size: S
evidence: `MaskCanvas.swift:332-346`
```swift
private var hasForeignPins: Bool {
    pinPositions().contains { $0.id != maskID && !$0.docked }
}
private var isLive: Bool {

```
`isLive` drives `.allowsHitTesting(isLive)` (`:279`) on a `contentShape(Rectangle())`

component selected (`.colorRange`, `.lumaRange`, `.luminosity`, `.aiSubject`, `.maskRef`,

`sliderGestureChanged(true)` (`:389`) for a gesture that will never write anything.
The call site's own comment (`LoupeView.swift:1493-1495`) still says "The canvas is inert
unless the masks section is open with a drawable component selected, so it never eats a pan
or a click-to-zoom" — that stopped being true when `hasForeignPins` was added to `isLive`.
how the owner sees it: with a Colour Range mask selected and any gradient elsewhere on the
frame, the photograph will not pan at 1:1 and the press-drag zoom scrub is dead. Nothing

`LoupeView` comment in the same commit. THE TEST: a `MaskHandles`-level predicate
`MaskHandles.consumesDrag(kind:pressIsOnPin:)` with a LumenCore test that a

### F1-07 — A self-crossing lasso silently punches a hole in its own mask
severity: S3
confidence: traced
class: defect
size: M
evidence: `MaskRaster.signedDistanceToOutline:761-787` decides inside/outside by an
even-odd crossing count (`if px < cross { inside.toggle() }`), and `polygonPlane:713-756`

## 4. THE ONE-LINE ANSWER TO THE OWNER'S ASK

The *shape* grammar is there and in places ahead of Lightroom: the whole rim resizes, the
whole outside band rotates, the feather ring drags, ⇧ snaps to 15° on both shapes, ⌥ draws
a radial from its centre, and a brush stroke is stabilised and pressure-sensitive. What is
missing is the **modifier and keyboard layer on top of it** — ⌥ on resize and on the
gradient's bands, ⌘-double-click, ⌘⌥-duplicate, Delete, `H`, `/` — plus two things that
make the present gestures unusable in practice: nothing on screen or in the cursor says
where the rotate band is (F1-03), and Delete does something dangerous instead of nothing
(F1-01).
