### B3-01 — "All bands" destroys the band spread it promises to preserve, and the thumb leaves the pointer while it does it
severity: S2
confidence: traced
class: defect
size: S
evidence:
`ColorPanel.swift:287` — the readout under the ring, in All-bands mode:
`"All bands move together; the spread between them is preserved."`
`ColorPanel.swift:676-706` — the binding it describes:
```
get:  let total = bands.reduce(0.0) { $0 + component.value($1) }
      return total / Double(bands.count)                       // :680-681
set:  let mean = sum / Double(bands.count)                     // :694
      let delta = newValue - mean                              // :695
      for i in bands.indices {
          let moved = component.value(bands[i]) + delta
          component.write(&bands[i], Num.clamp(moved, -100, 100))   // :697-698
      }
```
Worked case, arithmetic only. Bands `[+50, −50, 0, 0, 0, 0, 0, 0]`, mean 0. Drag
Saturation to **+100**: `delta = 100`; band 0 → 150 → **clamped to 100**, band 1 → 50,
bands 2–7 → 100. New mean = `(100 + 50 + 100×6) / 8` = **93.75**. The getter now returns
93.75, so the thumb sits at 93.75 while the pointer is at 100. Drag back to 0:
`delta = −93.75` → `[6.25, −43.75, 6.25 ×6]`. The original spread — one band 100 above
another — is now 50, and no further dragging restores it.
`LumenControls.swift:920` — `let fraction = geometryOfDrag.fraction(of: value)`: the
thumb's x is a pure function of the binding, so the decoupling is visible during the
drag, not only on release.
how the owner sees it: he builds a mixer with Blue pulled down and Orange pushed up,
switches to All bands to lift everything, and the thumb stops following his cursor
partway across; when he drags back to where he started the picture is not where it
started either — the difference he built between the bands has been quietly squeezed out,
and the sentence under the ring told him it would be preserved.
fix: `ColorPanel.mixerBinding`. Two changes, both local. (1) Clamp the *offset*, not each
band: compute `allowed = min over bands of the headroom in the drag's direction` and
apply `min(delta, allowed)` uniformly, so the group move stops at the first rail with the
spread intact. (2) Make the readout the offset that was actually applied, not a
re-derived mean — carry the group offset in view state for the length of the gesture so
`get` returns what the pointer asked for. Test (`LumenCoreTests`, on a pure static helper
`ColorPanel.groupMove(bands:delta:) -> [Double]` extracted from the setter):
`testAGroupMoveAtTheRailKeepsEverySpread` — bands `[50, −50, 0…]`, move `+100` then
`−100`, assert the array is bit-identical to the input. Red today (returns
`[6.25, −43.75, …]`), red again the moment the per-band clamp is substituted back.

### B3-02 — A single click anywhere inside the hue ring's 130×130 box throws a band handle to that angle; a click near the centre throws it to a random hue
severity: S2
confidence: traced
class: defect
size: S
evidence: `ColorPanel.swift:1125-1153`:
```
.frame(width: MixerHueRing.diameter + 12, height: MixerHueRing.diameter + 12)   // 130×130
.contentShape(Rectangle())                                                      // :1126
.gesture(DragGesture(minimumDistance: 0)
    .onChanged { drag in
        ...
        let dx = Double(drag.location.x - box / 2)
        let dy = Double(drag.location.y - box / 2)
        guard dx != 0 || dy != 0 else { return }                                // :1146
        let degrees = Num.wrapHue(atan2(dy, dx) * 180 / .pi)
        let handle = grabbed ?? MixerHueRing.nearestHandle(to: degrees, in: arcList[index])
        if grabbed == nil { grabbed = handle }
        onHandleMoved(handle, degrees)                                          // :1153
```
There is **no hit test**. `contentShape(Rectangle())` claims the whole 130 pt square —
the wheel's hollow interior, the four corners outside the circle, and the annulus alike —
`minimumDistance: 0` fires `onChanged` on mouse-down, and `nearestHandle` always returns
one of the four. Compare `LumenSlider`, which does gate the press:
`SliderDrag.grabsThumb(pressX:thumbX:)` with an 11 pt grab radius
(`LumenControls.swift:1093-1095`, and the constant's note at `:840-844`). The centre case
is the worst: the guard at `:1146` only rejects the exact pixel `(0,0)`, so a press one
point off-centre produces an `atan2` of two sub-pixel numbers — an essentially arbitrary
angle — and the nearest handle is dragged there.
how the owner sees it: he clicks the hue wheel to see a colour, or to try to select a
band the way DxO's ColorWheel lets him, and instead one end of the selected band's arc
snaps to wherever he clicked. Red's feather can end up 130° away in one click, the
picture changes, and nothing on screen says what he just did.
fix: `MixerHueRing`, extract the hit decision into a static pure function
`grab(at point: CGPoint, box: CGFloat, arc: ColorEngine.BandArc) -> MixerArcHandle?`:
return `nil` unless the press radius is inside `[arcRadius − 10, arcRadius + 10]` **and**
within the same 11 pt angular grab distance of a handle that `SliderDrag` uses for the
thumb; `onChanged` returns early on `nil`. The vacated interior is then free for the
grammar `docs/05-spec-color.md:59` and `docs/28-ui-refresh.md §5.3` both ask for — a click
on a hue selects the band that owns it — which is B3-06.
Test (`LumenAppTests`, no Mac needed, the function is pure):
`testTheRingIgnoresAPressInsideTheWheel` asserts `grab(at: centre + (1,1), …) == nil` and
`grab(at: corner, …) == nil`, and `testTheRingStillGrabsItsOwnHandle` asserts a press
plotted at `MixerHueRing.point(centre, arcRadius, arc.coreEnd)` returns `.coreEnd`. The
first assertion is red today for every point in the box.

### B3-04 — The mixer rebuilds the ribbon's 97 membership vectors and repaints a 180-wedge Canvas on every mouse event of every slider drag
severity: S2
confidence: traced
class: defect
size: M
evidence: `AppState.swift:1520-1522` — `var recipes: [URL: Recipe] { didSet { edits.bump() } }`;
`EditRevision.swift:60-62` — `@Published private(set) var value` — and `ColorPanel.swift:45`
observes it (`@EnvironmentObject var edits: EditRevision`). So one mouse event of any
slider drag ⇒ one `ColorPanel.body`. Per body, with the Mixer fold open:
- `ColorPanel.swift:117` — `ColorEngine.bandArcs(bands)`, rebuilt.
- `ColorPanel.swift:281` — `MixerBandRibbon(weights: ColorPanel.ribbonWeights(arcs), …)`.
  `ribbonWeights` (`:934-943`) loops `0...ribbonSteps` with `ribbonSteps = 96` (`:924`)
  ⇒ **97 calls to `ColorEngine.bandWeights(hue:arcs:)`**, each of which
  (`ColorEngine.swift:560-597`) heap-allocates `[Double](repeating: 0, count: 8)` and runs
  8 `hueDelta` + feather evaluations ⇒ **97 array allocations and 776 arc evaluations per
  mouse event**, before SwiftUI has diffed anything.
- `ColorPanel.swift:1052-1123` — the ring `Canvas` builds and fills **180 wedge `Path`s**
  (`MixerHueRing.steps = 180`, `:1033`) plus 8 ticks, 3 arc strokes and 4 handle dots; it
  cannot be skipped by SwiftUI's diff because `MixerHueRing` stores two closures
  (`onHandleMoved`, `onResetArc`, `:1026-1027`).
- `ColorPanel.swift:1247-1272` — the ribbon `Canvas` walks 8 × 97 = **776 `addLine`s**.
At a 120 Hz trackpad drag that is ~11,600 `bandWeights` calls and ~23,400 `Path`
constructions per second on the main actor, and *none of the inputs change* unless a ring
handle is being dragged. `docs/28-ui-refresh.md §5.5` prices exactly this: "Per-event cost
∝ expanded slider rows in the workspace… one panel of ≤16 rows re-bodies per mouse event."
This is one section adding the equivalent of many rows on top of that.
how the owner sees it: with the Colour section open, dragging *any* slider anywhere in the
develop column — Exposure in Basic included — is measurably heavier than the same drag with
Colour collapsed, and the mixer is doing all of it to redraw two pictures that did not
change.

a tiny `MixerRibbonCache` keyed on `[ColorEngine.BandArc]` (one entry; arcs change only
when a handle moves or the mixer is reset). (2) Conform both views to `Equatable` on their
value inputs and wrap them in `EquatableView`, moving the two closures behind a stable
`@State`-held coordinator object so identity does not defeat the comparison.
Test (`LumenAppTests`, in the shape `PanelLayoutBroadcastTests` already uses):
`testTheRibbonIsComputedOnceForUnchangedArcs` — call the cache twice with equal arc arrays
and assert the miss counter is 1; `testChangingOneHandleRecomputes` asserts 2. Red today:
there is no cache and `ribbonWeights` is an unconditional 97-iteration loop.

### B3-05 — Double-clicking the ring to reset an arc first drags a handle, so one undo lands on an arc the photographer never made

confidence: traced
class: defect
size: S
evidence: `ColorPanel.swift:1137-1143`:
```

    pressWasReset = true

```
`clickCount` is **1** on the first press of a double-click, so that press falls straight

## Checked and found correct

Recorded so no later pass re-opens them.

- **Both eyedroppers arm, disarm and re-arm correctly**, and both say so on screen:
  `pickIsArmed` reads `state.pickTarget` rather than a private flag (`:487`), so the button
  and the pick machinery cannot disagree; pressing an armed picker cancels
  (`:501-504`, `:516-518`). This is the same contract as BasicPanel's neutral picker
  (`BasicPanel.swift:348-352`).
- **A picked swatch becomes the selected swatch.** `:479-481` watches
  `swatches.count` and moves the ring to the tail on growth, which is the only signal the
  async resolver can deliver to this panel's `@State`. The asymmetry (growth only) is
  correct — `removeSwatch` re-aims the ring itself (`:562-563`).
- **`removeSwatch` removes the chip the ring marks**, through the clamp at `:551-564` +
  `:568-571`, and re-guards inside the per-photo mutation (`:557-560`) for multi-select.
  The behaviour is right; only its test is not (B3-08).
- **The B&W toggle keeps each photograph's own mix**, and I checked the case I expected to
  be wrong: turning the treatment on and straight off again leaves `look.bw` **nil**, not a
  disabled husk, because `BlackAndWhite.toggled` (`RecipeLook.swift:625-630`) returns nil
  when `!on && !next.hasMix`. So the section's `isModified: bw != nil` (`:599`) does not
  get stuck lit. `setTreatment` (`:645-649`) runs inside `updateRecipe`, so a
  multi-selection toggle gives each frame back its own mix.
- **The chevron follows the content** (`:581-596`): with the treatment off the header
  offers no fold, because there would be nothing behind it but the switch that brings it
  back — and that switch is drawn outside the gate (`:603-609`), so no state can strand it.

- **The wire format cannot overflow the panel.** `normalizedBands` / `normalizedDoubles`
  (`:793-807`) pad and truncate to `ColorEngine.bandCount` on every read *and* every write,

  index past a hostile sidecar.
- **The ribbon and the ring draw the engine's own geometry, not a redrawing of it**:

- **Layout fits at 320 pt.** G1 measures row content width as `W − 28` = **292 pt** at the

- **No hover on a slider row and no focus ring on one**, per the owner's two recorded
