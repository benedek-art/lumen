## Findings (ranked)

### F5-01 — A reference to a disabled Vision mask never gets its matte
severity: S2
confidence: traced
class: defect
size: S
evidence: `VisionMattes.swift:58` — `for mask in recipe.masks where mask.enabled` — is the
only source of "which mattes to generate" for both the async path (`RenderCoordinator
.ensureMattes` → `missingMatteKinds` `:415-419`) and the export path (`generateMattesNow`
`:402-412`). But `MaskRaster.referenced` (`:257-263`) deliberately lends a DISABLED mask's
selection: "A disabled mask still SELECTS … otherwise turning off the Sky mask to look at
something would silently empty every mask built on it", pinned by
`MaskChannelAndReferenceTests.testADisabledMaskStillLendsItsSelection` (`:187`). The
rasterizer promise and the generator's filter contradict each other.
how the owner sees it: Mask A = Subject (disabled to look at B alone), Mask B = "Another
Mask" → A. Open that photo in a new session, or after twelve other Vision-masked files have
evicted A's matte (`PipelineRenderer.swift:102`, `matteCacheLimit = 12`): B renders as
nothing in the loupe AND in the exported file, with no badge — B's row is a `referenceRow`
(`MaskPanel.swift:1291`) and never reaches `modelNote`. Re-enabling A "fixes" it, which is
the kind of bug nobody can reproduce twice.
fix: `VisionMattes.kinds(in:)` walks every mask that is enabled OR reachable through a
`maskRef` from an enabled mask (or, simplest and cheapest, drops the `enabled` filter — the
pass is once per file and cached). Move the walk into LumenCore
(`MaskKind.wantedMattes(in: Recipe)`) so the Linux lane can test it. THE TEST: recipe with
mask A `{enabled: false, aiSubject}` and mask B `{enabled: true, maskRef: A}` →
`wantedMattes` contains `.aiSubject`; put `where mask.enabled` back and it goes red.

### F5-02 — K-085 has no test that could go red; here is the one that can
severity: S2
confidence: inferred
class: defect
size: S
evidence: `Tests/` contains no reference to `VisionMattes`, `VisionMatteWorker` or
`plane(from:)`. The `MaskGPUParityTests` lesson (`XCTSkipUnless` at `:152,172,186`) is one
skip away from repeating here: a Vision test that skips when no instance is found would be
green forever. BUILDING `:280-284` says a vertical mirror "is a one-line fix" — it is also
one nobody would notice on a centred portrait, and would notice on every landscape with a
foreground rock.
how the owner sees it: if the convention is wrong, every Subject/Background/People mask is
upside down and the adjustment lands on the wrong half of the photograph; if it is right,
nothing. Neither outcome is currently observable from CI.
fix: two cases in `Tests/LumenPipelineTests` (macOS lane, no skips): (a) unit —
`VisionMattes.plane(from:)` on a hand-built `CVPixelBuffer` (`kCVPixelFormatType_OneComponent8`,
row 0 = 255, all other rows = 0, and a `bytesPerRow` deliberately wider than `width`) must
give `out[x, 0] == 1` and `out[x, h-1] == 0` — substitute `y * stride` with
`(height-1-y) * stride` and it goes red; (b) end-to-end — draw a 512×384 CGImage with one
dark high-contrast disc in the TOP-LEFT quadrant on a flat bright ground, call
`foregroundPlane`, `XCTAssertNotNil` (never `XCTSkip`) and assert the matte centroid has
`y < h/2` and `x < w/2`. If Vision declines the synthetic disc the test fails loudly and a
small photo fixture is the answer, which is the whole point.

### F5-04 — Brightness Range has no eyedropper and no luminance-map view
severity: S3

class: parity-gap
size: M

### F5-05 — The "neutral rendition" runs on the render actor, and nothing times any of it
severity: S3
confidence: traced
class: defect
size: S
evidence: `RenderCoordinator.ensureMattes` (`:476-481`) calls `renderer.matteSourceImage`
synchronously — inside the actor, BEFORE the `await` that hops to `VisionMatteWorker`.
`matteSourceImage` (`PipelineRenderer.swift:264-271`) is `renderPreview(recipe: Recipe(),
maxLongEdge: 1024, draft: false, coarseDecode: false)`: a full-quality decode and a whole
graph build. `VisionMattes.swift:14-16` claims "IT NEVER RUNS ON THE RENDER PATH" — true
of the segmentation, not of the rendition. Traced count: one non-draft 1024 px render per
(file, pass), re-paid after eviction (`matteCacheLimit = 12`). No number exists: `grep
signpost|ContinuousClock|Date()` in `VisionMattes.swift` and `RenderCoordinator.swift` → 0.
So "speed vs LR/C1/Luminar" (docs/08 budgets: Subject ≤ 1 s, Sky ≤ 1.5 s) cannot be
answered by anyone, on any Mac, until it is measured.
how the owner sees it: the first frame after selecting a Subject-masked photo waits for a
second render before it can start; the HUD's `decodeMilliseconds` attributes none of it.
fix: hand the worker the decoded frame and let IT build the neutral CGImage (or at minimum
`coarseDecode: true` — the segmenter does not need a full demosaic at 1024 px); wrap both
halves in `ContinuousClock` and return `MattePass.renditionMS`/`segmentMS`, shown next to
decode ms on the HUD. THE TEST: an actor-hop test that a `renderPreview` issued while
`ensureMattes` is mid-rendition completes first (LumenPipelineTests, macOS lane); with the
rendition left on the actor it serialises and goes red.
