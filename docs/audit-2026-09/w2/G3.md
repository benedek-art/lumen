## 0. Checked and found correct — recorded so nobody re-derives it

- **Escape → R does not reset the crop.** The obvious trap — Escape leaves the tool
  without clearing the double-press clock, so the next `R` inside 0.45 s reads as the
  second half of `R R` and throws the framing away — **does not exist**:
  `CropTool.revert` calls `forgetArming()` on *both* branches (`CropPanel.swift:174–178`
  and `:197`), and `settle` calls it on every way out of the workspace
  (`WorkspaceEntry.swift:165`). `noteArming` (`CropPanel.swift:252–257`) counts
  transitions, not states, so both press orders resolve identically.
- **The key-up hoist is correct and load-bearing.** `handle` answers a key-up before the
  text-field, sheet, popover, ⌘ and ⌃ guards (`Keymap.swift:81–83`), and `handleKeyUp`
  folds `{`/`}` back to `[`/`]` (`:434`) — so a shift or a ⌘ pressed mid-hold cannot
  strand `holdActive` and dead-end both brackets and the Space peek for the session.
  `InspectionHolds.resolve` answers a key-up from state rather than surface
  (`InspectionHolds.swift:174–180`), so a hold survives a view change and still releases.
- **`ArrowNavigation` is honest.** `moveSelection` routes every arrow through
  `ArrowNavigation.step` (`AppState.swift:2724–2740`), the comparing branch requires
  `selectionCount >= 2` and returns `.moveWithinSelection` so a survey cannot be
  collapsed by the key that walks it, and `ComparePanes.pairWindow` keeps the cursor
  inside the drawn pair. The dispatcher yields all four arrows to a focused slider
  (`Keymap.swift:522`) and `KeyGrammarTests:335–365` proves the slider handles all four.
- **The palette does not strand you in the mask editor.** `jump` → `PanelLayout.reveal`
  → `WorkspaceLayout.select`, which clears `isMasking` (`Workspace.swift:418–421`), so
  ⌘K pressed while masking leaves masking rather than opening a section behind the mask
  editor. Same for ⌘1–⌘5 and the rail.
- **`KeyGrammar.dispatchedKeys` and the dispatcher's switch agree**, and the scanner has
  a floor assertion so silent non-scanning fails (`KeyGrammarTests:310`). The two `-`
  cases (`Keymap.swift:187` purple label outside the loupe, `:354` zoom out inside it)
  are one set member and are correctly disjoint; each zoom key guards its own surface
  rather than sharing a `where` (`:347–350`), which is right — a `where` on a
  multi-pattern case binds the last pattern only.
- **The empty state is scoped correctly.** `centre` tests `state.allPhotos.isEmpty`, not
  `photos` (`ContentView.swift:316`), so a filter that matches nothing shows the grid's
  own "nothing matches / Clear Filter" overlay rather than "Open a folder" to somebody
  who has one open.

### G3-01 — ⌘B is attached to two different actions, the reference names one, and the sidebar's own tooltip promises the other
severity: S2
confidence: measured
class: defect
size: S
evidence: two literal call sites, from a grep of every `.keyboardShortcut` in the target.
`Sources/LumenApp/ContentView.swift:507–516`:
```swift
Button { state.addSelectionToTargetCollection() } label: { … }
    .buttonStyle(.borderless)
    .keyboardShortcut("b", modifiers: [.command])
    .disabled(state.targetCollection == nil || state.editTargets.isEmpty)
    .help("Add the selection to the target album (⌘B)")
```
`Sources/LumenApp/LumenApp.swift:241–245`:
```swift
Button(state.assessmentMode ? "Assessment Surround (on)" : "Assessment Surround") {
    state.toggleAssessmentMode()
}
.keyboardShortcut("b", modifiers: [.command])
```
`KeyGrammar` declares ⌘B exactly once, as "Assessment surround (ISO 12646 mid-grey)"

the window's view hierarchy sees the event, so the View menu wins and the sidebar button

twice and built `KeyGrammarTests` for.

**Why the mechanism did not catch it.**

into `var attached: Set<KeyBinding> = []`, so two attachments of one chord collapse to one

diagnostic would name only the last file scanned. `testNoTwoEntriesClaimTheSameChord:392`
checks the reference table against itself and never looks at the sources. Nothing in the
suite asks "is any chord attached twice", which is the one question a keymap audit exists
to ask.

Sequence: the row that put ⌘B on the album button was written when `B` was the Basic
panel — the Sidebar's own header still says so, staler than the code it documents
(`ContentView.swift:341–347`: *"The bare-key dispatcher in Keymap.swift already spends
those two letters on the Basic panel and the scopes … `⌘B`, `⌘G`, `⇧⌘G` and `⌘K` are
free"*). K-104 then gave the bare `B` to the album and ⌘B to assessment, and the sidebar
row was not retired with it.

how the owner sees it: he reads "Add the selection to the target album (⌘B)" on the button
he is pointing at, presses ⌘B, and the photograph's surround turns ISO 12646 mid-grey.
Nothing is added to the album. The Help sheet, if he opens it, agrees with the surround
and never mentions the album, so the button is the only thing in the app that says ⌘B
means anything else.

fix: `ContentView.swift` — drop `.keyboardShortcut("b", modifiers: [.command])` from the
albums button and shorten its `.help` to "Add the selection to the target album (B)", the
bare key that now does it (`Keymap.swift:286`). THE TEST, and it is the one that matters
more than the fix: in `KeyGrammarTests`, change `attached` from a `Set` to a

naming the files when it does not —
```swift
for (binding, files) in attached where files.count > 1 {
    XCTFail("\(binding.display) is attached in \(files.joined(separator: ", "))")
}
```
That is red today (`⌘B is attached in ContentView.swift, LumenApp.swift`) and stays red
the next time a chord is spent twice. Keep the existing set-equality assertions; they
answer a different question.

### G3-02 — `R` pressed inside the mask editor arms the crop rectangle underneath it: the picture loses its crop and its straighten, no crop panel appears, and no key puts it back
severity: S2
confidence: traced
class: defect
size: S
evidence: `Sources/LumenApp/WorkspaceEntry.swift:177–194`
```swift
func toggleCropTool() {
    let viewport = LoupeViewport.shared
    let doublePressed = CropTool.shared.noteArming()

    guard PanelLayout.shared.layout.workspace == .crop else {
        enter(.crop)
        …
    }
    viewport.showCrop.toggle()
    …
}
```
The guard asks only for the **workspace**, and masking does not change the workspace: it
is a flag beside it (`Workspace.swift:348`, `PanelLayout.setMasking:155–159` — *"moves
the flag and nothing else"*). `WorkspaceLayout.select` clears `isMasking`
(`Workspace.swift:418–421`) and `click` does not, so the only ways out of masking are the
verb, Escape and a workspace change — none of which `R` performs when the workspace is
already `.crop`. So from Crop → `M` → `R`, `showCrop` becomes `true` with `isMasking`
still `true`.

**This is what is left of KG-02 after its fix.** The `O` route was closed mid-audit by
splitting `enterMasking()` out of `toggleMasking` (`WorkspaceEntry.swift:125–148`) and
pointing `Keymap.swift:265` at it — the right fix, and it makes `R` the last route in.
`toggleCropTool` is untouched by it (`WorkspaceEntry.swift:197–214`, quoted above from the
post-fix tree) and `cropArmed` still omits `isMasking` (`LoupeView.swift:1042–1045`,
re-read after the fix). So the pattern the file's own header describes — *"Every route
into a workspace had been fixed one at a time at its own call site, so each new route
arrived unfixed"* — has repeated once more: the key that was reported got the verb, the
key beside it did not.

Everything downstream then behaves exactly as it did for KG-02, which the K audit
traced through the `O` key: `cropArmed` is `viewport.showCrop && panel.layout.workspace ==
.crop` and knows nothing about `isMasking` (`LoupeView.swift:1042–1045`), so `content`
routes to `cropCanvas`, `renderRecipe` strips `crop` and `angle` (`:1059–1065`), and
`MaskOverlayView`/`MaskCanvas` are inside `canvas`, which is never built. The develop
column meanwhile still draws the mask editor (`DevelopPanel.swift:415, 473` branch on
`panel.layout.isMasking`), so the crop rectangle has **no panel** — no ratio, no angle, no
guides — and pressing `R` again only toggles `showCrop` back off without leaving masking.

`settle`'s own comment says *"the two verbs above are the vocabulary and a third caller
reaching past them would be the next unwired route"* (`WorkspaceEntry.swift:149–151`).
That file now holds **four** public entry verbs — `enter`, `jump`, `toggleMasking`,
`enterMasking` — plus `toggleCropTool`, which is a fifth and is the one that reaches past
the masking pair.

how the owner sees it: he is framing a photograph, presses `M` to check a mask, presses
`R` out of habit to get the rectangle back — and the photograph snaps to its full
uncropped, un-straightened self with a rectangle on it, the column still showing the mask
list, and nothing on screen naming either state. Escape gets him out of masking but leaves
`showCrop` set; `R` again removes the rectangle but not the mask editor.

fix: `WorkspaceEntry.swift` — make `toggleCropTool`'s guard the full question, not half of
it: `guard PanelLayout.shared.layout.workspace == .crop, !PanelLayout.shared.layout.isMasking
else { enter(.crop); … }`. `enter` already goes through `PanelLayout.expose` → `select`,
which clears `isMasking` for free, so the masked case falls into the branch that is
already correct. Belt and braces, and the line the K audit also asks for: make `cropArmed`
read `viewport.showCrop && panel.layout.workspace == .crop && !panel.layout.isMasking`
(`LoupeView.swift:1043–1045`), so no future route can strand the rectangle either.
THE TEST: the rule is pure and belongs in LumenCore beside the layout it is about —
```swift
// WorkspaceTests
func testTheCropToolCannotBeArmedInsideMasking() {
    var layout = WorkspaceLayout(workspace: .crop, isMasking: true)
    XCTAssertFalse(WorkspaceLayout.cropMayArm(in: layout))   // new, one line
    layout.select(.crop)                                      // the entry verb's route
    XCTAssertTrue(WorkspaceLayout.cropMayArm(in: layout))
}
```
red today because no such predicate exists and the app's answer is `workspace == .crop`
alone. The view-level assertion (`showCrop == false` after `R` from inside masking)
belongs in `LumenAppTests`, which needs the K-102 CI filter to count.

gains a `Group` wrapper; the sidebar buttons keep their labels and lose their
`.keyboardShortcut`. THE TEST: extend `KeyGrammarTests` with the structural half —
`.keyboardShortcut` is allowed only in `LumenApp.swift` (the always-registered `Scene`)
or in a file named in a new `KeyGrammar.filesWithConditionalShortcuts` table carrying, per
file, the reason the view is always in the hierarchy — the same escape-hatch-as-data shape
`filesWithComputedShortcuts` (`KeyGrammar.swift:257–265`) already uses and
`testAComputedShortcutOnlyExistsInAFileThatSaysWhy:369` already enforces. That is red
today for `ContentView.swift` and `FilterBar.swift`, and it is the only assertion a text
