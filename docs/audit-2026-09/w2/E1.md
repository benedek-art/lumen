### E1-01 — Double-clicking a Noise row stamps the primary photo's ISO baseline on every selected photo
severity: S2
confidence: traced
class: defect
size: S

evidence: `Sources/LumenApp/DetailPanel.swift:435-441`

```swift
onReset: { binder.edit("denoise.classic.luma") { recipe in
    recipe.develop.denoise.classic.luma =
        isoDefault.classic.luma
    recipe.develop.denoise.classic.lumaUserSet = false
} })
```

and the same shape for Colour at `:498-502`. `isoDefault` is
`ISODefaults.startingDenoise(forISO: captureISO)` `:342-344`, and `captureISO` reads
`state.primarySelection` `:327-331`. `binder.edit` routes to
`AppState.updateRecipe(coalescingKey:)` (`DevelopPanel.swift:103-105`), which is the
overload that **cannot see the photo** — `AppState.swift:3158-3163` forwards to
`:3180-3199`, whose `targets = explicit ?? editTargets` is the whole selection
(`:2373-2377`). The four sub-sliders reach the same place by a shorter route:
`defaultValue: isoDefault.classic.lumaDetail` `:468` etc., and `LumenSlider.reset()`
writes `value = defaultValue` through the binding when no `onReset` is given
(`LumenControls.swift:1296-1305`).

The photo-aware overload already exists and its own doc comment names this exact case:
*"a reset must land on `startingRecipe(for:)`, which is not the same for every file
(Linear preset for rendered files, **ISO-resolved denoise** for RAW), and a closure that
cannot see the photo can only reset everyone to the same wrong baseline"*
(`AppState.swift:3165-3171`). The denoise resets are the case it warns about and the one
call site that does not use it.

Measured spread of what gets stamped (`ISODefaults` anchors, re-derived):

| ISO | Luminance | Colour | Detail (luma) | Smoothness |
|---:|---:|---:|---:|---:|
| 400 | 0.00 | 15.00 | 50.00 | 50.00 |
| 1600 | 12.50 | 20.00 | 48.51 | 55.97 |
| 6400 | 25.00 | 25.00 | 45.04 | 69.85 |
| 25600 | 40.00 | 30.00 | 41.54 | 83.86 |

how the owner sees it: he selects the night's keepers — ISO 400 to ISO 25600 in one
selection — double-clicks Luminance to put one frame back to its default, and every
other frame in the selection is silently given the *primary's* ISO number instead of its
own. An ISO 25600 frame ends on Luminance 0 and an ISO 400 frame on 40. `lumaUserSet` is
cleared on all of them at the same time, so the recipes now claim those numbers were
inherited from the ISO table when they were not.

fix: `Sources/LumenApp/DetailPanel.swift`. Replace `binder.edit` in the two `onReset`
closures with a per-photo write through `state.updateRecipe(coalescingKey:) { photo,
recipe in … ISODefaults.startingDenoise(forISO: photo.iso.map(Double.init)) … }`, and
give the four sub-sliders explicit `onReset:` closures of the same shape rather than a
`defaultValue` that is one photo's number. `RecipeBinder` wants a sibling of `edit` that
forwards to the photo-aware overload so no panel has to reach past the binder.
THE TEST (red today, in `Tests/LumenAppTests` or a LumenCore-side test over
`ISODefaults`): select two photos at ISO 400 and ISO 25600 with the ISO-400 frame
primary, invoke the Luminance reset, assert
`recipe(for: iso25600).develop.denoise.classic.luma == 40` and
`recipe(for: iso400)…luma == 0`. Today both come back 0. Note K-102 — no CI lane runs
`LumenAppTests` under a filter — so the assertion is worth more as a LumenCore test over

    + "go through, so Amount changes nothing here. Classic is the engine "

`ClassicNR(chroma: 25, chromaUserSet: false)` (`Recipe.swift:1168`, decode default `:1196`), so `coupled`

artifact actually existing, not on the mode — give it an `artifactPresent: Bool` and
have `ISODefaults.classic(for:)` pass `false` until Tier 2 ships (today that makes `.ai`
render exactly like `.classic` plus the decoder stand-in on RAW, which is the honest

tooltip. THE TEST (red today, LumenCore, no macOS needed):
`ISODefaults.classic(for: Denoise(mode: .ai, classic: ClassicNR()))` currently returns

rendered-file path consumes it, so a test that renders a rendered source through
`RenderPlan` in `.ai` versus `.classic` and asserts the two frames **differ** goes red.

### E1-03 — "Profiled" is the flagship claim and the profiler has no caller, no test, and (measured) a 1.3–3.3× σ bias
severity: S2
confidence: measured
class: defect
size: M

evidence: `Sources/LumenCore/Image/DenoiseEngine.swift:139-247` —
`NoiseProfile.estimate(from plane: Plane)`, 109 lines. Callers:

```
$ grep -r "NoiseProfile.estimate\|\.estimate(from" Sources/ Tests/
Sources/LumenCore/Image/DenoiseEngine.swift:1069:  ///    read-noise-dominated profile — which is what `NoiseProfile.estimate` returns
```
— one mention, in a comment. Zero call sites, zero tests. The only profile the render
path ever builds is the generic seed curve: `RenderPlan.swift:455` —
`let noiseProfile = NoiseProfile.forISO(captureISO ?? 100)`.

docs/07 §2.4 specifies the other half: *"For unknown (camera, ISO) pairs the model is
estimated on first encounter from flat image regions and cached in the catalog; every
subsequent photo from that body benefits."* Nothing does that. Every body at a given ISO
gets identical thresholds off the `shotAnchors`/`readAnchors` table
(`DenoiseEngine.swift:78-95`), whose own comment calls it "a physically-derived generic
seed" that "every real body replaces". Nothing replaces it.

The dead code is also wrong. I ported `estimate` to Python line for line (8×8 blocks →
16 mean-bins → 10th-percentile variance × `1/0.78` → weighted LS → the negative-intercept
origin-refit branch at `:240-245`) and ran it against a synthetic plane whose true
profile is `NoiseProfile.forISO(6400)` (`a = 6.4e-4`, `b = 3.0e-6`), 256×256:

| scene | recovered `a` | recovered `b` | σ(0.18) est / true |
|---|---:|---:|---:|
| flat ramp, no texture | 1.14e-3 (178 % of truth) | 0 | **1.32×** |
| ramp + 2 % 6-px sinusoid | 1.26e-3 (196 %) | 0 | **1.38×** |
| ramp + 15 % 6-px sinusoid (the proof frame's own texture) | 7.27e-3 (1136 %) | 0 | **3.33×** |

The cause is visible in the code: a block's variance is taken as noise variance with no
gradient or flatness rejection, so the scene's own slope inside an 8×8 block (the proof
ramp changes ≈11 % across 8 rows) is fitted as shot noise. `b` is driven negative every
time and the `:240-245` branch then refits through the origin, which is why the read term
comes back exactly 0 in all three cases. Thresholds are denominated in σ
(`lumaThresholds`/`chromaThresholds` `:857-905`), so a 3.3× σ is a 3.3× threshold — a
wavelet stage that flattens the picture.

how the owner sees it: today, nothing — the code never runs. The moment anyone wires it
(docs/07 §2.4 requires it, R6 §5 assumes the same `(a,b)` store conditions the network's
noise map), his ISO 6400 frames get denoised as though they were ISO 60000.

fix: `DenoiseEngine.swift`. Either (a) delete `estimate(from:)` and change docs/07 §2.4
plus the panel's "profiled" language to say the profile is a generic per-ISO curve, or
(b) wire it properly: reject blocks whose within-block gradient exceeds a σ-relative
bound before binning (darktable's `MODE_VARIANCE` uses the mode of the variance cloud,
not a percentile of everything), fit on the mode rather than the 10th percentile, and
cache the result per (camera model, ISO) in the catalog. THE TEST, red today, LumenCore,
no macOS: `testEstimateRecoversAKnownProfile` — build a plane from a smooth ramp plus
Poisson–Gaussian noise at `NoiseProfile.forISO(6400)`, assert
`estimate(from:).sigma(at: 0.18)` is within 10 % of `forISO(6400).sigma(at: 0.18)`.
It fails at 132 % on the easiest possible input.

## Where `AIDenoiseSplice` would be wired, and what the classical engine keeps doing

The brief asks for this explicitly. R6 §5 recommends **NAFNet-SIDD-width32 (MIT), hybrid**.
Against the tree as it stands:

**The splice point.** `RenderGraph.swift` gets an `applyAIDenoise(_:plan:options:)` called
from `render` immediately *before* `applyDenoise` (line 136 today is
`image = applyDenoise(image, plan: plan, options: options)`; S2 goes on the line above).
It reads `AIDenoiseSplice.amount(for: plan.denoise)` — nil means do nothing, which is
already the right shape (`DenoiseEngine.swift:1408-1413` distinguishes nil from Amount 0
so the stale badge can stay honest). The blend is
`AIDenoiseSplice.blend(original:denoised:amount:)`, which on the GPU is one `mix` kernel;
the CPU twin at `:1358-1377` is the reference it is measured against. Nothing in
`AIDenoiseSplice` needs to change.

**What produces the artifact.** A new `AIDenoiseWorker` actor in LumenPipeline, patterned
on `VisionMatteWorker`: S1 checkpoint → the classical **hot-pixel pass first**
(`ClassicalDenoise.hotPixelPass`, `:1010-1046`, moved ahead of S2 — SIDD carries no stuck
pixels and the net will smear them) → `TilePlan(width:height:tile: TilePlan.aiTile,
overlap: TilePlan.aiOverlap)` (768/32, already the shipped default at `:1559-1560`) →
per-tile encoding shim (linear Rec.2020 → mid-grey-anchored sRGB OETF → clip; inverse on
the way out, with pre-clip >1.0 pixels taken back from the input) → CoreML → 
`TilePlan.stitch` → fp16 atlas at `ArtifactKey.relativePath` (`:1469-1476`).
`ArtifactKey` already carries `modelID`/`modelVersion`/`prefixHash`/`pipelineVersion`, and
the catalog already has `model_id`/`model_version` columns, so invalidation is free.

**What the classical engine keeps doing, concretely.** Three jobs, and the code changes
needed for each:

1. **Hot pixels — moved upstream of S2.** Today `hotPixelPass` runs inside
   `ClassicalDenoise.apply` at S3 (`:753-756`) and in the graph at `RenderGraph.swift:359-361`.
   The worker must run it before inference, and S3 must then skip it, or a stuck pixel is
   denoised into a smear and then median-replaced against a neighbourhood that no longer
   has one.
2. **Chroma and Colour Smoothness as the finishing pass.** R6's whole reason for
   "hybrid": SIDD is phone noise at ISO ≤ 3200 in sRGB, and a full-frame ISO 12800 file
   has coarser, more chroma-heavy noise than the net saw. `chromaThresholds` +
   `blotchMix` are what catch the residue.
3. **Luminance drops toward zero** — which `ISODefaults.coupled` already does
   (`:1824-1829`), and which E1-02 shows is currently firing a mode too early.

**The one number that must change and does not fall out of the wiring.** `RenderPlan.swift:455`
builds the S3 profile from `NoiseProfile.forISO(captureISO)`. After S2 the σ in the image
is *not* the sensor's σ — it is whatever the net left. Reading it from ISO would make S3
over-shrink a frame the net already cleaned. The profile for S3-after-S2 must come from
`NoiseProfile.estimate(from:)` on the artifact — which is E1-03's dead-and-biased
estimator. **E1-03 is therefore a prerequisite for K-070, not a separate cleanup.**

**What is missing entirely** (matching R6 §I): the worker actor, the CoreML session,
`ModelStore` with SHA-256 verification, the encoding shim, viewport-first tile ordering,
cancel, the progress row, and the "artifact stale" badge. `TilePlan` and `AIDenoiseSplice`
are genuinely complete for what surrounds a model — that part of R6 §0 checks out.

## Checked and found correct (so nobody re-checks it)

- **The à-trous detail-σ table.** `atrousDetailSigma = [0.8907, 0.2007, 0.0856, 0.0413,
  0.0205, 0.0103]` (`DenoiseEngine.swift:496`). I re-derived it from the B3-spline
  `[1,4,6,4,1]/16` à-trous scheme (`‖C_j ⊗ C_j − C_{j+1} ⊗ C_{j+1}‖₂` for unit white
  noise): **0.8908, 0.2007, 0.0855, 0.0412, 0.0204, 0.0102**. Agrees to the last printed
  digit. The `detailSigma(level:)` extrapolation past the table (×0.5 per octave,
  `:692-704`) matches the computed ratio.
- **The hot-pixel sorting network.** The 19-comparator Batcher network generated into the
  shader (`Kernels.swift:808-819`) is a *correct* 8-input sorting network: exhaustive
  0-1-principle test over all 256 inputs, **0 failures**. So `(a3+a4)*0.5` really is the
  median, and the GPU extremum test `max(1-step(v,a7), 1-step(a0,v))` is exactly the
  reference's `value > hi || value < lo` (`DenoiseEngine.swift:1034`).
- **The scale gate does not leak the blotch pass.** I expected a divergence: `gpuPlan`
  computes `kC` and `blotch` from `self.chroma` rather than the scaled engine's
  (`:1284-1287`), so `blotchMix > 0` survives the gate. It is defused one level up —
  `RenderGraph.swift:365-367` guards on `shrinks` (all thresholds zero) and returns
  before the blotch block at `:431`. GPU and CPU agree below `contributingNoiseScale`.
- **Alpha survives the à-trous loop.** `denoiseRemoved` returns `vec4(…, 1.0)`
  (`Kernels.swift:781`), which looked like it would destroy alpha when subtracted — but
  `lumenSubtract` returns `vec4(a.rgb - b.rgb, a.a)` (`Kernels.swift:419`). Correct.
- **The ISO badge and the per-row defaults already respect rendered files.**
  `captureISO` guards on `!PhotoFormats.isRendered` (`DetailPanel.swift:327-331`), so
  `isoDefault` collapses to `Denoise()` for a JPEG and matches
  `AppState.startingRecipe`'s own choice (`AppState.swift:2941-2949`). An untouched JPEG
  reads "Auto" with no modified dots. I nearly filed this as a defect; it was fixed, and
  the fix is documented at `DetailPanel.swift:312-326`.
- **The render side does not hand a rendered file a sensor profile.**
  `ImageSource.swift:122-138` reports `iso: nil` deliberately, so `RenderPlan` uses the
  base-ISO profile. Consistent with the panel.
- **`.off` really is off**, hot pixels included (`ISODefaults.classic(for:)` `:1839-1840`).
- **The GPU change of variables.** `GPUPlan.encodedForward`/`encodedInverse`
  (`:1140-1190`) are written as the quotient form `2(x−x₀)/(√u+√u₀)`, which is what the
  shaders compute (`Kernels.swift:651-658, 670-687`) — the same expression, same
  constants, and the degenerate `a → 0` branch needs no shader branch, as documented.
- **One definition of what a slider means.** `RenderGraph.applyDenoise` reads every
  threshold, knee, protection and mix from `gpuPlan` and re-derives nothing
  (`RenderGraph.swift:355-462`). The claim in the header holds.
- **The scale gate is pinned.** `SpeedBenchTests.swift:90-129` covers the boundary, the
  hot-pixel survival, and that it follows scale rather than pixel count.
- **`TilePlan` degenerate case.** `TilePlan(width: 128, height: 128, tile: 768,
  overlap: 32)` clamps `t = min(768, 128)` and emits two full-frame tiles with
  complementary valid halves; `coversExactly` holds. Correct behaviour, and the reason a
  128-px fixture cannot exercise a fixed-768 model (E1-04).
