Where the drag arithmetic is concerned the contract is in good shape: relative
resolution makes dropped samples harmless (`SliderDrag.swift:12-27`), the release is
treated as the last sample at both the track and the readout, and `FineDrag.resolving`
returns "no new gearbox" so a drag does not write `@State` per event. **No control
publishes a value per mouse event that did not cross a step** — `commit` guards on
`next != value` (`LumenControls.swift:420`) and `updateRecipe` guards on
`updated != old` (`AppState.swift:3122`). The failures below are all in the
*bookkeeping* of a gesture, not in its arithmetic.

---

## The brief's sharpest question: is one drag exactly one undo step?

**No.** Undo boundaries are decided by `(coalescingKey, photo-set, <1.2 s)` alone
(`HistoryCoalescing.swift:26-33`, `HistoryStack.swift:47,51,115-133`). The app knows
when a gesture is in flight — `AppState.sliderGestureActive`, fed by
`sliderGestureChanged` from every slider — and `history.record` never consults it
(`AppState.swift:3130-3132`). Three consequences, plus five key collisions, below.

## Findings

### A2-01 — A grading-wheel drag makes two undo steps per mouse event and evicts real history
severity: S1
confidence: traced
class: defect
size: S
evidence: `LookPanel.swift:540-542` — `hue: bindWheel(path, \Wheel.hue, key: "wheel.\(title).hue")`, `sat: … "wheel.\(title).sat"`, `lum: … ".lum"`. `LumenControls.swift:1597-1599` writes **both** on every sample: `hue = (atan2…)`, `sat = Double(r)`. Each binding is its own `updateRecipe(coalescingKey:)` (`LookPanel.swift:1155-1165`), so the open step's key alternates `…hue` / `…sat` and `HistoryCoalescing.shouldCoalesce` fails its first guard (`key == openKey`) on every write. `HistoryStack.limit = 400` (`:47`), and past it `steps.removeFirst(steps.count - Self.limit)` (`:161`). `MaskPanel.swift:2380-2382` has the identical shape for per-mask wheels.
how the owner sees it: One puck drag on a colour wheel is ~2 undo steps per delivered mouse event — a two-second drag at 60 Hz is ~240 steps. ⌘Z walks back the drag one pixel at a time, and once 400 is passed the *earlier* edits of the session are dropped off the front of the stack and can never be undone.
fix: `LookPanel.wheel` / `MaskPanel.wheelValue` — give the puck's two axes ONE key (`"wheel.\(title).puck"`), or better, have `LumenColorWheel` write hue+sat through a single binding so it is one recipe mutation per sample. Test (LumenAppTests, beside `DragBroadcastTests`): drive 50 synthetic puck samples through the two bindings and assert `history.steps.count == 1`; it goes red with the two-key version substituted back.

### A2-02 — Undo steps are cut by a stopwatch, not by the gesture the app already tracks
severity: S2
confidence: traced
class: defect
size: M
evidence: `AppState.swift:3130` records history unconditionally, then `:3132 if sliderGestureActive { … }` uses the gesture only for persistence. `HistoryStack.swift:126-133` is the whole boundary rule; `HistoryCoalescingTests.testAPauseBeyondTheWindowOpensANewStep` pins the current behaviour, so the lane is green over the defect.
how the owner sees it: Hold a slider still for more than 1.2 s in the middle of a long drag (routine while watching the picture settle) and let go — one hand movement is now two undo entries. The converse also holds: two deliberate, separate drags of the same slider inside 1.2 s become one entry, so ⌘Z jumps past both. docs/12 §12.10 says "one drag = one entry".
fix: `HistoryStack.record` takes a gesture epoch (a monotonically increasing id bumped by `AppState.noteSliderGesture(false)`); `shouldCoalesce` gains a fourth input — same epoch always coalesces, epoch change never does, time only arbitrates keyboard nudges. `HistoryCoalescingTests`: a 3 s pause inside one epoch stays one step; two epochs 100 ms apart are two steps.

### A2-03 — Double-clicking the TRACK of an as-shot row costs two undo steps and ⌘Z lands on a value nobody chose
severity: S2
confidence: traced
class: defect
size: S
evidence: the first click of the double-click is a complete press: `LumenControls.swift:939-941` — `dragStartValue = geometryOfDrag.valueAtPress(x:)` then `value = dragStartValue` — recorded under the row's own key (`"wb.temp"`, `BasicPanel.swift:223`). The second press calls `reset()` → `onReset` → `applyAsShot()` → `binder.edit("wb.preset")` (`BasicPanel.swift:404-410`). Two different keys, so `shouldCoalesce` refuses to fold them.
how the owner sees it: Double-click the Temp track to get back to As Shot, then ⌘Z: the row does not go back to where it was — it goes to whatever Kelvin the first click happened to land on, which the photographer never asked for. A second ⌘Z is needed. Tint is the same (`BasicPanel.swift:245, 260`); the same shape exists wherever `onReset`'s key differs from the row's binding key.
fix: give `reset()` the row's own coalescing key (pass the key into `LumenSlider` alongside the binding, or have `onReset` re-use it), or suppress the first click's jump when `clickCount` will reach 2. Test in LumenAppTests: press-jump + reset on Temp leaves `history.steps.count == 1` and one ⌘Z restores the pre-click recipe exactly.

### A2-04 — ↑/↓ on a focused slider do nothing at all
severity: S2
confidence: traced
class: defect
size: S
evidence: `Keymap.swift:495-511` — the monitor's arrow case yields **all four** arrows (`if state.sliderHoldsFocus { return nil }`) before it dispatches; `LumenControls.swift:582-583` binds only `.onKeyPress(.leftArrow)` and `.onKeyPress(.rightArrow)`. docs/12 §12.5 specifies `↑`/`↓` for the nudge, and gap-table §A's LrC cell is "↑↓ 5 / ⇧10 / ⌥1".
how the owner sees it: Click a slider row, press ↑ — the value does not move and the photo does not change either. The key is swallowed. Every competitor nudges on ↑/↓; Lumen's own spec says it does.
fix: add `.onKeyPress(.upArrow) { nudge(1) }` / `.downArrow { nudge(-1) }` in `LumenControls.swift` beside the existing pair (one line each, same `nudge`). Test: `KeyGrammarTests`-style pair assertion, plus a `SliderNudgeTests` case is already sufficient for the arithmetic — the missing half is the binding, so the guard is an app-level assertion that all four arrow key paths reach `nudge`.

### A2-05 — Five coalescing keys carry two different decisions (K-038 re-verified, and it is wider than the row says)
severity: S2
confidence: measured (every `coalescingKey:` string in `Sources/LumenApp` enumerated; 3 literal duplicates + 2 structural)
class: defect
size: S
evidence:
· `"wb.preset"` — `BasicPanel.swift:405` (`applyAsShot`, clears temp+tint) and `:412` (`applyIlluminant`, writes a preset's Kelvin/tint). Two different decisions, one key. **K-038's "two WB presets": STILL-OPEN.**
· `"curve." + channel.rawValue` — `CurveEditorView.swift:556` (`writePoints`, `keyPrefix + channel.rawValue`) is the key for **every point of a channel**, so moving point A then point B, or adding a point then moving another, is one step. **K-038's "two curve points": STILL-OPEN.**
· `"geometry.crop.aspect"` — `CropPanel.swift:663` is the key for all nine ratios plus the custom one, so 3:2 then 16:9 inside 1.2 s is one step and ⌘Z skips both. **K-038's "two aspect ratios": STILL-OPEN.**
· NEW: `"look.grain.amount"` and `"look.grain.size"` are each used for **two different recipe fields with different ranges** — the film-lab stock grain (`EffectsPanel.swift:246,269`, `filmLab.grain.amount`, size 0.5…2.0) and the creative grain (`:293,304`, `CreativeGrain`, size 0…100). Pull Film Lab's Strength to 0, the rows swap under the pointer, and a creative-grain drag inside 1.2 s folds into the stock-grain step whose `before` is a different field.
· NEW: `"denoise.classic.luma"` / `".chroma"` are shared by the drag binding and by the clearing reset (`DetailPanel.swift:416` vs `:435`; `:462` vs `:476`), so "drag, then double-click to reset" is one undo entry and ⌘Z discards the drag too.
how the owner sees it: ⌘Z after two deliberate, different choices takes both away, and in the grain case takes away a value on a field the photographer was no longer looking at.
fix: make each key name the decision, not the group — `wb.preset.asShot` / `wb.preset.\(illuminant)`, `curve.\(channel).point.\(index)`, `geometry.crop.aspect.\(ratio)`, `look.grain.film.*` vs `look.grain.creative.*`, `denoise.classic.luma.reset`. Test: a `HistoryStack` test per pair asserting two steps; each goes red when the shared key is substituted back.

### A2-06 — A mask-canvas drag commits its release with no key, so it can be two undo steps
severity: S2
confidence: traced
class: defect
size: S
evidence: `MaskCanvas.swift:553, 683, 843, 1005` — `coalescingKey: ended ? nil : coalescingKey("radial")` (and outline/point/line). `HistoryCoalescing.shouldCoalesce` returns false for a nil key (`:30`), and `HistoryStack.record` appends a fresh step.
how the owner sees it: Drag a radial's handle; whenever the pointer moved between the last delivered motion event and the mouse-up — exactly the case `SliderDrag.swift:21-27` says is normal when the main actor is behind — the release becomes its own step. ⌘Z then appears to do nothing (it walks back the last few pixels) and a second ⌘Z is needed.
fix: keep the key on the release (`coalescingKey("radial")` in both branches); the gesture epoch of A2-02 subsumes it. Test: drive a synthetic drag whose release carries new travel and assert one step.

### A2-07 — The readout scrub's "three times finer" is pinned to a width the column no longer has
severity: S3
confidence: measured
class: defect
size: S
evidence: `LumenControls.swift:437-441` — `SliderTrack(width: 426, …)`, with the comment "Three times the develop column's ~142 points" and `:1075` "2.13 points per unit against the track's 0.71". Both numbers are from the retired 94/52/142 layout; the current row is 86/44 and the track is ~180 pt at the 380 pt default (`:245-265`), and the column is draggable 320…520 (`:250-262`). So the scrub is 2.37× the track at the default, 3.55× at 320 pt, and **1.33× at 520 pt**.
how the owner sees it: Widen the develop column — which the app invites, and which makes the *track* more precise — and the readout scrub quietly stops being the precision instrument, because its gain never moved. The help string "Drag to adjust, click to type — ⇧ for fine" keeps promising it.
fix: derive the scrub width from the measured track width (the `GeometryReader` already has it) × 3, hoisted into a `@State` set in `track`'s body, or from `AppState.developPanelWidth − 200`. Test in `SliderDragTests`: for track widths 100…400, assert `travelNeeded` on the scrub track is 3× the track's, parametrically — red the moment 426 is restored.

### A2-08 — Speed Edit's fine gear is 0.1 while the slider's is 0.25, under a comment saying they match
severity: S3
confidence: measured
class: defect
size: S
evidence: `SpeedEdit.swift:133` — "`fine` is ⇧, at a tenth, **matching the slider's own fine drag** rather than inventing a second ratio for the same idea" — and `:144` `* (fine ? 0.1 : 1)`. `FineDrag.scale = 0.25` (`SliderDrag.swift:330`). The comment is not the code.
how the owner sees it: When Speed Edit is wired (A2-11), ⇧ will mean two different amounts of precision depending on whether the hand is on the photograph or on the panel — the exact "hands learn one slider, know every slider" property §12.5 is written to protect.
fix: one constant. `SpeedEdit.delta` uses `FineDrag.scale`; `SpeedEditTests` gains an equality assertion between the two so they cannot drift again.

### A2-09 — The two arithmetic examples docs/12 §12.5 prints are both refused, and one of them silently means something else
severity: S3
confidence: measured
class: parity-gap
size: S
evidence: docs/12 §12.5 "Typed entry … accepts arithmetic (`x/2+0.5`, `+1.3`)". `SliderEntry.decimal` (`SliderEntry.swift:98-106`) rejects any character outside `[0-9.\-+eE]`, so `x/2+0.5` returns nil (the field silently keeps its value, `LumenControls.swift:1143`), and `+1.3` matches no `+=` prefix and falls through to `.absolute(1.3)` — deliberate, argued at `:17-24`, and the opposite of what the spec's own example means.
how the owner sees it: Types the value the spec documents; on Exposure at +0.4, `+1.3` sets 1.3 rather than 1.7, with no complaint.
fix: not the parser — the doc. Amend docs/12 §12.5's example cell to the shipped grammar (`+= 0.3`, `* 2`) per docs/00 §3, and say in the row that a leading sign is absolute. If the owner wants relative signs instead, that is a different, larger change and needs the negative-absolute answer first.

### A2-10 — ⌥ does nothing on any slider: no fine step, no clipping view, no hard-limit reach
severity: S3
confidence: measured
class: parity-gap
size: M
evidence: `LumenSlider` reads `NSEvent.modifierFlags.contains(.shift)` only (`LumenControls.swift:404`); `.option` appears in the file solely in `LumenSectionHeader` (`LumenControls.swift:1236`) and `LumenSegmented`. severity: S3

## What is right, and worth not breaking in U1

The drag arithmetic (relative resolution, release-is-a-sample at both track and
readout, `FineDrag`'s rebase, `nudged`'s one-sided soft clamp, `ScrollNudge`'s
residue, `crossesDetent`) is tested in LumenCore and is the strongest part of this
area. `SliderEntry` refuses NaN/inf/hex *before* the clamp, which is the difference
between a bad render and a sidecar that collapses to `{}`. The per-event publish
discipline — `commit`'s `next != value` guard, `FineDrag.resolving` returning nil,
`updateRecipe`'s `updated != old`, the wheel's half-second settle closer — means no
slider publishes per mouse event. U1 changes the anatomy of this row; none of the
above is anatomy.
